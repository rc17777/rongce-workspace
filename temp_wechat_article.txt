大家好，我是agentAlpha社区的阿泽。今天给大家分享一道字节 Agent 岗三面的高频面试题。
👔面试官：讲讲 Agent 的记忆系统怎么设计？
🙋‍♂️我：记忆系统啊，就是把聊天记录存起来，下次对话的时候塞回上下文里，让模型记得之前说过什么。用 LangChain 的 Memory 模块就行。
👔面试官："塞回上下文" 就完了？那上下文窗口装不下了怎么办？用户一个月前说过的偏好，你也全塞进去？
🙋‍♂️我：呃…… 那就只存最近几轮的，太远的就不要了。
👔面试官：不要了？用户上周说自己对花生过敏，你这周就忘了，给人推荐花生酱饼干，出了问题谁负责？记忆不是 "存不存" 的问题，是 "什么该记、什么该忘、什么时候想起来" 的问题。你对记忆系统的理解还停留在 Demo 阶段。
这个问题确实很容易答浅。很多人做 Agent，第一个版本记忆就是个滑动窗口，能跑就行。但真到了生产环境，记忆系统的复杂度会超出你的预期。下面我从基础分类到工程落地，把记忆系统完整拆开讲。◆💡 简要回答
我的理解是，Agent 的记忆系统是一个分层架构，不能一概而论。
最上层是工作记忆，就是当前上下文窗口里的内容，模型直接能用，但是容量最小。中间是短期记忆，存整个会话的对话历史，会话结束就清掉，用来维持单次任务的连贯性。最底层是长期记忆，跨会话持久化存储，比如用户的偏好、历史决策、经验教训，需要的时候通过检索召回。
真正的难点不在 "存"，而在 "管"：长期记忆怎么检索才准、什么记忆该淘汰、新旧记忆冲突了听谁的、怎么控制 Token 成本。这些问题没想清楚，记忆系统最后只会变成噪声源，帮倒忙。◆📝 详细解析先搞清楚：为什么需要分层记忆？
很多人第一次接触 Agent 记忆，会觉得 "不就是存聊天记录吗"，然后直接把所有历史全塞回上下文。
这么做有三个致命问题：
第一，装不下。 上下文窗口再大也是有限的，GPT-4o 也就 128K，聊久了肯定溢出。你说用 1M 上下文的模型？那成本翻十倍，延迟也翻几倍，商业上根本跑不通。
第二，会变蠢。 上下文越长，模型越容易忽略中间位置的信息，学术上叫 "Lost in the Middle"。你塞了一堆历史进去，模型根本没 "看" 进去，白花钱还拖速度。
第三，噪声大。 十天前的闲聊内容跟今天的任务有什么关系？全塞进去只会干扰模型判断，反而降低准确率。
所以记忆必须分层 —— 不同时效、不同重要性的信息，放在不同的地方，用不同的策略管理。就像人脑也分瞬时记忆、短期记忆、长期记忆，不是一锅粥。第一层：工作记忆 —— 模型正在 "想" 的内容
工作记忆就是大模型的上下文窗口本身，每一轮推理都能直接看到。
这一层的特点是：最快、最准，但最贵、容量最小。
你可以把它理解成 CPU 的寄存器 —— 离计算单元最近，读写零延迟，但只有几十个字节。同样，工作记忆里的每一个 Token 都是要花钱的，不能什么都往里塞。
工作记忆里通常放三类东西：System Prompt角色设定、安全规则、输出格式 —— 这些是固定的，每轮都要有最近几轮对话保证当前对话的连贯性当前任务状态比如 "用户正在查询订单号 12345"—— 任务相关的关键信息
面试里一个常见的追问：工作记忆满了怎么办？
答案不是 "换更大的模型"，而是 "该腾地方了"—— 把不重要的内容移到短期记忆或者压缩掉，给新内容腾空间。这就是记忆管理的核心动作。第二层：短期记忆 —— 会话内的上下文缓冲
短期记忆是会话级别的，一次对话从头到尾的完整记录都存在这里。
存储介质一般用 Redis 或者内存数据库，按 session_id 存，会话结束后按 TTL 自动过期。比如用户聊了半小时，关了页面，24 小时后这条短期记忆就清掉了。
短期记忆的实现方案有三种，从简单到复杂：
方案一：滑动窗口
最简单粗暴，只保留最近 N 轮对话，超出的直接丢弃。
优点：零实现成本，信息完整无损。缺点：窗口外的信息彻底丢失，"金鱼脑"。适合：客服机器人、单轮任务型 Agent，聊完就忘也没关系。
方案二：滚动摘要
对话长到一定程度，就把前面的内容用 LLM 摘要压缩一下，腾出空间。
优点：能保留更长时间的信息，Token 成本可控。缺点：摘要不是无损的，会有事实漂移 —— 用户明明说的是 "不喜欢红色"，摘要两轮后可能变成 "用户偏好红色"。适合：中等长度的对话，对精确性要求不是极高的场景。
方案三：关键帧机制
借鉴视频编码的思路：重要节点完整保存，中间过程只存摘要。
什么是关键帧？用户明确表达偏好、任务目标变更、重要工具调用结果 —— 这些是不能丢的。怎么判断关键帧？简单的用规则触发，复杂的用轻量分类模型打分，比每轮调大模型便宜得多。
这是工业界比较推荐的方案，兼顾了成本和准确性。第三层：长期记忆 —— 跨会话的知识沉淀
这才是记忆系统真正的价值所在，也是面试最容易考深的地方。
短期记忆会话结束就没了，长期记忆是持久化的 —— 用户上周说过的话、上个月做过的决策、甚至半年前提过的偏好，都能存下来。下次用户再来，系统能 "认出" 他，记得他的习惯。
长期记忆按内容又分三类，这个分类源自认知心理学，面试说出来很加分：
情景记忆（Episodic Memory）
存的是 "发生过什么事"，比如具体的对话片段、某次任务的执行记录。特点：时间属性强，有具体场景。用途：回溯历史对话、复盘之前的决策。
语义记忆（Semantic Memory）
存的是 "事实性知识"，比如 "用户对花生过敏"、"用户常用编程语言是 Python"、"用户所在部门是市场部"。特点：结构化、事实性、更新频率低。用途：个性化服务、偏好预判 —— 这是用户感知 "这个 Agent 懂我" 的关键。
程序记忆（Procedural Memory）
存的是 "怎么做事情"，比如 "用户喜欢先看摘要再看详情"、"上次做数据分析时用户要求按周维度汇总"。特点：是经验和方法论，不是具体事实。用途：优化工作流、减少重复沟通。长期记忆怎么用？—— 检索式召回
不可能把所有长期记忆都塞回上下文，那样几万条早就爆了。正确的做法是按需检索：当前用户问了一个问题，先去长期记忆库里搜相关的内容，只把最相关的 Top-K 条捞出来，拼到上下文里。
这本质上就是 RAG，只不过知识库不是产品文档，而是用户的历史记忆。长期记忆检索的三重评分 —— 只看相似度是初级做法
很多团队做长期记忆检索，就只算一个语义相似度，找最像的几条。这是不够的。
斯坦福 Generative Agents 论文里提出了一个三重评分框架，工业界也在广泛使用：
第一重：相关性（Relevance）
就是语义相似度，这条记忆跟当前问题有没有关系。用 Embedding 余弦相似度计算，最基础的一项。
第二重：重要性（Importance）
这条记忆本身有多重要？"用户对花生过敏" 比 "用户今天喝了杯咖啡" 重要得多。怎么打分？可以用 LLM 打 1-10 分，也可以训练轻量模型做分类。重要性低的记忆，哪怕相关也排后面。
第三重：时效性（Recency）
越新的记忆权重越高，符合人脑的遗忘曲线。一般用指数衰减函数：时间越久，分数越低。比如半年前的偏好，可能已经变了，权重就要打折扣。
最终分数 = 相关性 × α + 重要性 × β + 时效性 × γ，三个权重按业务场景调。
面试的时候能讲出这三重评分，说明你真的深入思考过，不是只会调向量库。工程踩坑：记忆系统的几个真实问题
讲完基础架构，再补几个生产环境踩过的坑，这是拉开差距的地方。
坑一：记忆会越存越多，最后检索变慢、噪声变大
现象：系统跑了三个月，向量库膨胀了十几倍，检索从 200ms 变成 2s。
解法：必须有遗忘机制。不是什么都该永久记住 —— 不重要的、太久没访问的、已经过时的，该删就删。具体做法：重要性低于阈值的，30 天后自动归档；半年没被检索过的，直接清理。
坑二：新旧记忆冲突，听谁的？
现象：用户上个月说 "我用 React"，这个月说 "我转 Go 了"，两条记忆都在，检索出来模型就懵了。
解法：时间戳优先 + 冲突检测。每条记忆都带创建时间，冲突时默认采信新的。复杂场景用小模型判断一下是 "更新" 还是 "补充"。
坑三：摘要压缩导致事实漂移
现象：滚动摘要滚了几轮之后，信息慢慢失真，最后模型记的跟用户说的完全是两回事。
解法：关键事实结构化存储，不参与摘要压缩。比如用户的核心偏好、过敏信息、重要参数，单独存在结构化槽位里，永远是原始值。
坑四：记忆注入破坏 Prompt Cache
现象：现在大模型都有 Prompt Cache 功能，System Prompt 固定的话能省 30% 成本还提速。但记忆系统每轮都往 System 里塞东西，缓存直接失效。
解法：记忆不要放 System Prompt 里，放 User Message 部分；或者不要每轮都更新，攒几轮再统一更新一次。最后：记忆系统的本质是什么？
聊到最后，可以升华一句。
很多人觉得记忆系统就是个存储模块，其实不是。记忆系统的本质是认知管理—— 它决定了 Agent 在每一个时刻，"脑子里装着哪些信息"。
存什么、忘什么、什么时候想起、以什么形式呈现 —— 这些决策直接决定了 Agent 的表现。就像人一样，真正聪明的人不是过目不忘，而是在需要的时候，能准确想起该想的事情。
