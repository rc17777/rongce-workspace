## 1.1 审前准备阶段（进场前3-5天）

### 1.1.1 资料预采集——不进场就先拿到的数据

在正式发审计通知书之前，通过公开渠道或主管部门先行获取以下数据，用于构建"预期使用率"的参照基线：

| 预采数据类型 | 获取途径 | 用途 |
|------------|---------|------|
| 学校基本信息 | 教育局官网/教育事业统计年报 | 学生数、班级数、教师数 → 计算设备配置标准是否超标 |
| 学校等级/类别 | 教育局官网/省级示范校名单 | 识别"评估采购"——等级评审年份前后的大额采购 |
| 同类学校设备配置 | 政府采购网/公共资源交易平台 | 横向比对：同类学校买了什么、花多少钱、什么时候买的 |
| 教学大纲/课程标准 | 教育部/省教育厅官网 | 实验教学计划中的应开实验项目和课时数 |
| 学校公开信息 | 学校官网/公众号 | 智慧校园/智慧教室的宣传报道——与实际情况的"温差" |

### 1.1.2 构建"预期使用模型"——进场前就要心里有数

在拿到被审计单位数据之前，先用公开数据建立一套"这个设备应该在什么时间、被什么人在什么场景下使用"的预期模型。

**以智慧教室为例：**

```
输入参数：
  - 学校：XXX中学
  - 班级数：36个班（每年级12个班）
  - 智慧教室数：8间
  - 每日可排课时段：上午4节 + 下午3节 = 7节
  - 每周教学日：5天

理论最大使用率：
  每周可排课时段 = 8间 × 7节 × 5天 = 280节·教室
  每周实际课时 = 36班 × 35节（初中标准周课时）= 1260节
  智慧教室理论使用率 = 280 / 1260 = 22.2%（即最多22.2%的课在智慧教室上）

如果智慧教室配置了36间（每班一间）→ 理论最大使用率 ≈ 100%
如果智慧教室配置了8间 → 理论最大使用率 ≈ 22.2%
```

**这个模型的意义：** 进场前你就知道——如果这个学校建了36间智慧教室但只有8间的使用率，那多出来的28间去哪了？这就是你的第一个审计线索。

### 1.1.3 审计抽样策略

教育装备审计不追求全覆盖——追求覆盖"高价值+高风险"资产。

```
抽样规则（三层筛选）：
  第一层：金额筛选
    → 单项合同金额 ≥ 50万元的资产 100%覆盖
    → 单项合同金额 10-50万元的资产 按30%随机抽样
    → 单项合同金额 < 10万元的资产 5%随机抽样（异常发现后可扩大）
  
  第二层：风险加权
    → "评估/创建/评审"时间节点前后6个月内采购的资产 → 权重×3
    → 供应商为异地/非教育行业主流供应商 → 权重×2
    → 资产类型为学校首次采购（无历史同类设备）→ 权重×2
    → 质保期已过但无后续维保合同的设备 → 权重×1.5
  
  第三层：异常特征
    → 固定资产台账中"使用状态=在用"但存放地点为"仓库/库房" → 直接列入
    → 同一供应商在同一学校连续中标≥3次的设备类项目 → 直接列入
```

**抽样结果示例：**
```
XX学校固定资产台账：共1563项，总原值4872万元
  → 第一层金额筛选后：287项，总原值3820万元（覆盖78%金额）
  → 第二层风险加权后：前20项高风险 → 重点审计
  → 第三层异常特征：发现5项台账异常 → 直接列入
  → 最终审计范围：312项，总原值3910万元（覆盖80%金额）
```

## 1.2 现场数据采集阶段（3-5天）

### 1.2.1 第一步：物理盘点——先看实物在不在

**操作流程：**
```
步骤1：从固定资产台账抽取审计样本清单
步骤2：不提前通知使用部门，直接按台账记录的"存放地点"前往核验
步骤3：逐项拍照留证（设备照片+存放环境+铭牌/资产标签特写）
步骤4：记录实际存放地点与台账记录的差异
步骤5：对"找不到"的资产，当场要求使用部门书面说明去向
```

**实物核验记录表：**

| 资产编号 | 资产名称 | 台账记录地点 | 实际存放地点 | 偏差 | 实物状态 | 现场照片编号 |
|---------|---------|------------|------------|------|---------|------------|
| ZC-2023-001 | 86寸交互大屏 | 教学楼301 | 教学楼301 | 一致 | 正常使用 | IMG_001 |
| ZC-2022-045 | 3D打印机 | 创客实验室 | 仓库B-3 | ⚠️ 搬至仓库 | 落灰、未拆封 | IMG_045 |
| ZC-2021-089 | 虚拟仿真实验台 | 实验楼502 | 未找到 | 🔴 实物缺失 | — | — |

**重点关注以下"实物状态"信号：**

| 观察信号 | 推断 | 后续动作 |
|---------|------|---------|
| 设备表面有明显积灰 | 长期未使用 | 结合日志验证停用时长 |
| 包装未拆/保护膜未撕 | 验收后从未使用 | 🔴 直接定性：事实闲置 |
| 电源线未连接/网线未插 | 物理上不具备使用条件 | 拍照留证+立即追问 |
| 设备周围堆满杂物/无法靠近 | 物理上不便使用 | 拍照留证 |
| 设备位置与功能不匹配（如精密仪器放在无空调的房间）| 不具备正常使用环境 | 记录环境参数（温度/湿度/灰尘）|
| 资产标签被撕毁/覆盖 | 可能已被私自处置 | 核对资产编号的其他标识（如MAC地址）|

### 1.2.2 第二步：日志数据采集——按设备类型操作

**通用采集SOP：**

```
1. 到达设备所在位置
2. 确认设备处于通电状态
3. 由被审计单位IT/设备管理员操作，审计人员全程目视
4. 登录设备管理后台/系统
5. 导出指定时间范围的日志（时间范围：从验收日期至审计基准日）
6. 保存原始文件（不接收截图、不接收二次加工的Excel）
7. 审计人员用U盘直接拷贝，或现场上传至审计专用云盘
8. 填写数据采集单，双方签字确认数据完整性和时间范围
```

**分设备类型的数据采集操作要点：**

**A. 智慧教室中控系统：**
```
登录方式：浏览器访问中控平台IP:端口
导出路径：系统管理 → 日志管理 → 设备运行日志 → 选择时间范围 → 导出CSV
必须验证：导出后在Excel中打开，确认"记录条数"是否与系统显示的"总日志条数"一致
常见陷阱：部分中控只保留3个月日志 → 如果超过3个月，要求从备份服务器恢复
最低要求：至少覆盖最近1个完整学期
```

**B. 实验室仪器（高精密设备）：**
```
操作方式：不同于IT系统，实验仪器日志通常在设备自带的操作面板或工作站软件中
采集方式：
  → 方式1（优先）：设备厂商提供的Service Tool/维护软件 → 导出运行日志
  → 方式2：设备面板 → 维护菜单 → 使用统计 → 拍照记录
  → 方式3：连接设备的控制电脑 → 查找软件安装目录下的Log文件夹
验证手段：核对设备面板显示的"总运行小时数"是否与日志累计一致
```

**C. 计算机教室：**
```
登录方式：电子教室软件（如极域、联想等）管理端
导出路径：管理端 → 统计报表 → 上机记录统计 → 选择机房/时间 → 导出
必须验证：导出后的机器台数是否与机房实际机器台数一致
          → 如果不一致，说明部分机器的日志未被采集（可能网线断开/软件未装）
```

### 1.2.3 第三步：排课/教学数据对照采集

**这是教育装备审计独有的关键步骤——设备日志提供了"实际使用"的数据，排课系统提供了"应使用"的参照：**

| 采集项 | 来源系统 | 采集内容 | 用途 |
|--------|---------|---------|------|
| 完整学年课表 | 教务排课系统 | 每间教室每个时段安排的课程、教师、班级 | 构建"应使用时间表" |
| 教师任课信息 | 教务系统 | 教师姓名、所教学科、所教班级 | 关联到设备日志中的"使用者"字段 |
| 实验教学计划 | 教务处/教学大纲 | 每学期每门课的实验项目、课时、所需仪器 | 判断实验室设备是否按计划使用 |
| 教师培训记录 | 教师发展中心/人事处 | 新设备操作培训的参训人员名单、培训内容、培训日期 | 判断设备是否"有人会用" |
| 招生/分班数据 | 教务处 | 在校生人数、班级数、分班名单 | 计算生均设备投入 |

### 1.2.4 第四步：人员访谈——分层抽样、结构式提问

**访谈对象分层：**

| 层级 | 访谈对象 | 人数 | 重点问题方向 |
|------|---------|------|------------|
| 管理者 | 分管副校长/教务处主任/总务主任 | 2-3人 | 设备采购决策过程、使用的整体情况、存在的问题 |
| 使用者 | 学科教师（至少覆盖3个不同学科+不同年龄段）| 5-8人 | 实际使用频率、使用中遇到的困难、不会用的功能 |
| 支撑者 | 信息技术教师/实验员/设备管理员 | 2-3人 | 设备故障频率、维修情况、培训组织情况 |
| 受益者 | 学生（随机选取，至少2个年级）| 5-10人 | 有没有在智慧教室上过课？频次多少？ |

**结构化提问——每个访谈对象必问的10个问题：**

```
1. 你知道学校有哪些智慧教室/新型教学设备吗？
2. [教师] 你上一次使用XX设备是什么时候？做了什么？
   [管理员] 你上一次维护XX设备是什么时候？
3. 你觉得使用这些设备的频率够吗？不够的原因是什么？
4. 从你入职/设备安装到现在，你接受过几次相关培训？
5. 你觉得培训够用吗？还有哪些功能你想用但不会用？
6. 设备出过故障吗？报修到修好大概要多久？
7. 如果这个设备明天被搬走，对你的教学/工作有影响吗？（关键问题——测真实依赖度）
8. 你觉得花这么多钱买这些设备，值吗？
9. 如果让你提一个建议改善设备使用，你会说什么？
10. 还有什么我没问到但你觉得应该让审计知道的？

访谈原则：
  → 不录音（降低防御心理）
  → 先聊日常再切入设备（建立信任）
  → 不要说"审计"，说"了解设备使用情况"
  → 一个人访谈，一个人记录（或现场笔记，事后整理）
  → 关注"不一致"——管理者说"用得不错"+教师说"半年没开过"=深度矛盾
```

## 1.3 数据分析阶段（2-3天）

### 1.3.1 "应使用 vs 实使用"对照分析

**核心分析框架：**

```
第一步：生成"应使用时间表"
  输入：排课系统的完整课表
  处理：筛选出安排在智慧教室/实验室的课程
  输出：每间教室、每个时段、应有的课程内容和任课教师

第二步：生成"实使用时间表"  
  输入：中控系统/设备日志
  处理：提取开机事件、活跃时段
  输出：每间教室、每个日期、实际的开机时间和活跃时长

第三步：逐格对照
  应使用时间表[教室X][周一第3节] = "语文课，张老师"
  实使用时间表[教室X][周一第3节] = 设备未开机
  → 判定：有课但设备未使用 → 教师未使用智慧教室功能
```

**自动化脚本逻辑（可交给融策数据处理脚本生成器）：**

```python
# 伪代码——分析逻辑示意
import pandas as pd

# 加载数据
schedule = pd.read_csv("排课表.csv")     # 列：教室, 日期, 节次, 课程, 教师
logs = pd.read_csv("设备日志.csv")        # 列：设备ID(对应教室), 开机时间, 关机时间

# 构建应使用网格
schedule['time_slot'] = schedule['日期'] + '_' + schedule['节次']

# 判断每个应使用时段设备是否开机
for idx, row in schedule.iterrows():
    room = row['教室']
    slot_start = row['上课时间']
    slot_end = row['下课时间']
    
    # 查找该时段内的设备开机记录
    room_logs = logs[(logs['设备ID'] == room) & 
                     (logs['开机时间'] <= slot_start) & 
                     (logs['关机时间'] >= slot_end)]
    
    if len(room_logs) == 0:
        schedule.at[idx, '设备使用'] = '未用'
    else:
        schedule.at[idx, '设备使用'] = '已用'

# 统计
usage_rate = len(schedule[schedule['设备使用']=='已用']) / len(schedule)
print(f"智慧教室使用率：{usage_rate:.1%}")
```

### 1.3.3 交叉验证执行流程

**以"智慧教室301第3节语文课"为例的交叉验证过程：**

```
验证节点1：排课系统 → "周三第3节，301教室，语文，王老师"
验证节点2：中控日志 → "周三9:45开机，10:30关机" ✅ 有开机
验证节点3：交互大屏触摸记录 → "该时段触摸事件数：3次" ⚠️ 一节课45分钟只触屏3次？
验证节点4：录播系统 → "该时段未启动录播" → 正常（讲授课可以不录）
验证节点5：学生访谈 → "王老师确实在智慧教室上课，但只用投影放PPT，从不用大屏互动"

结论：设备"在使用"但"使用层次极浅"——相当于花10万买了一台投影仪
审计意见：设备功能利用率不足，建议针对性培训或调整配置
```

### 1.3.4 闲置损失金额计算

**计算逻辑（可用于审计报告）：**

```
方法一：资产利用率法
  闲置损失 = 合同金额 × (1 - 实际使用率)
  示例：智慧教室一套50万，3年使用率12%
  闲置损失 = 50万 × (1-12%) = 44万

方法二：等效替代法（更严谨，推荐用于报告）
  该设备实际提供的服务 = 使用率 × 理论最大服务能力
  如果达到相同服务量，只需要合同金额 × 实际使用率的设备即可
  多花的钱 = 合同金额 × (1 - 实际使用率)
  
  验证：如果A校100万的智慧教室使用率90%，B校100万同样配置的使用率10%
  B校多花了 100万 × (1-10%) = 90万 → 这90万就是"财政资金损失浪费"

方法三：全生命周期法（最完整）
  闲置损失 = 设备折旧 + 运维费 + 场地占用机会成本 + 人员浪费
  
  示例计算：
    设备原值：50万，5年折旧
    年折旧：10万
    年维保费：2万
    场地占用（按当地租金折算）：1万
    兼职管理员人力成本分摊：3万
    年闲置率：85%
    
    年损失 = (10+2+1+3) × 85% = 13.6万/年
    3年累计损失 = 40.8万
```

## 1.4 典型审计发现问题及取证要求

### 1.4.1 场景一："采购后从未投入使用"

**问题描述：** 设备完成验收后，包装未拆/电源从未接通/无任何使用记录

**证据链要求：**
```
证据1：实物照片（包装完好、保护膜未撕、电源线未连接）
证据2：设备日志（零条运行记录或记录条数=验收当天的测试记录）
证据3：访谈记录（设备管理员/教师确认"从未使用过"）
证据4：采购合同+验收报告（确认验收日期和金额）
证据5：排课系统（证明该设备的理论使用场景客观存在）

需要排除的情况：
  □ 设备属于"备用机"且有正式审批文件 → 不判定为闲置
  □ 设备因场地未竣工暂存 → 需核实场地竣工时间和暂存审批
```

### 1.4.2 场景二："验收后断崖式闲置"

**问题描述：** 验收后前3个月正常使用，之后使用率断崖下跌至接近零

**证据链要求：**
```
证据1：验收后逐月使用率趋势图（可视化）
证据2：断崖节点的原因追溯——设备故障、教师调离、课程改革？
证据3：断崖发生后的运维工单——有没有报修？有没有修好？
证据4：访谈记录——断崖前后负责的教师/管理员还原当时情况

审计定性关键：
  → 如果是"教师不会用"→ 培训投入不足，管理责任
  → 如果是"设备故障无人修"→ 运维缺位，管理责任
  → 如果是"课程改革导致设备不再需要"→ 采购决策失误，规划责任
```

### 1.4.3 场景三："表面在使用，实质走过场"

**问题描述：** 设备有开机记录，但深度使用为零——交互大屏只当投影用

**证据链要求：**
```
证据1：设备日志中的交互记录（触摸、书写、投屏次数）显著低于同类
证据2：访谈记录（教师坦言"只会放PPT"）
证据3：培训记录（该教师是否接受过深度培训）
证据4：对比——使用率正常 vs 使用率浅层的教师，培训次数差异

审计意见定位：不是"闲置"，是"能力闲置"——系统功能利用率不足
```

## 2.1 审前准备阶段

### 2.1.1 资料预采集

| 预采数据类型 | 获取途径 | 用途 |
|------------|---------|------|
| 医院等级评审公告 | 卫健委官网 | 识别"等级评审采购"——评审前后半年的设备采购 |
| 同级同类医院设备配置 | 卫健委统计年报/公开数据 | 建立设备配置标准参照（如：每百张床位CT数）|
| 医保DRG/DIP结算数据 | 医保局公开统计 | 该医院的病种结构——决定设备配置是否合理 |
| 大型设备配置许可证 | 卫健委官网公示 | 是否持证上岗、是否超范围使用 |
| 医院公开的诊疗数据 | 医院官网/年报 | 门急诊量、住院量、手术量——反推设备需求容量 |

### 2.1.2 构建"设备需求预测模型"

**以CT为例：**

```
输入参数（从公开数据获取）：
  - 医院等级：三级乙等
  - 年门急诊量：80万人次（公开数据）
  - 年住院量：3万人次
  - 开放床位数：800床
  - 同类同级医院CT配置基准：1台/500床（行业经验值）

预测：
  该院合理CT配置 = 800床 ÷ 500床/台 ≈ 1.6台 → 1-2台合理
  如果该院有3台以上CT → 首先怀疑存在超配闲置
```

### 2.1.3 医疗设备审计抽样策略

```
抽样规则（四层筛选）：

第一层：金额筛选（大型设备100%覆盖）
  → 单项原值 ≥ 100万元的设备 → 100%覆盖
  → 单项原值 50-100万元 → 50%随机抽样
  → 单项原值 < 50万元 → 10%随机抽样

第二层：使用强度加权（高风险优先）
  → 年检查量 < 同类医院同级设备中位数的50% → 权重×3
  → 设备已购买≥3年，但累计检查量 < 行业标准的50% → 权重×3
  → 设备已过质保期，但近1年无任何维保记录 → 权重×2

第三层：效益异常
  → 年检查收入 ÷ 设备原值 < 0.3（3年回不了本）→ 权重×2
  → 耗材消耗量/检查量比值显著低于同类设备 → 权重×1.5

第四层：管理异常
  → 设备操作人员资质过期/无证 → 直接列入
  → 设备配置许可证过期 → 直接列入
  → 连续6个月无质控记录的检验设备 → 直接列入
```

## 2.2 现场数据采集阶段

### 2.2.1 医疗设备数据采集四层递进

**医疗设备的数据采集必须按"可信度从高到低"的顺序递进采集，每一步都要和上一步交叉比对：**

```
第一层：计费数据（最不可抵赖，优先级最高）
  采集来源：HIS系统 → 财务管理 → 收费明细查询
  查询条件：检查/治疗项目名称、执行科室、设备（如有字段）
  时间范围：设备验收日期至审计基准日
  导出格式：CSV，包含每条收费记录的字段：日期、患者ID、项目名称、项目编码、
           数量、单价、金额、执行科室、开单医生

  验证：总金额是否与财务收入账一致

第二层：临床产出数据（医技系统）
  影像设备 → PACS/RIS → 按设备导出的检查量
  检验设备 → LIS → 按仪器导出的检测量
  手术设备 → 手术麻醉系统 → 手术记录中使用的设备

第三层：设备物理运行数据（设备自身日志）
  CT球管曝光次数、MRI磁体运行小时数、超声探头使用小时数
  采集方式：设备面板/Service Tool → 总运行量统计

第四层：运营支撑数据
  耗材/试剂领用记录
  维保/维修工单
  设备巡检记录
  人员排班/考勤记录
```

### 2.2.2 逐层交叉比对——找到"不一致"

**这是医疗设备审计最核心的操作——四层数据两两比对，任何不一致都是线索：**

```
比对1：HIS计费 vs PACS/LIS产出
  HIS显示某CT全年检查5000人次
  PACS显示该CT全年影像归档4800个检查号
  偏差 = 5000 - 4800 = 200人次
  → 这200次计费没有产生影像？→ PACS漏传 or 重复计费？

比对2：PACS产出 vs 设备物理计数
  PACS显示该CT全年5000人次
  CT球管曝光计数年度增量 = 4200次
  偏差 = 5000 - 4200 = 800次
  → 如果不增强扫描，1人次=1次曝光 → 偏差5%以内可接受
  → 如果偏差>10% → PACS数据或设备物理计数有一方不准

比对3：HIS计费 vs 耗材/试剂消耗
  HIS显示全年血糖检测10万次
  试剂消耗量 = 10万测试用的试剂量
  比对 → 是否匹配？偏差>20% = 有问题

比对4：设备运行日志 vs 维保工单
  设备日志记录连续180天零运行
  维保工单系统显示该设备在此期间有2次"巡检正常"
  → 巡检人员根本没有实际检查设备运行状态 → 虚假巡检
```

### 2.2.3 大型影像设备专项采集操作

**CT/MRI/DSA现场数据采集SOP：**

```
步骤1：进入设备操作间
  → 不提前通知放射科——防止提前"补数据"
  → 要求操作技师在场
  → 审计人员全程目视设备屏幕

步骤2：采集设备物理运行计数
  CT设备：
    → 进入Service/维护界面
    → 记录：Total Exposure Count（总曝光次数）
    → 记录：Tube Usage（球管使用量，单位：扫描秒或mAs累计）
    → 拍照保存设备屏幕截图
    → 如果设备有上一个球管的更换记录 → 也要拍照
  
  MRI设备：
    → 进入Service界面
    → 记录：Magnet Hours（磁体总运行小时数）
    → 记录：Total Scan Count（总扫描次数）
    → 记录：Cold Head运行小时数

步骤3：采集设备操作台记录的检查历史
  → 设备操作台 → 患者列表/检查历史
  → 查看最近一周的检查记录——确认设备确实每天在做检查
  → 随机抽查某一天的记录 → 到PACS里核对是否确实有对应影像

步骤4：核对设备资产标签
  → 拍照设备机身铭牌（型号、序列号、出厂日期）
  → 核对与固定资产台账是否一致
  → 核对与配置许可证是否一致
```

### 2.2.4 医疗设备人员访谈提纲

**分层访谈对象及核心问题：**

| 访谈对象 | 核心问题 | 需要观察的"非语言信号" |
|---------|---------|---------------------|
| 科室主任 | "这台设备每天排多少病人？等多久能约上？" | 等候天数长→设备不够用；等候天数=0→没人约 |
| 操作技师 | "你一天最多做多少个病人？正常的量是多少？" | 如果"正常量"远低于同类医院→设备没饱和 |
| 设备科工程师 | "这台设备过去一年报修过几次？最长一次停用多久？" | 对比维修工单——看看有没有"瞒报"的故障 |
| 财务/收费处 | "这台CT上月收入大概多少？" | 与HIS系统导出的数据对比 |
| 分管副院长 | "买这台设备时，是怎么论证的？预期的年检查量是多少？" | 实际量 vs 预期量的差距=决策失误的证据 |

**关键追问技巧（当发现疑点时）：**

```
当被问到"为什么检查量这么低"时，常见回答及追问：

回答A："病人少"
  → 追问："周边同类医院的CT检查量大概多少？你们有比较过吗？"
  → 追问："有考虑过和其他医院共享设备或者转诊吗？"

回答B："设备太高端，适用的病人少"
  → 追问："当初采购时，论证报告里预期适用病人量是多少？"
  → 追问："既然现在发现不适用，有向卫健委申请调整配置吗？"
  → 这直接否定了采购决策的合理性

回答C："技师不够/技师离职了"
  → 追问："技师什么时候离职的？有招聘新人的计划吗？"
  → 追问："设备停用了多长时间？期间有做维护保养吗？"

回答D：[沉默/回避/说不知道]
  → 记录："被询问人未能就检查量偏低的原因做出合理解释"
  → 这个写在审计报告里比任何结论都有力
```

## 2.3 数据分析阶段

### 2.3.1 CT设备四维效率分析示例

**以一台采购价2000万的64排CT为例：**

```
═══════════════════════════════════════════
设备四维效率分析——西门子SOMATOM Definition AS 64排CT
设备原值：2000万元 | 验收日期：2023年6月 | 分析基准日：2026年6月
═══════════════════════════════════════════

维度1：使用率
  ┌─────────────────────────────────────┐
  │ 年检查量：3200人次                    │
  │ 行业基准（同级医院64排CT）：5000-8000人次│
  │ 与基准的比值：3200/5000 = 64%          │
  │ 日均检查量：3200/250工作日 = 12.8人次/天 │
  │ 设备日扫描能力：40-50人次/天            │
  │ 产能利用率：12.8/40 = 32%              │
  │                                      │
  │ 判定：🟠 产能利用率严重不足             │
  └─────────────────────────────────────┘

维度2：效益
  ┌─────────────────────────────────────┐
  │ 年检查收入：3200人次 × 均次收费350元    │
  │          = 112万元                    │
  │ 设备年折旧：2000万 ÷ 8年 = 250万/年    │
  │ 年维保费：50万                        │
  │ 年耗材/造影剂：30万                    │
  │ 年人工成本（技师+报告医师分摊）：40万    │
  │                                      │
  │ 年收入：112万                         │
  │ 年成本：250+50+30+40 = 370万          │
  │ 年亏损：112 - 370 = -258万            │
  │                                      │
  │ 判定：🔴 连年亏损，投资回报率为负        │
  └─────────────────────────────────────┘

维度3：质量
  ┌─────────────────────────────────────┐
  │ 平扫 vs 增强扫描比例：3500 vs 200     │
  │ 增强率：200/3700 = 5.4%               │
  │ 行业正常范围：15-30%                  │
  │                                      │
  │ 判定：🟠 增强扫描占比极低               │
  │ → 可能是技师不会做增强/患者不愿做        │
  │ → 这本身是"能力闲置"的另一种形式         │
  └─────────────────────────────────────┘

维度4：时效
  ┌─────────────────────────────────────┐
  │ 预约等候天数：0天（当天来当天做）        │
  │ 行业正常：1-2天                       │
  │                                      │
  │ 判定：即时满足 → 需求未饱和             │
  │ → 如果需求旺盛，预约等候会自然产生        │
  │ → 当天能做=没人在排队=设备在"等人用"      │
  └─────────────────────────────────────┘

═══════════════════════════════════════════
综合判定：
  这台2000万的CT，产能利用率32%，年亏损258万
  建议：启动闲置资产处置程序——
    ① 考虑调拨给有需求的院区
    ② 或与周边基层医院建立共享机制
    ③ 如果市场需求确实不足 → 当初就不该买
═══════════════════════════════════════════

### 2.3.2 设备全生命周期损失计算

```

┌───────────────┬──────────┬──────────┐

│ 安装调试费      │  50万    │  50万    │
│ 房屋改造        │  120万   │  120万   │
│ 操作人员培训    │  10万    │  10万    │
│ 年维保费        │  150万   │  50万    │
│ 年耗材          │  90万    │  30万    │
│ 年电费          │  30万    │  10万    │
│ 人力成本        │  120万   │  40万    │
│ 机会成本        │   —     │   —      │
├───────────────┼──────────┼──────────┤
│ 合计           │  1320万  │  550万   │
└───────────────┴──────────┴──────────┘

  → 其中已确认可量化的闲置期间损失550万

## 2.4 医疗设备典型问题的取证要求

### 2.4.1 场景一："设备买来没人会用"

**问题特征：** 设备有价、有人、有场地，但操作人员未接受完整培训或唯一会用的技师已离职

**证据链：**
```
证据1：操作人员培训记录（仅接受基础培训/培训记录缺失）
证据2：设备日志（购买前3个月有少量使用→之后断崖归零）
证据3：HIS计费记录（购买前后的检查量变化）
证据4：人事记录（唯一掌握操作技能的人员离职时间）
证据5：访谈记录（科室主任承认"现在没人会开"）
证据6：设备维保记录（设备本身完好——不是设备问题，是人的问题）

审计定性：管理责任——人才梯队建设缺位，单点依赖
损失认定：设备和配套的总成本 × 断崖后至今的时间占比
```

### 2.4.2 场景二："耗材绑架型闲置"

**问题特征：** 设备本身不贵，但配套耗材太贵，医院不愿承担亏损，医生不愿意开

**证据链：**
```
证据1：设备采购合同（设备价 vs 中标价，是否低价中标？）
证据2：耗材采购价 vs 收费定价（HIS收费单价 - 耗材成本 = 单项毛利）
证据3：检查量分析——是否因为亏损，医生被口头通知"少开"？
证据4：同地区同级医院的检查量对比
证据5：其他替代检查项目的增长（如用B超替代CT——因为B超便宜？）

审计定性：
  → 如果是耗材定价问题 → 建议与医保/物价部门沟通调整
  → 如果是采购时未做全生命周期成本测算 → 采购决策失误
  → 如果是供应商恶意捆绑（设备低价+耗材高价）→ 采购质量审计延伸
```

### 2.4.3 场景三："评审/达标采购后闲置"

**这是医疗设备中最隐蔽也最普遍的闲置类型**

**识别方法：**
```
步骤1：获取该医院过去5年的评审/创建记录
  → 三级医院评审
  → 重点专科评审（如"省级重点骨科"）
  → 胸痛中心/卒中中心/创伤中心认证
  → 教学医院评审

步骤2：标出每次评审/创建的时间窗口（通常为评审前1年）

步骤3：拉取医院设备采购清单 → 标记在评审窗口内的采购

步骤4：分析这些"评审窗口"采购的设备的使用率
  → 如果评审窗口采购的设备使用率显著低于其他设备 → 典型"达标采购"

步骤5：最确凿的证据——评审通过后，该设备使用率断崖式下降

示例：
  2023年6月：医院通过"省级重点骨科"评审
  2022年12月（评审前半年）：采购关节镜系统280万
  2023年1-6月（评审期间）：月均手术15台 → 使用率"看起来正常"
  2023年7-12月（评审后）：月均手术骤降至2台 → 🔴
  2024-2026年：月均手术1-3台 → 设备实质闲置已3年
```

### 3.1.2 构建"系统使用预期模型"

**以政务服务一体化平台为例：**

```
输入参数（公开数据）：
  - 该地区常住人口：50万人
  - 平台上线事项数：1200项
  - 同类地区平台月均办件量：3-5万件
  - 线上办理率目标（国办要求）：≥80%

预期模型：
  该平台月均办件量应在3-5万件区间（与同类地区对标）
  如果实际办件量 < 1万件/月 → 严重偏离预期 → 重点审计

注意：这个模型进场前就要建好
  → 进场当天拿到办件量数据后，5分钟内就能判定问题严重程度
  → 不需要等到分析阶段才"发现"问题
```

### 3.1.3 政务信息化审计抽样策略

```
第一层：金额筛选
  → 单项合同金额 ≥ 500万元 → 100%覆盖
  → 单项合同金额 100-500万元 → 50%抽样
  → 单项合同金额 < 100万元 → 10%抽样

第二层：风险加权
  → 甲方无专职技术团队的部门 → 权重×3（"建而不管"高发）
  → 项目验收后无运维合同/运维费 → 权重×3（"验收即终点"高发）
  → 供应商注册地在外省且无本地服务团队 → 权重×2
  → 上级统建、下级被动使用的系统 → 权重×2
  → 与已有系统功能存在重叠的新建系统 → 权重×3（"重复建设"高发）

第三层：使用表现（如果已有预采数据）
  → 公开渠道无法找到任何关于该系统的使用报道 → 权重×2
  → 政务APP最后更新时间 > 1年 → 权重×3 → 直接列入
```

## 3.2 现场数据采集阶段

### 3.2.1 "系统登记"——先把家底盘清楚

**政务信息化审计进场后第一件事不是看日志，是把"单位到底有多少个系统"搞明白——因为大量的闲置系统可能根本不在常规台账里。**

```
操作流程：
步骤1：要求提供《信息系统资产清单/台账》
  → 含系统名称、建设时间、建设金额、运维单位、运维金额、业务主管部门
  → 如果"没有这个清单"——本身就是第一个审计发现

步骤2：交叉比对
  → 将台账与以下来源一一比对：
    - 网络安全等保测评报告中的"信息系统清单"
    - 政务云管平台中的"已分配资源列表"
    - 财务系统中"软件/信息系统开发"类支出明细
    - IT运维团队掌握的"正在运维的系统清单"
  → 四个来源拼在一起，找出"系统中介"——台账上没有但其他来源有的系统
  
步骤3：补充登记
  → 对每个"新发现"的系统，补充登记其基本信息
  → 追问为什么台账上不体现
```

### 3.2.2 IAM日志采集——"一把钥匙开所有门"

**统一身份认证(IAM)日志是政务信息化审计最重要的单一数据源——因为它是所有系统的统一登录入口，几乎无法绕过。**

```
采集内容：
  时间范围：从系统验收日期至审计基准日（至少覆盖最近1年）
  必采字段：
    □ 用户ID（脱敏后取前4位+后4位）
    □ 用户类型（个人/法人/公务员/运维）
    □ 登录时间（精确到秒）
    □ 登录IP
    □ 登录方式（账号密码/扫码/短信/CA证书）
    □ 登录目标系统名称
    □ 登录结果（成功/失败/账号锁定）
    □ 会话时长（可选，如有）

IAM日志预处理：
  步骤1：排除运维/管理账号
    → 筛选：username包含 admin/root/system/test/devops/ops/管理/运维/测试
    → 筛选：IP段 = 内网运维段（如 10.x.x.x 或 172.16.x.x）
  
  步骤2：排除非工作时段异常登录（可选分析）
    → 凌晨0:00-6:00的登录 → 定时任务/数据同步
    → 周末的登录（政务系统很少有周末业务）
  
  步骤3：按系统聚合
    → 每个系统每天的独立用户登录数
    → 月活跃用户数（MAU）

输出结果示例：
┌─────────────────────┬──────────┬──────────┬──────────┐
│ 系统名称             │ 月活跃用户│ 月登录次数│ 判定      │
├─────────────────────┼──────────┼──────────┼──────────┤
│ 政务服务平台          │ 28,456   │ 156,230  │ 🟢 正常   │
│ OA协同办公           │ 1,892    │ 45,330   │ 🟢 正常   │
│ 数据共享交换平台      │ 12       │ 368      │ 🔴 闲置   │
│ 行政执法监管平台      │ 3        │ 15       │ 🔴 闲置   │
│ 智慧城管系统          │ 0        │ 0        │ 🔴 闲置   │
│ "XX阳光政务"APP     │ 8        │ 42       │ 🔴 闲置   │
└─────────────────────┴──────────┴──────────┴──────────┘
→ 12个注册用户、月15次登录的"行政执法监管平台"→ 重点核查
→ 0用户0登录的"智慧城管"→ 直接定性：事实闲置
```

### 3.2.3 各系统自身的功能级日志采集

**业界有一个关键区分：系统级日志 vs 功能级日志**

- **系统级日志**（Web服务器access log）→ 只能看出"有人访问了系统"→ 看不出"干没干活"
- **功能级日志**（业务操作日志/审计日志）→ 能看出"用户做了什么操作"→ 这是真正的"使用"

```
采集优先级：
  优先：应用自身的操作审计日志（如"行政审批系统→操作日志→事项受理/审批/办结"）
  次之：Web服务器access log（用于交叉验证）
  最后：数据库审计日志（用于极端情况——系统日志全无时）
```

**政务服务网功能级日志采集：**

| 功能模块 | 日志内容 | 对应的"使用"含义 |
|---------|---------|---------------|
| 事项受理 | 用户提交办事申请 | 系统真正在"被使用"的核心证据 |
| 材料预审 | 工作人员审核材料 | 后台人员在用系统 |
| 审批流转 | 审批→通过/退回/转办 | 系统在支撑业务流程 |
| 结果送达 | 电子证照/批文推送 | 系统产出了价值 |
| 好差评 | 用户评价 | 用户使用后的反馈 |
| 咨询投诉 | 在线咨询/投诉 | 系统在对外服务 |

**"假活跃"检测SOP：**

```
输入：系统Web服务器access log（Nginx/Apache格式）

步骤1：过滤非业务请求
  排除：
    → 静态资源（.css, .js, .png, .jpg, .ico, .woff）
    → 健康检查（/health, /ping, /status）
    → API文档（/swagger, /api-docs, /doc.html）
    → 错误页（状态码 4xx, 5xx）
    → favicon.ico
  保留：
    → 所有GET/POST请求到业务路径的

步骤2：分析请求间隔
  人的操作间隔 = 随机（几秒到几分钟）
  机器的操作间隔 = 固定（每30秒、每5分钟）
  
  处理逻辑：
    → 将同一IP的所有请求按时间排序
    → 计算相邻请求的时间间隔
    → 统计间隔分布
    → 如果90%以上的间隔在某个固定值±1秒内 → 脚本

步骤3：分析请求的User-Agent
  浏览器UA → 符合预期（Chrome/Edge/IE/手机浏览器）
  脚本UA → curl/python-requests/go-http → 排除
  
步骤4：分析操作深度
  单IP的请求路径：
    → 只有 /login + /index + /logout → 只登录浏览没办事
    → 包含 /apply + /submit + /query → 有实质性业务操作
    → 深度操作占比 < 10% → 假的活跃

步骤5：输出"真人活跃度"
  真人活跃度 = (总活跃IP - 脚本IP) / 总注册用户数
```

### 3.2.4 管理人员访谈提纲

| 访谈对象 | 核心问题 | 挖掘方向 |
|---------|---------|---------|
| 大数据局/信息中心负责人 | "单位现在在用的系统大概有多少个？哪些用得比较好？哪些用得不太好？" | 对比台账——他说的"不好"的系统就是重点 |
| 各业务部门负责人 | "你部门的XX系统，平时用得多吗？有没有遇到过什么问题？" | 业务部门的使用感受是第一手证据 |
| 一线窗口/操作人员 | "你现在办事用这个系统还是用老办法？每天大概在上面处理多少件？" | "用老办法"=系统是摆设 |
| 驻场运维工程师 | "你平时主要维护哪些系统？哪些系统报修最多？哪些系统几乎没人报修？" | "无人报修"=无人使用/无人关心 |

## 3.3 数据分析阶段

### 3.3.1 办件量——政务系统最核心的使用率指标

**计算公式与基准参考：**

| 指标 | 计算公式 | 数据来源 | 正常参考值 |
|------|---------|---------|----------|
| 事项上线率 | 已上线事项数 ÷ 政务服务事项目录总数 | 平台后台+政务服务网 | ≥95% |
| 网上办理率 | 网办件数 ÷ (网办件数+线下办件数) | 平台后台+线下窗口统计 | ≥80% |
| 事项活跃率 | 有办件的事项数 ÷ 已上线事项数 | 平台后台（按月）| ≥60% |
| 人均办件量 | 月均办件量 ÷ 辖区常住人口 | 平台后台+统计局 | ≥同地区中位数 |
| 事项办件集中度 | Top 10事项办件量 ÷ 总办件量 | 平台后台 | 30-50%（太集中说明大部分事项没用）|

**政务系统最典型的异常模式——"金字塔式分布"：**

```
事项办件量分布：
  Top 10事项：占总办件的85% ████████████████████
  第11-50事项：占总办件的14% ███
  第51-1200事项：占总办件的1% ▏
  → 1200个事项里，1149个几乎没人用
  → 这些事项对应的开发成本，大部分是浪费
  → 要问：为什么上这么多没人用的事项？
    → "上级要求必须上线" → 这就是"指建不用"的典型模式
```

### 3.3.2 系统间重复度分析

```
步骤1：功能清单比对
  → 提取每个系统的功能模块清单
  → 用关键词匹配找出相同/相似功能
  
  示例：
  系统A（行政审批系统）：材料受理、在线审批、电子签章、结果送达、进度查询
  系统B（电子监察系统）：办件受理、流程监控、超时预警、在线审批、统计分析
  系统C（"一窗受理"平台）：材料受理、窗口叫号、在线审批、统一出件

  重叠矩阵：
              A审批系统  B监察系统  C一窗受理
  材料受理     ✅         ✅         ✅      ← 三个系统都做了受理
  在线审批     ✅         ✅         ✅      ← 三个系统都做了审批
  结果/出件    ✅                    ✅
  流程监控               ✅
  超时预警               ✅

  → "材料受理"功能重复开发了3次
  → "在线审批"功能重复开发了3次

步骤2：使用率对比——重叠功能中哪个系统在真正被用
  材料受理功能：
    系统A（行政审批）：月均1200件
    系统B（电子监察）：月均0件（监察系统不需要做受理，规划时就设错了功能）
    系统C（一窗受理）：月均3500件（这才是真正在用的）
  
  → 系统B的"材料受理"功能 = 纯浪费
  → 系统A部分被替代 = 部分浪费
  
步骤3：重复建设损失估算
  系统B合同金额500万，"材料受理"占功能模块的15%（按功能点估）
  重复浪费金额 = 500 × 15% = 75万
```

### 3.3.3 时间序列分析——找到"验收后断崖"

```
分析维度：
  月均办件量趋势（以系统验收月为原点M0）
  
  示例1：正常系统
  M0-M3（上线初期）：100 → 300 → 500 → 700 → 稳定增长
  M4+：维持在 800-1000 → 🟢 持续使用
  
  示例2：验收后断崖
  M0-M3（测试/试运行）：50 → 80 → 100
  M4-M6（验收通过）：120 → 30 → 5 → 🔴开始下降
  M7-M12：3, 2, 0, 1, 2, 0 → 🔴 闲置
  M13+：0, 0, 0, 0 → 🔴 完全闲置
  
  示例3："做给审计看"
  M0-M12：0, 0, 0, ..., 0 → 闲置一整年
  M13（审计入场前1个月）：突然变成 500 → 🔍
  → 用融策时间序列异常检测工具直接标记异常跳变点

关键判定：
  → 断崖发生在验收后6个月内 → 系统从未真正"用起来"
  → 断崖发生在验收后1-3年 → 系统曾被使用但因某种原因停止
  → 无论哪种 — 验收后连续>12个月月均低于正常的20% = 闲置
```

### 3.3.4 云资源利用率分析

**政务云浪费是比系统闲置更隐蔽的浪费——因为云资源一直在"计费"，但从来没人管到底用了多少。**

```
分析维度：
  
维度1：CPU使用率分布
  导出政务云上所有虚拟机的CPU月均使用率
  分级统计：
    CPU < 5%：XX台（占比XX%）→ 🔴 超配严重
    CPU 5-10%：XX台 → 🟠 闲置嫌疑
    CPU 10-30%：XX台 → 🟡 偏保守
    CPU 30-70%：XX台 → 🟢 合理
    CPU > 70%：XX台 → 需扩容

维度2：零流量资源
  → 网络流量连续30天 = 0的虚拟机
  → 已分配但没有任何网络通信 → 根本没有系统在运行
  → 直接判定：闲置资源

维度3：超长不活跃
  → 连续90天CPU均值 < 1%，内存使用 < 5%
  → 这些虚拟机要么是"僵尸"（建立后就没用过）
  → 要么是"备机"（但政务云应该靠弹性伸缩，不需要备机）

损失计算：
  月均云服务费中，低负载（CPU<10%）资源的占比
  → 示例：月云费50万，其中低负载资源占比60%
  → 年浪费 = 50万 × 60% × 12 = 360万/年
```

## 3.4 政务信息化典型问题的取证要求

### 3.4.1 场景一："系统建成后从未使用"

**这是最严重的情况——等同于财政资金完全损失**

**证据链标准：**
```
证据1：系统验收报告（确认系统已通过验收，已付款）
证据2：IAM统一认证日志（验收后至今：零真实用户登录或仅有运维/测试账号）
证据3：系统自身办件量/业务量统计（零或极微量）
证据4：业务部门访谈记录（业务人员确认"没有用过/不知道有这个系统"）
证据5：驻场运维人员访谈记录（运维人员确认"系统在运行但无人使用"）
证据6：政务云资源使用率（CPU/内存长期处于基线水平——系统在空转）
证据7：如果系统有对应的线下业务流程 → 证明线下业务确实存在 → 排除"业务需求不存在"

证据效力排序：
  证据2+证据3（硬数据，最可靠）
  > 证据4+证据5（访谈，需多方交叉印证）
  > 证据1（基础事实确认）
  > 证据6（辅助证据）
  > 证据7（排除"需求不存在"的抗辩）

损失认定：
  → 项目建设金额 100% → 全额认定为"未发挥效益"
  → 如果已产生运维费 → 运维费也全额认定
```

### 3.4.2 场景二："部分功能从未启用"

**这正是审计署公告中"部分功能从未启用"的标准场景**

**证据链标准：**
```
证据1：合同约定的功能模块清单（含每个模块的开发费用/人天）
证据2：系统后台的功能模块使用统计（按模块统计调用次数）
证据3：显示"调用次数=0"的功能模块列表
证据4：未启用模块的开发费用占比计算
  
  未启用功能费用占比 = Σ未启用模块的开发费用 ÷ 合同总金额
  
示例：
  系统功能模块16个，有4个从未启用
  这4个模块的开发工作量占合同总工作量的30%
  合同金额500万 × 30% = 150万
  → 认定"150万元的系统功能未发挥效益"
```

### 3.4.3 场景三："系统在用但无业务产出"

**这是最隐蔽的——系统在运行、有人在登录、但不产生实际的政务服务价值**

**识别方法：**
```
信号1：办件量 ÷ 登录人次 < 5%
  → 大量登录但极少办事 → 浏览型使用

信号2：申报提交量 ÷ 登录人次 < 10%
  → 一直在浏览、查询，但不提交 → 业务链路断裂
  → 常见原因：系统太难用、材料要求不合理、流程设计有缺陷

信号3：线上收件量 ÷ 总收件量 < 20%
  → 群众选择线下办理而不用线上
  → 常见原因：线上流程比线下还麻烦

信号4：好差评数据
  → 差评中高频出现"流程复杂""上传失败""打不开"→ 系统质量问题

审计定性：
  这类不是"闲置"，是"系统不好用导致使用者流失"
  建议方向：系统优化 → 而不是简单建议"加强使用"
```

## 3.5 政务信息化审计报告措辞参考

基于2026年审计署公告口径，可直接使用的表述：

```
【系统闲置】
"XX系统自XXXX年XX月验收以来，月均真实用户登录数不足X次，
月均办件量不足X件。实际未发挥信息系统应有的服务效能。
该项目合同金额XXX万元，财政资金面临损失浪费风险。"

【重复建设】
"XX系统与已建成的YY系统在XX项核心功能上存在重叠，
XX系统对应功能的月均使用率为0。重复建设涉及的财政资金为XXX万元。"

【云资源低效利用】
"抽查发现，XX单位在政务云上共有XX台虚拟机，
其中XX台CPU月均利用率低于5%，XX台连续XX个月网络流量为零。
按当前配置测算，年产生低效云服务费约XX万元。"

【验收后闲置】
"XX系统于XXXX年XX月验收，验收后第X个月起使用人次断崖式下降。
截至审计日，该系统已连续XX个月处于实质闲置状态。"

【功能覆盖率不足】
"系统功能模块共计XX个，实际启用XX个，XX个模块从未被调用。
未启用模块的合同金额约为XX万元。"
```
