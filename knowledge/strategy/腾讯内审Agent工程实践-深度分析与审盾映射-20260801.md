## 一、文章技术内核拆解

### 1.1 核心命题：把"临场发挥"变成"工程可复现"

文章开篇点出审计场景对 Agent 的根本要求：**稳定、高效、可追溯**。通用 Agent 面对复杂任务的问题：

| 问题 | 表现 | 后果 |
|:--|:--|:--|
| 路径不可复现 | 每次思考路径/停止条件不同，一次成功≠下次成功 | 过程控制失效 |
| 覆盖不可控 | 只选部分渠道、拿少量结果就停 | 查不全→结论失真 |
| 成本不可控 | 反复读全文、重复调用 | 时间/Token 双浪费 |
| 来源不可信 | 检索空白时用模型知识补写 | 无源信息进入结论 |

**对策：Agent Harness（外骨骼，非马具）**——不是写死 Agent 每一步，而是按工作性质分工：
- **模型/Agent**：语义理解、模糊判断、动态调整
- **工程链路**：批量、重复、规则明确的处理（稳定、可记录、可复用）
- **审计师**：核查目标、必查范围、业务口径、歧义确认、最终结论

### 1.2 三大场景的工程控制点

#### 场景A：深度检索（查全查实）
四个控制环节：
1. **生成查询** — 笼统问题拆成多个查证角度
2. **控制来源与访问** — 信源白名单 + 只允许受控工具（MCP/API），禁止临时爬虫；必查信源设覆盖检查
3. **迭代检索** — 每轮查信息缺口+新线索，动态决定下一轮查什么（检索范围不是一次性固定）
4. **控制收敛与证据** — 停止条件+轮次上限；至少一次真实检索；关键结论绑定来源编号；有缺口如实说明，禁止模型知识补白

**关键细节**：粗略搜索只用于发现候选，进入结论的关键信息必须全文读取+绑定来源编号，方便审计师回原文核对。

#### 场景B：智能分类（先看全貌再归类）
解决：数万行报销事由/付款说明/合同条款的分类。
三步法：
1. **预打标** — 工程链路先归组相似记录→抽代表性样本→批量生成候选维度/标签→标准化去重（减噪声、省Token）
2. **构建分类体系** — Agent 据样本+标签形成体系，用覆盖率/集中度指标提出增删合并建议；**审计师确认分类维度、类别定义、适用边界**
3. **全量分类** — 链路按确认体系批量分类；低置信/未归类/冲突记录交 Agent 复判；同类问题集中→回退调整体系

**关键细节**：分类体系允许"先粗后细"（开始无法一次定义完整，随理解调整）；结合金额/频次补充重要性视角；标准类别编号保证输出一致。

#### 场景C：智能问数（先理解数据，再持续分析）
痛点：数据理解偏差→后续分析全错；通用 Agent 的数据理解靠用户维护/交互提供/临场探索，均不可靠。
解法：**结构化数据理解底座 + 配套链路**
- 固定链路：结构扫描→数据画像→语义识别→口径校验→结果沉淀（确定性事实走工程链路，语义判断调模型）
- 分层加载：**核心理解**（表粒度/业务对象/字段角色/表间关系/已确认口径）自动注入每次分析；**详细证据**（字段画像/值分布/样本/质量细节/历史修正）按需查询
- 回写闭环：分析中确认的新关系/新口径/修正信息回写底座，优先于机器推断；结构没变就直接复用，变了才重进对应环节
- 边界原则：**无法确认不贸然出数**——口径不清/缺字段/查询失败时明确说明缺什么，必要时请审计师确认

### 1.3 贯穿三场景的共同设计原则（这是最值得提炼的）

1. **分工原则**：确定性→工程链路；语义性→模型；业务性→审计师
2. **控制点前置**：把质量风险消灭在流程设计里，而不是事后检查（信源白名单、口径确认都在执行前）
3. **人机接口标准化**：审计师只在"歧义口径+关键判断"两处介入，介入有明确触发条件
4. **成本工程化**：归组抽样减重复调用、分层加载防上下文爆炸、理解复用免重复探索
5. **诚实边界**：不编答案、不强行出数、缺口如实说明——这是审计可信度的底线

## 二、与审盾 v2.0 的深度对标

### 2.1 高度共振的部分（审盾已设计，腾讯已实战验证）

| 审盾 v2.0 设计 | 腾讯实践 | 结论 |
|:--|:--|:--|
| Skill 7 结论确认：金额显示计算过程、法规引用条款、附依据来源 | 关键结论绑定来源编号、证据回溯 | ✅ 方向一致，腾讯验证可行 |
| Skill 3 疑点穿透：不完成根因分析不得定性 | 无法确认不贸然出数、缺口如实说明 | ✅ 同频，都是"证据先于结论" |
| Skill 5 复核三关：三级复核 | 审计师确认歧义事项+关键判断+最终结论 | ✅ 人机确认机制一致 |
| HARD-GATE 硬门槛机制 | 停止条件+轮次上限+覆盖检查 | ✅ 同为"流程内嵌控制"思路 |
| 五层穿透思考框架 | 迭代检索的缺口+线索驱动 | ⚠️ 审盾更偏"根因深度"，腾讯更偏"检索广度"，可互补 |

### 2.2 审盾的差距（腾讯有、审盾没有——这是本次分析最大价值）

**差距1：数据理解底座（审盾最该补的模块）**

审盾目前的数据处理是"项目级一次性"的：每个项目重新理解数据、重新定口径。腾讯的底座实现了：
- 数据理解**资产化**（可复用档案）
- 口径**持续校正**（回写闭环）
- **分层加载**控制 Token（核心理解注入+详细证据按需）

→ 对融策的直接价值：**绩效评价复核里"口径不一致"是高频 P0 问题**（报告里的产出指标口径、资金统计口径经常前后打架）。一个跨项目复用的"数据理解档案"（比如"项目评审金额"在不同项目里怎么算、哪个口径被业主确认过）能让复核器越用越准。这正是审盾一期"AI复核≥审计经理平均水平"目标的关键杠杆——**审计经理强就强在对口径的长期记忆，AI 要有这个记忆就得靠底座**。

**差距2：信源白名单 + 受控访问**

腾讯只允许通过已接入、已授权、符合访问规范的 MCP/API 取数，禁止临时爬虫。审盾的 RAG 和法规库目前是"本地索引"模式，还没有"受控外部信源"层。对审计场景：
- 法规检索、企业工商信息（天眼查）、招投标公告 → 应做成白名单受控接口
- 好处：来源可审计、留痕统一、防 Agent 幻觉编造来源

**差距3：预打标→体系→全量分类的三步法**

审盾 22 Agent 里没有专门的"数据分类"流程标准化。报销事由/合同条款/付款说明的分类在政府审计（专项资金、补贴审计）里是高频场景，三步法（归组抽样→人确认体系→全量分类+复判回退）可以直接沉淀为审盾的一个 Skill。

### 2.3 腾讯的局限（审盾可以做得更好的地方）

1. **大甲方视角 vs 乙方视角**：腾讯内审面对的是自家数据（系统全、权限足、可持续建设）。融策是乙方：数据来源杂（Excel、扫描件、PDF、手工台账）、项目周期短（没有 6 个月建底座的时间）、交付物要能带走。**底座建设必须轻量**：一次项目沉淀一份档案（JSON/Markdown），跨项目复用靠知识库索引，不依赖常驻系统。
2. **文章没讲多 Agent 协同**：腾讯是"单 Agent + 工程链路"模式；审盾已有 22 Agent + H-packet 交接 + 疑点融合中枢。**融合方向**：每个 Agent 的 H-packet 里增加"数据理解档案引用"字段，交接时把口径一起交，避免每个 Agent 重新理解数据。
3. **文章没讲成本量化**：没给 Token 数字。审盾有 token 预算体系（¥100/天熔断），落地时要把腾讯的"归组抽样""分层加载"翻译成明确的 Token 节省目标。

### 2.4 战略层面启示

1. **Harness 工程 = 审盾可产品化的护城河**："外骨骼"叙事比"AI 自动审计"更符合审计伦理（人负责、AI 辅助），对外投标/汇报时这个框架既能讲清价值又不踩"AI 替代审计师"的红线
2. **腾讯内审亲自背书**：腾讯内审公众号发文 = 大厂内审体系公开认可 Agent 工程化，可用于说服业主/省注协"这是行业方向"
3. **审盾叙事升级**：从"22 Agent"（谁干活）→"外骨骼体系"（怎么干得稳），与审盾 v2.0 Superpowers 融合方案的"工程纪律层"一脉相承，可合并为"审盾 = 审计师的外骨骼"统一叙事

## 三、落地行动建议（对齐审盾实施路线）

### P0 — 立即做（本周，嵌入绩效复核试点）

1. **设计《数据理解档案模板 v0.1》**：字段 = 数据源/表结构/业务对象/字段角色/口径定义/确认人/确认日期/变更记录。试点项目每个数据集填一份，存 `audit-blackboard/projects/<项目>/data_profiles/`
2. **复核器增加"口径一致性检查"**：复核时自动加载该项目已有档案，报告中的统计口径与档案比对，不一致即 P1 告警（这是审盾一期最容易见效、最能对标"审计经理平均水平"的功能）

### P1 — 一个月内（沉淀为审盾 Skill 9/10）

3. **Skill 9：智能分类三步法**——先用在招投标审计（投标文件分类）或补贴审计（补贴申请事由分类）试点
4. **Skill 10：数据理解底座**——结构扫描/画像/口径校验脚本化（可基于现有 `data-analyst-cn`、SQL 工具链封装）

### P2 — 三个月内（能力扩展）

5. **信源白名单层**：天眼查/企查查、法规库、招投标公告做成受控接口（对接串标检测 L8 工商关联），来源编号自动绑定进底稿
6. **深度检索模块**：把现有 RAG 查询升级为"查询拆分→迭代→证据绑定"流程（可先用 `scripts/rag_query.py` 改造）
7. **底座回写闭环**：项目结项时把新确认口径自动回写知识库，跨项目复用

### 成本控制红线

- 预打标/归组抽样必须走工程链路（本地去重/聚类），模型只处理样本——预计省 60-80% Token
- 分层加载：核心理解 ≤2K token 注入，详细证据按需查询
- 底座复用：同结构数据直接复用档案，禁止每次重新探索

## 四、风险与边界

| 风险 | 说明 | 对策 |
|:--|:--|:--|
| 乙方数据可得性差 | 腾讯自建系统 vs 融策拿到的是杂数据 | 档案模板轻量化，一次项目一次沉淀，不强求常驻底座 |
| 口径档案错误传导 | 档案里记错的口径被后续项目复用=错误放大 | 档案必须含"确认人+确认日期"，AI 推断口径标注"待确认"，优先级低于人工确认 |
| 过度工程化 | 小项目也走完整底座流程=成本倒挂 | 设触发阈值：数据量<1000行或项目<5天不走底座，直接人工口径 |
| 审计责任边界 | AI 参与分析不改变审计师签字责任 | 对外叙事坚持"外骨骼"定位，人确认关键判断；投标文件明确"AI 辅助、审计师负责" |
| Token 成本 | 深度检索迭代会放大调用量 | 轮次上限（如≤5轮）+ 每轮结果去重 + 停止条件显式化 |

## 五、结论

**一句话**：这篇文章把审盾 v2.0 的设计从"纸面正确"推进到"已被大厂实战验证"，并暴露了审盾最大的结构性缺口——**数据理解底座**。

**三件事最重要**：
1. 补"数据理解档案"模块（审盾 9/10 Skill），直接服务于绩效复核的口径一致性——这是审盾一期通过验收的最短路径
2. 采纳"信源白名单+证据绑定"（对接串标 L8 工商检测）
3. 对外叙事升级为"审计师的外骨骼"，拿腾讯内审文章做行业背书

**审盾 vs 腾讯的本质差异要守住**：腾讯做的是"自家数据的深加工"，融策做的是"甲方数据的快诊"——底座要轻、复用要快、成本要狠。学 Harness 的骨架，不学大厂的重装备。
