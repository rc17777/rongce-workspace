# 审盾·数据理解底座 — 离线异构数据适配器设计

> 编制时间：2026-08-04
> 依据：公众号「审计实践」文章四步构建中「数据入湖」环节，以及融策作为乙方事务所的离线异构数据环境
> 用途：审盾路线图阶段1 H1任务「数据理解底座v1.0」的补充设计

---

## 一、核心矛盾

文章描述的"数据入湖"前提是：

> "将财务、采购、销售、HR、OA、资金、税务等核心系统数据汇聚到数据中台"

这是**央企甲方视角**——所有系统都在自己手里，API一对接就行。

融策作为**乙方会计师事务所**，面对的现实是：

- 被审计单位提供的可能是任何格式
- 数据质量参差不齐（缺失、乱码、口径不一致）
- 同一个被审计单位，不同年度提供的数据格式可能完全不一样
- 不能假设数据库直连——绝大多数是离线文件交付

**审盾的数据理解底座，必须在更恶劣的环境下工作。**

## 二、六种数据入口归一化

### 入口矩阵

| 入口类型 | 典型场景 | 频次 | 难度 | 审盾处理链 |
|:--|:--|:--:|:--:|:--|
| **CSV/TSV** | 财务软件导出的科目余额表、序时账 | 极高 | ★ | 编码检测→列类型推断→空值处理→结构化 |
| **Excel (.xlsx/.xls)** | 被审计单位手工维护台账、统计局报表 | 极高 | ★★ | 多Sheet识别→多行表头处理→合并单元格展开→公式→结构化 |
| **PDF扫描件** | 发票、合同、银行回单、会议纪要 | 高 | ★★★★ | OCR→版面分析→表格抽取→结构化 |
| **PDF电子件** | 从系统直接导出的可编辑PDF | 中 | ★★★ | 文本层提取→表格定位→结构化 |
| **数据库导出 (.sql/.dmp/.mdb)** | 被审计单位IT配合导出 | 低 | ★★ | 建表语句解析→数据行提取→结构化 |
| **API接口** | 被审计单位有对外开放的数据接口（极少） | 极低 | ★ | 字段映射→分页拉取→结构化 |

### 归一化目标

所有六种入口，最终输出统一的**审盾数据帧格式（SDF, Shendun Data Frame）**：

```json
{
  "source": {
    "type": "excel|csv|pdf_scanned|pdf_electronic|sql_dump|api",
    "original_file": "2025年序时账.xlsx",
    "ingestion_time": "2026-08-04T16:00:00+08:00",
    "checksum": "sha256:abc123..."
  },
  "profile": {
    "row_count": 15230,
    "col_count": 18,
    "encoding": "utf-8",
    "null_rate": 0.023,
    "duplicate_rows": 47
  },
  "schema": {
    "columns": [
      {"name": "凭证号", "type": "string", "nullable": false, "unique_rate": 1.0, "sample": ["记-0001", "记-0002"]},
      {"name": "科目代码", "type": "string", "nullable": false, "unique_rate": 0.12, "sample": ["1001", "1002"]},
      {"name": "借方金额", "type": "decimal", "nullable": true, "unique_rate": 0.45, "sample": [15000.00, 2300.50], "stats": {"min": 0.01, "max": 5000000.00, "mean": 12500.00, "std": 58000.00}}
    ]
  },
  "semantic_tags": {
    "financial": ["借方金额", "贷方金额", "科目代码", "科目名称"],
    "date": ["凭证日期", "记账日期"],
    "entity": ["供应商名称", "客户名称"],
    "id": ["凭证号", "凭证编号"]
  },
  "data": [
    {"凭证号": "记-0001", "科目代码": "1001", "借方金额": 15000.00, "凭证日期": "2025-01-05", "供应商名称": "四川XX公司"},
    ...
  ]
}
```

## 三、适配器流水线架构

```
┌──────────────┐
│  原始文件      │  (CSV/Excel/PDF/.sql/API)
└──────┬───────┘
       ▼
┌──────────────┐
│ 入口路由器     │  识别文件类型 → 分派到对应适配器
└──────┬───────┘
       │
       ├──→ CSV适配器  ──→ 编码检测 → 分隔符识别 → 列类型推断
       ├──→ Excel适配器 ──→ Sheet遍历 → 表头定位 → 合并单元格展开
       ├──→ PDF扫描适配器 ──→ OCR(PaddleOCR) → 版面分析 → 表格抽取
       ├──→ PDF电子适配器 ──→ 文本层提取 → 表格定位
       ├──→ SQL适配器 ──→ 建表语句解析 → 数据行提取
       └──→ API适配器 ──→ 字段映射 → 分页拉取
       │
       ▼
┌──────────────┐
│ 统一清洗层    │  去重 → 空值标记 → 类型强制转换 → 编码归一
└──────┬───────┘
       ▼
┌──────────────┐
│ 语义标注层    │  列名→语义标签映射（规则+AI辅助）
│              │  识别：金额/日期/实体/ID/代码/比率/文本
└──────┬───────┘
       ▼
┌──────────────┐
│ 口径校验层    │  借贷平衡校验 → 日期连续性 → 勾稽关系核验
│              │  → 与历史数据口径一致性对比
└──────┬───────┘
       ▼
┌──────────────┐
│ SDF输出      │  → 进入数据理解底座（profile + schema + tags）
│              │  → 注册到项目黑板
│              │  → 供Agent按需查询
└──────────────┘
```

## 四、关键设计决策

### 4.1 不做实时，做批次

融策场景不需要流式处理。数据以"项目批次"为单位接入，一个项目的所有文件批量入湖后开始分析。

### 4.2 关键适配：多行表头（中国式报表）

这是最高频的坑——被审计单位的Excel表头经常是：
```
|    2025年度收入情况    |
| 预算数 | 实际数 | 差异 |
| 金额 | 金额 | 金额 |
```

适配器必须支持：
- 自动检测表头行数（1-4行）
- 表头层级合并为单层列名
- 人工可确认/修正表头识别结果

### 4.3 OCR 质量分层

PDF扫描件的OCR结果不可靠，需要质量分层：
- **高质量（≥95%）**：自动入库
- **中等质量（85%-95%）**：自动入库 + 标记"建议人工抽检"
- **低质量（<85%）**：暂停入库，推送给审计师确认

### 4.4 增量更新

同一个项目可能有多次数据交付。适配器需支持：
- 追加模式：新增行
- 替换模式：整个文件重新处理
- 差异报告：自动对比新旧版本差异

## 五、与审盾现有组件的集成

| 审盾组件 | 集成方式 |
|:--|:--|
| `profile_builder.py` (v0.1) | 替代其文件读取层，统一输出SDF |
| `caliber_checker.py` | SDF的schema/semantic_tags字段直接喂入 |
| `orchestrate_v3.py` | 项目新建时自动触发适配器 → SDF写入项目黑板 |
| `handover_protocol.py` (H-packet) | SDF的source/schema作为H-packet的"数据基础"字段 |
| `issue_fusion.py` | 所有问题发现必须引用SDF中的source.file + row_index |
