# 审盾知识架构设计（一页纸）

> 以下框架基于 RAG+KG 根因分析协同方法论，翻译为审计业务语言。
> 来源：星数智联《RAG 与知识图谱在根因分析中的协同》(2026-05-29)

---

## 一、核心洞察：审计 = 根因分析

审计问题定性、归因、追溯，和工业 RCA 是同构问题：

| 根因分析概念 | 审计对应 |
|:--|:--|
| 根因分析（RCA） | 审计发现的原因追溯与定性 |
| 运行态实体 | 被审计单位、项目、资金、合同、供应商、责任人 |
| 知识态实体 | 问题类型、定性依据、法规条款、整改建议、评分标准 |
| 多跳推理 | 资金→项目→合同→供应商→责任人的穿透链条 |
| 确认边 vs 推断边 | AI 推断的关联必须人工确认 |

**结论：审盾的四库（前沿技术/政策法规/项目经验/问题整改）天然对应两套实体体系。**

---

## 二、实体分类设计

### 运行态实体（Operational）——"谁/什么东西出了问题"

| 实体类型 | 示例 | 审计业务场景 |
|:--|:--|:--|
| 被审计单位 | XX 县财政局 / XX 学校 | 项目主体、预算单位 |
| 项目 | 2024 年营养餐改善计划 | 绩效评价对象 |
| 资金 | 中央财政专项资金 | 资金流向追踪 |
| 合同/供应商 | 中标施工企业 | 串标检测、合同履约 |
| 责任人 | 时任局长、项目负责人 | 经责审计定责 |
| 整改事项 | 重复发放补贴 | 整改跟踪闭环 |

> 说明：运行态实体构成问题追溯的"舞台"，但不包含诊断知识本身。

### 知识态实体（Knowledge）——"出了什么问题、为什么、怎么定、怎么改"

| 实体类型 | 示例 | 审计业务场景 |
|:--|:--|:--|
| 问题类型 | 超标准列支 / 违规发放 / 串标 | 发现定性分类 |
| 定性依据 | 财政部令第 XX 号 第 X 条 | 法规匹配 |
| 违规标准 | 未按规定程序招标 | 问题严重程度判断 |
| 整改建议 | 追回资金 / 完善制度 | 审计建议一致性 |
| 绩效指标 | 产出指标 / 效益指标 / 满意度指标 | 绩效评价打分 |
| 整改路径 | 7 日内退回 / 30 日内修订制度 | 整改跟踪 |

> 说明：知识态实体是"引擎"，运行态实体是"机架"。
> 只有引擎没有机架 → 推理无法落到具体项目；只有机架没有引擎 → 缺乏诊断能力。

## 三、两套实体之间的关联关系

```
运行态实体 ←→ 知识态实体

[被审计单位] ──〔被发现有〕──→ [问题类型]
[项目]        ──〔引用了〕──→ [定性依据]
[资金]        ──〔涉及〕──→ [违规标准]
[供应商]      ──〔存在问题〕──→ [问题类型]
[责任人]      ──〔应承担〕──→ [整改建议]
[整改事项]    ──〔依据〕──→ [整改路径]
```

## 四、确认边 vs 推断边（核心质控机制）

这是整个框架里最关键的设计——直接对应审盾的人工确认红线。

### 边类型定义

| 类型 | 来源 | 置信度 | 使用规则 |
|:--|:--|:--|:--|
| **确认边** | 人工校验 / 权威数据源（法规原文、入库底稿） | 1.0 | 优先遍历，可在报告中直接引用 |
| **推断边** | LLM 抽取 / RAG 自动补全 | 0.5（默认） | 仅在无确认边可达时使用，报告必须标注"基于推断" |

### 升级规则

- 同一条推断边被 **2 个以上独立来源**（不同文档、不同时间段、不同项目）交叉验证 → 自动升级为确认边，置信度提升至 0.9
- 升级操作需人工确认后正式写入知识库

### 审计报告中的展示

```
候选问题 1：超标准列支（置信度：高，路径：2 跳）
  推理路径：XX项目 →〔资金构成〕→ 培训费占比 42% →〔违反〕→ 财政部令第 XX 号（确认边）

候选问题 2：利益输送（置信度：中，路径：3 跳）
  推理路径：供应商 A →〔疑似关联〕→ 单位负责人 →〔推断边，来源：合同审查 + 企业查询交叉验证〕
```

## 五、演进路径（审盾 1.0 → 2.0 → 3.0）

### 一审盾一期：RAG-first 复核器
- 不做图谱，不做实体抽取
- 向量检索 + 复核规则引擎 + 人工确认
- 高频复核场景跑通，积累实体样本

### 二审盾二期：KG-enhanced RAG
- 从高频出现实体抽知识态实体（问题类型、定性依据、整改建议）
- 用实体关系扩展检索 Query，提升召回精准度
- 推断边人工确认机制上线

### 三审盾三期：GraphRAG / 微调
- 社区摘要回答全局问题（"这类项目最常见的问题是什么"）
- 微调管"审计报告语感"，RAG 管"定性依据内容"
- 确认边池积累到一定量后可支持自动发现

---

## 六、对审盾一期的约束

1. **一期不对知识图谱做任何承诺**——只做 RAG 向量检索 + 规则引擎
2. 但一期项目经验库的结构需预留实体标签字段，为二期图谱建设铺路
3. 一期复核输出模板中就已包含"来源标注"（AI 意见必须指明引用来源），这是二期确认边/推断边机制的雏形
4. 一期不是不做图谱就完全不管实体——建议在项目经验入库时手工标注"运行态实体"和"知识态实体"两类标签，积累足够样本后二期直接抽图
