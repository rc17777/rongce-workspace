## 一、RAG + LLM Wiki 混合架构

### ⚠️ 需关注 — 概念重叠严重，分工模糊

**问题分析：**

1. **"LLM Wiki 预编译"与 RAG 检索本质上是同一种能力的两种呈现形式。** 设计文档说"将高频稳定的法规条款、常见问题类型、标准整改建议预编译为结构化 Markdown 页面"，但这本质上就是一个**静态知识缓存层**——不是 Wiki，更不是"LLM Wiki"。它不需要 LLM 来持续生成内容，甚至不需要 QMD 搜索引擎。用一个简单的全文索引（甚至内存 Map）就够用了。

2. **"查询时优先读取预编译 Wiki，而非实时向量检索"——这句话暴露了核心设计缺陷。** 任何检索系统都不应该让用户去操心"应该搜哪个库"。正确做法是混合检索后统一排序，而不是把路由决策推给用户或前置逻辑层。当前设计把"高频稳定知识"和"低频动态知识"人为拆成两条管道，结果就是：查询问到了一句话，一半答案在 Wiki 里，一半在 RAG 里，谁来拼？拼得好吗？

3. **QMD 搜索引擎的引入值得商榷。** QMD（BM25 + 向量混合搜索 + LLM 重排）本质上和 RAG 流水线（向量检索 + 计划中的 Reranker）高度重叠。引入两套独立的检索引擎（一套向量库 + 一套 QMD）是维护地狱。除非 QMD 在处理预编译 Wiki 时能提供显著不同的价值（比如双向链接遍历），否则这是**过度工程化**。

**改进建议：**
- 把"预编译 Wiki"降级为"知识缓存层"，本质是提前执行 RAG 检索并将 Top-3 结果固化，供高频查询直接命中，命中不到了回退到实时 RAG。不要建独立的检索系统。
- 统一为一个检索 API，内部按置信度和时效性自动决定走缓存还是走实时检索，外部无感。
- QMD 如果确实需要（为双向链接遍历），应明确其不可替代性，而非作为"另一个搜索引擎"引入。

**评级：⚠️ 需关注**

## 二、LLM Wiki 预编译是否真有价值

### ⚠️ 需关注 — 价值的财务账算不过来

**问题分析：**

1. **审计法规的"高频稳定"是一个伪命题。** 审计场景中使用最频繁的法规条款，恰恰也是更新最频繁的——预算法、政府采购法、招投标法每年都有修订/解释/补充文件。预编译后的维护成本（检测法规更新 → 失效旧 Wiki → 重新生成 → 验证一致性）不会比实时 RAG 低。你最终得到的是一个需要持续维护的静态副本，和一个自动更新的动态源——这个模式最典型的结局就是静态副本逐渐过期，没人维护。

2. **标准整改建议预编译的价值存疑。** "常见问题类型 → 标准整改建议"这种映射如果是静态的，那就是查表，不需要 LLM 预编译。如果每次需要 LLM 根据上下文生成，那就等于还是走实时推理，拆出来也没省下计算量。

3. **真正有价值的预编译是"审计工作底稿模板 → 填充"这条链**，但文档里根本没提这个。问题类型分类模板、报告段落模板、法规引用标准格式模板——这些才是审计场景真正高频、真正稳定的东西，但不是"知识"，是"模板"。文档把"知识"和"模板"混为一谈。

**改进建议：**
- 区分"知识预编译"（法规条款、案例摘要）和"模板预编译"（报告格式、分类结构、引用规范）。后者价值远大于前者。
- 如果坚持法规预编译，必须配套法规版本监控和失效检测机制，否则一年后就是一堆过期的垃圾。
- 算一笔经济账：维护预编译 Wiki 的人力成本 vs 多跑几次 RAG 的 API 成本，审计事务所的优势是人便宜还是算力便宜？大概率是人更贵。

**评级：⚠️ 需关注**

## 三、实体设计：运行态 + 知识态

### ⚠️ 需关注 — 分类正确但遗漏严重

**当前设计：**
- 运行态实体：被审计单位 / 项目 / 资金
- 知识态实体：问题类型 / 法规 / 整改建议

**遗漏的关键实体类型：**

| 遗漏实体 | 类型 | 影响 | 严重程度 |
|:--|:--|:--|:--|
| **审计证据/底稿** | 运行态 | 审计复核的核心依据，没有它"溯源"就是空话 | 🔴 高 |
| **审计人员/团队** | 运行态 | 责任追溯、质控流程、复核签字全部依赖 | 🔴 高 |
| **时间线/事件** | 运行态 | 资金拨付时间线、合同执行时间线——审计的时空维度 | 🟡 中 |
| **金额/财务科目** | 运行态 | 审计的核心对象，不能只作为实体的属性而非独立实体 | 🟡 中 |
| **风险等级/分类** | 知识态 | 问题分级 P0/P1/P2 的来源，不建模则分级无依据 | 🟡 中 |
| **审计程序/方法** | 知识态 | 审计标准（如《国家审计准则》）规定的方法论，与法规同等重要 | 🟡 中 |
| **主管部门/监管机构** | 运行态 | 政府审计绕不开的实体，问责链条的终点 | 🟡 中 |

**更深层的问题：** 文档把"运行态"和"知识态"当作两种平行的实体分类，但审计场景中它们不是平行关系——是**引用关系**。一个"问题"（运行态）引用一个"法规"（知识态）来"定性"，引用一个"整改建议"（知识态）来"纠偏"。这种引用本身应被建模为一阶实体（`Citation`/`Evidence`），而非仅作为图谱的边。否则按文档 Phase 2 的"确认边 vs 推断边"设计，你无法区分"审计师确认的引用"和"被 AI 推断的引用"——这两者在审计中是天壤之别。

**改进建议：**
- 增加 `Evidence` / `Citation` 作为一阶实体，记录"谁（审计师/AI）在什么时间基于什么来源建立了此引用"。
- 明确区分实体的属性（如金额作为资金实体的属性）和独立实体（如金额异常作为独立的问题实体）。
- 把"审计程序/方法"纳入知识态实体——法规告诉你什么是对，审计程序告诉你怎么查。缺了后者，你不具备指导实操的能力。

**评级：⚠️ 需关注**

## 四、隐含假设与设计缺陷

### ❌ 不科学 — 多项核心假设站不住脚

**假设 1："审计场景 = 根因分析（RCA）——问题定性、归因、追溯与工业 RCA 同构"**

**评价：❌ 不科学。** 工业 RCA 的目标是找到故障根因并修复系统，不涉及法律定性、不涉及问责、不涉及证据链的法律效力。审计场景的"根因分析"需要同时回答三个问题：①这件事违反了什么规定（定性）→ ②谁的责任（问责）→ ③造成了什么后果（影响评估）。工业 RCA 只回答①的工程版。把审计等同于 RCA，会漏掉问责和影响评估这两个审计核心维度。框架设计中完全没有"责任主体归因"和"资金影响量化"的结构化支撑。

**假设 2："先做 RAG 再做图谱，从高频实体逐步积累"**

**评价：⚠️ 需关注。** 方向对了，但"高频实体"的定义缺失。什么算高频？出现了 5 次还是 50 次？谁来统计？在什么时间窗口内？如果不定义阈值和统计机制，Phase 2 的启动条件就是模糊的——要么永远不启动（"还不够高频"），要么仓促启动（"已经够高频了但实体质量很差"）。

**假设 3："AI 输出是辅助，人工确认是红线"**

**评价：✅ 合理但落实不充分。** 理念正确，但在框架设计层面缺乏"如何强制人工确认"的机制。比如：推断边标注为 0.5 置信度，但如果下游系统直接消费图谱边而不看置信度呢？框架没有设计"阻断机制"——即当置信度低于阈值时，系统层面拒绝输出，而非仅依赖人工事后发现。这在审计中是不可接受的。

**假设 4："确认边置信度 1.0，人工校验/权威来源"**

**评价：❌ 不科学。** 置信度 1.0 在信息系统中是一个危险信号——它意味着"绝对无误"。但即便人工校验也有失误概率（人工评审的错误率通常在 5-15%）。更合理的做法是"确认边置信度 ≥ 0.95"，保留"仍可能存在人工疏漏"的余地。把机器推断标注 0.5 而人工确认标注 1.0，会给下游系统（和用户）传递一种虚假的安全感。

**隐藏假设 5：所有知识都可以从现有 12K chunks 中提取**

**评价：⚠️ 需关注。** 框架设计全程假设知识已经入库，但政府审计中大量关键信息不在"入库文档"里——在电话沟通记录里、在微信消息里、在会议纪要的空白处、在审计师的脑子里。没有任何机制处理"未入库知识"的缺口检测和补充流程。

**改进建议：**
- 不要简单挂靠工业 RCA，明确定义审计场景的三个分析维度（定性/问责/影响）。
- 定义 Phase 2 的明确启动条件：实体数量阈值 + 实体关系密度 + 人工校验通过率。
- "推断边"需要配套阻断机制：在审计报告生成环节，含推断边的结论必须触发强制人工确认弹窗。
- 将"确认边"置信度上限设为 0.95，并在 UI 中明确标注"人工校验可达的最高置信度"。
- 增加"知识缺口检测"模块：当查询命中低分或未命中时，生成 knowledge gap report。

**评级：❌ 不科学 / ⚠️ 需关注（多假设各有不同评级）**

## 五、可扩展性：12K → 100K+ chunks

### ⚠️ 需关注 — 架构有死穴

**问题分析：**

1. **余弦相似度 + Top-K 在 12K 规模下没问题，到 100K+ 会出问题。** 余弦相似度在高维空间中随数据量增大，噪声点会显著稀释 Top-K 的精度。100K chunks 时，如果不引入粗排+精排的两阶段策略（Coarse Ranking + Reranker），Top-50 的精度会明显下降。

2. **512 字符固定分块在 100K 规模下是灾难。** 审计文档最需要的是语义完整性——一个法规条款可能 200 字，也可能 2000 字。硬切成 512 会导致：短条款被噪音填充，长条款被截断。文档说计划升级到 800-1000 + 语义切分混合，但**没有给出升级的触发条件和测试标准**。这意味着可能已经错了很久才想起来改。

3. **text2vec-base-chinese → BGE-large-zh-v1.5 的升级路径是合理的，但缺少评估平面。** 换模型后怎么验证效果提升了？怎么判断不是换了个"更贵的差不多的东西"？没有一个固定的评估数据集和基准测试，模型选型就是拍脑袋。

4. **当前无 Reranker，"计划二期加入"——这是把性能问题推迟了，但没说推迟到什么时候。** 一期验收标准要求 Accuracy ≥ 80%、FP ≤ 20%，不加 Reranker 在 12K 规模下可能勉强达标，到 30K 就悬了。如果在 12K 时就加了 Reranker 并以此为基础设定标准，后期扩展时反而有底。

**改进建议：**
- 现在就建立评估数据集（至少 200 条标注查询+答案对），用于后续所有架构变更的回归测试。
- 50K chunks 是一个关键分水岭——在此规模之前必须完成 Reranker 引入和分块策略升级。
- 考虑引入粗排层（如乘积量化 PQ 或 HNSW 的近似搜索），减少精排的候选集。

**评级：⚠️ 需关注**

## 六、审计场景特有约束

### ❌ 不科学 — 关键约束几乎全面缺位

**缺失清单：**

| 约束 | 当前状态 | 严重程度 |
|:--|:--|:--|
| **法规版本管理** | 完全缺失 | 🔴 高 |
| **法规生效/废止时间线** | 完全缺失 | 🔴 高 |
| **数据隔离（多客户）** | 完全缺失 | 🔴 高 |
| **审计底稿保密性** | 完全缺失 | 🔴 高 |
| **引用追溯链审计日志** | 框架提及"溯源"但无实现路径 | 🟡 中 |
| **AI辅助决策的合规声明** | 提及"人工确认是红线"但缺少法律框架支持 | 🟡 中 |

**逐条分析：**

**1. 法规版本管理与时间线（🔴）**
审计的核心命题是"在特定时间点的行为是否符合当时有效的法规"。如果知识库存储了最新版《预算法》但没有记录 2018 年修订前的版本，那么对一个发生在 2017 年的项目行为进行"定性"时，检索到的是无效法规。当前框架没有任何"法规时间有效性"的概念，这是一个致命缺陷。

**2. 数据隔离（🔴）**
事务所服务多个政府客户，不同客户的数据（审计报告、底稿、资金数据）必须严格隔离。当前框架的 RAG 检索是全库检索——这意味着客户 A 的审计知识会被用于回答客户 B 的查询。这在政府审计中不仅是合规问题，是有可能触犯保密法的。

**3. 审计底稿保密性（🔴）**
审计底稿含有大量涉密信息（政府预算细节、项目资金流向、内部管理问题）。当前框架将这些数据作为 RAG chunk 入库，检索时会暴露给 AI 模型处理。如果使用外部 API（如 DeepSeek），则等同于向第三方传输涉密数据——这严重违反政府审计的保密要求。

**4. 引用追溯链（🟡）**
框架说"每条意见必须能追到具体法规和项目底稿"，但没有描述这个追溯链的技术实现。如果只是把引用来源存储为文本字段，那就无法实现"当底层法规更新时，自动标记所有引用该法规的历史报告为待复核"这种高级功能。

**改进建议：**
- **紧急：在知识库中为每条法规增加 `effective_date` 和 `expiry_date` 字段**，检索时必须带时间上下文过滤。
- **紧急：在 RAG 检索层实现租户隔离**（tenant_id 必传，强制过滤）。多租户架构必须在一期就设计好，后期改是数据迁移的噩梦。
- **紧急：评估本地部署 LLM 的可行性**——如果涉密数据必须经过外部 API，必须有明确的数据脱敏方案和客户知情同意流程。
- 建立"法规-报告"的引用图谱，支持法规更新后的反向追溯。

**评级：❌ 不科学**

## 七、缺失的关键组件（补充发现）

除上述六项评审要点外，以下组件在当前框架中完全缺失：

### 7.1 监控与可观测性
- 没有提到 retrieval quality 的持续监控（准确率漂移检测）
- 没有提到 chunk 质量的自动化评估
- 没有提到 LLM 输出的自动回归测试

### 7.2 反馈闭环
- 审计师修正 AI 输出后，修正结果是否回流到知识库？
- 推断边被人工确认后，如何自动升级为确认边？
- 没有 Human-in-the-loop 作为系统级能力的设计

### 7.3 灾难恢复
- 12K chunks 的索引重建需要多长时间？
- 向量库损坏后的恢复流程是什么？
- 没有备份策略

### 7.4 成本模型
- RAG 查询一次多少钱？LLM Wiki 页生成一次多少钱？
- 不同阶段的预算估算完全缺失
- 从"预编译 Wiki + 缓存 + 实时 RAG"三级走，每次查询的预期成本是多少？

## 九、优先级行动清单

### 🔴 P0 — 不做不能上线
1. 法规版本时间线（effective_date / expiry_date）建模
2. 多租户数据隔离架构设计（一期就必须有）
3. 涉密数据与外部 API 的交互策略（本地 LLM 或脱敏方案）

### 🟡 P1 — 一期结束前必须完成
4. 建立评估数据集（≥200 条标注查询）
5. 知识缺口自动检测机制
6. 推断边阻断机制（置信度 < 阈值 → 强制人工确认弹窗）
7. 审计底稿/证据链实体建模

### 🟢 P2 — 二期规划时考虑
8. Reranker 引入时机和评估标准
9. 粗排+精排两阶段检索架构
10. 知识反馈闭环（人工修正回流）
11. 可观测性与持续质量监控
12. 成本模型与预算规划

## 结语

框架的**方向是对的**——RAG 先导、阶段性演进、人工确认红线——这些都是冷静务实的选择。但方向对不等于能落地。当前版本在安全合规层面有三个致命缺口（法规版本、数据隔离、涉密保护），任何一个不解决都不该进入工程实施。在补上这些之前，这个框架仍然停留在"美好的想法"阶段。

审计不是一个可以"先上线再迭代"的领域。一次涉密信息泄露的代价远比技术债务更高。先把基础做扎实，再谈演进。
