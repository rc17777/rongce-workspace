## 一、两篇文章的核心洞察

### 文章1：Agent Harness Engineering（腾讯内审）

**核心命题**：通用 Agent 面对复杂任务时，「临场发挥」不可靠——需要一套工程「外骨骼」把模型能力约束在可控边界内。

| 维度 | 通用Agent的问题 | Harness Engineering的解法 |
|:--|:--|:--|
| 深度检索 | 查不全、乱编造、过程不可追溯 | 四环节控制：生成查询→来源约束→迭代检索→收敛与证据 |
| 智能分类 | 上下文不够、重复稀释信息 | 三步法：预打标(工程)→构建体系(人机)→全量分类(工程+AI复判) |
| 智能问数 | 每次都从头探索、口径不一致 | 数据理解底座：结构扫描→画像→语义→校验→沉淀，分层加载 |

**三层分工模型**（理论基石）：
- **审计师**：提出目标、定范围口径、确认歧义与结论
- **Agent**：理解任务、组织步骤、处理模糊、动态调整
- **工程链路**：批量、重复、规则明确的处理，保证稳定可复用

### 文章2：Multi-Agent 18步协作框架

**核心命题**：Multi-Agent 拼的不是模型能力，是组织能力——把一堆模型组织成一支打得赢的团队。

**七大角色**：
- 用户（甲方）
- 管理Agent（项目经理/Orchestrator）
- Planner（规划师/架构师）
- 研究Agent（情报员）
- 执行Agent（工程师/写手）
- Reviewer（质检员）
- 工具/环境（外部世界）

**18步核心流程**：
```
对齐目标(1-3) → 拆任务排依赖(4-5) → 派活(6)
  → 双线并行：研究线(7-9) ∥ 执行线(10-11)
  → 汇总中间稿(12) → Reviewer审查(13-14)
  → 虚线反馈回路(15-16) → 交付(17-18)
```

**五条原则 + 八个落地坑**已在上方原文中详述。

## 二、两篇文章的统一框架：融策·审盾「外骨骼+项目组」双引擎模型

### 2.1 为什么两篇必须一起读

**文章1（Harness Engineering）回答了「单个Agent怎么做才对」**：
- 不是让 Agent 自由发挥，而是给它搭工程脚手架
- 数据理解底座、智能分类三步法、深度检索四环节——都是「单一能力域」的工程化

**文章2（Multi-Agent）回答了「多个Agent怎么协作才对」**：
- 不是几个 GPT 互相发消息，而是像项目组一样有分工有复核
- 对齐→规划→执行→审查→迭代——是「跨能力域」的组织化

**两篇合在一起 = 完整答案**：先给每个 Agent 搭好 Harness（让它单兵作战能力可靠），再用 Multi-Agent 框架把它们组织成协同作战的项目组。

## 四、顶层设计原则（两篇文章的共同方法论）

### 原则1：按工作性质分工，不按模型能力分工

| 谁做 | 做什么 | 为什么 |
|:--|:--|:--|
| **模型/Agent** | 语义理解、模糊判断、动态调整 | 这是模型擅长的 |
| **工程链路** | 批量、重复、规则明确的处理 | 稳定、可记录、可复用 |
| **审计师** | 业务口径、关键判断、最终结论 | 专业判断不可替代 |

### 原则2：执行不打分，打分不执行

> 「让做事的人不打分，让打分的人不做事。」

- 执行Agent不评估自己的产出质量
- Reviewer不亲自下场修改
- 角色分离 = 对抗错误累积的**结构**解法，不是模型能力解法

### 原则3：闭环比单次生成更重要

> 一次性生成靠运气，带闭环的生成靠机制。

- Plan → Execute → Review → Replan 循环
- 虚线反馈回路：精准派单式返工，不整体重跑
- 必须设退出条件和最大轮次

### 原则4：复杂被藏进流程，简单是被设计出来的

- 用户只做两件事：提任务 + 收结果
- 中间全部复杂度由「Harness + Multi-Agent 框架」消化
- 过程全留痕、可回溯、可复盘

### 原则5：先 Harness，后 Multi-Agent

- 没有 Harness 的 Agent 是「裸奔」——不可控
- 没有 Multi-Agent 的 Harness 是「独狼」——不协同
- 建设顺序：先给单个 Agent 搭好外骨骼 → 再把它们组织成项目组

## 八、2026-08-04 五项完善（基于审计预警体系文章深度分析）

### 8.1 可解释性验收标准（⚠️ 一期准生证）

> 详见：[审盾一期验收标准-可解释性增补](审盾一期验收标准-可解释性增补-20260804.md)

**核心红线**：无法解释的预警，在审计报告里无法作为证据使用。

**新增必须达标项**（嵌入一期30天实验）：
- Level 1：规则编号 + 触发条件覆盖率 **100%**
- Level 2：文件级溯源率 **100%**，页级≥90%，行级≥70%
- Level 3：风险逻辑链完整率 **≥60%**
- 人工可复现率 **≥85%**

**影响**：一期复核器输出格式必须按修订版规范——不含解释的不算发现。

### 8.2 离线异构数据适配器（🔧 阶段1 H1 增强）

> 详见：[审盾-数据理解底座-离线异构适配器设计](审盾-数据理解底座-离线异构适配器设计-20260804.md)

**核心矛盾**：央企甲方有数据中台，融策乙方面对的是离线异构低质量数据。

**六种入口归一化**：CSV/Excel/PDF扫描件(OCR)/PDF电子件/数据库导出/API → 统一SDF数据帧

**v1.0 交付时间表**：
- v0.3（阶段1第2-3周）：CSV + 多Sheet Excel + 多行表头
- v0.5（阶段1第3-4周）：PDF电子件 + 语义标注层
- v1.0（阶段1结束）：完整六入口 + 口径校验层

### 8.3 指标体系：复核→预警延伸（📊 一期→二期桥接）

> 详见：[审盾-指标体系-复核到预警延伸设计](审盾-指标体系-复核到预警延伸设计-20260804.md)

**核心设计**：一套指标，两个时钟。复核阈值（严）和预警阈值（敏感）共享同一指标定义。

**关键发现**：趋势指标是复核的天生短板但预警的核心武器——这是审盾预警最大的差异化空间。

**新增配套工具**：`indicator_registry.py` — 指标注册/查询/共享率统计

### 8.4 独立模型层：四层可插拔架构（🧠 阶段2新增模块）

> 详见：[审盾-模型层可插拔架构设计](审盾-模型层可插拔架构设计-20260804.md)

**为什么Agent还不够**：Agent Prompt里混合了业务逻辑和检测逻辑 → 复用差、升级难、可解释性弱。

**四层架构**：
- **L1 规则引擎**（白盒，解决已知风险）：从AgentDebugX迁移 + 新增R4xx/R5xx/R6xx规则包
- **L2 统计模型**（灰盒，统计异常）：Benford/Z-score/DBSCAN/DTW/FP-growth/回归残差
- **L3 机器学习**（黑盒+可解释补偿，未知模式）：孤立森林/LOF/XGBoost → SHAP补偿可解释性
- **L4 知识图谱**（灰盒，关系异常）：路径推理/环检测/图异常/模式匹配
- **L0 统一输出层**：所有发现统一Finding Schema（评分+解释+证据链）

**与阶段2的关系**：模型层与Agent协作层平行运行。Agent变成业务编排器，模型层变成检测引擎。

### 8.5 对外品牌话术：三维风险画像（🎯 客户沟通标准化）

**对外讲三维，对内跑五维**：
- 👤 身份画像（对客） = 社会关系坐标系（对内）

**交付物**：宣传册/PPT/投标方案的标准化话术素材库，含常见客户质疑应答模板。
