# 审盾一期验收标准 — 可解释性指标增补

> 编制时间：2026-08-04
> 依据：公众号「审计实践」《审计预警体系构建》三条红线之「模型不能是黑箱」
> 用途：审盾一期30天实验第4-10天（构建最小复核器）和第21-25天（盲测）必须加入此标准

---

## 一、为什么可解释性是审盾的"准生证"

文章原话：

> "无法解释的预警，在审计报告里无法作为证据使用。"

翻译成审盾场景：**AI复核发现的每一个问题，必须能写进复核意见——而复核意见是审计工作底稿的一部分**。如果AI只能说"这条有问题"但说不出"为什么有问题"，这条发现就没有证据效力。

这意味着可解释性不是"锦上添花"或"二期再说"——它是一期能不能通过验收的硬门槛。

---

## 二、可解释性三级标准

### Level 1：规则可解释（最低门槛，必须100%达标）

> 每一条AI发现必须附带**具体的触犯规则编号和触发条件**。

格式：
```
[F-R0xx] 规则编号 & 规则名称
触发值：XX（实际值）
阈值/基准：XX（期望值或参照值）
数据来源：文件A-第B页-第C行
```

**例子**：
```
[F-R001] 报告日期格式不一致
触发值："2024.6"（第23页）
阈值/基准：正文中所有日期应为"YYYY年MM月"格式
数据来源：绩效评价报告.docx-第23页-第3行
```

### Level 2：证据可溯源（目标覆盖率≥90%）

> 每条发现必须指向**可验证的原始数据位置**。

要求：
- 文件级溯源（指向具体文件）：100%覆盖
- 页级溯源（指向页码范围）：≥90%覆盖
- 行级溯源（指向具体行/单元格）：≥70%覆盖

### Level 3：因果可解释（目标覆盖率≥60%，盲测重点）

> 不仅说"是什么"，还要说"为什么这构成风险"。

格式：
```
风险逻辑链：
① A数据呈现X值 → ② 该值超出行业基准B的C% → ③ 导致D类风险（ε级）
→ ④ 建议：核查E原因，确认F影响
类似案例：[引用本项目或历史项目中相似发现的处理]
```

**例子（绩效评价情景）**：
```
风险逻辑链：
① 项目完成率88.7% → ② 低于合同约定的95%完成标准6.3个百分点
→ ③ 构成资金使用效率风险（P1级） → ④ 建议：核查6.3%差口的资金去向及原因
类似案例：2025年郫都区XX项目中，完成率低于目标5%以上触发了资金收回建议
```

## 三、验收指标矩阵

| 指标 | Level 1 要求 | Level 2 要求 | Level 3 要求 | 测量方式 |
|:--|:--:|:--:|:--:|:--|
| 规则编号覆盖率 | 100% | — | — | 随机抽20条AI发现，检查是否全部附带规则编号 |
| 触发值/阈值标注率 | 100% | — | — | 同上，检查是否全部标注了触发条件和对比基准 |
| 文件级溯源率 | — | 100% | — | 统计所有AI发现指向的文件，是否100%明确 |
| 页级溯源率 | — | ≥90% | — | 随机抽20条，检查≥18条能定位到页码范围 |
| 行/单元格溯源率 | — | ≥70% | — | 随机抽20条，检查≥14条能定位到具体行 |
| 风险逻辑链完整率 | — | — | ≥60% | 随机抽20条，检查≥12条有完整因果链 |
| 人工可复现率 | — | — | ≥85% | 给审计经理看AI发现+解释，独立确认能否复现判断 |

## 四、AI复核输出格式规范（修订版）

### 原有格式（不可接受）
```
⚠️ 发现：XX项目绩效指标完成率异常
```

### 修订后格式（必须达标）
```markdown
### [F-P002] 绩效指标完成率低于合同约定

| 要素 | 内容 |
|:--|:--|
| **规则编号** | F-P002 |
| **规则名称** | 产出指标完成率低于合同约定 |
| **触发值** | 项目完成率 88.7% |
| **阈值/基准** | 合同约定 ≥95% |
| **偏离幅度** | -6.3 个百分点 |
| **数据来源** | 《绩效评价报告》第23页，表5-3「产出指标完成情况」 |
| **严重程度** | P1（资金使用效率风险） |
| **风险逻辑链** | 完成率低于合同约定 → 差口6.3pp → 可能涉及资金闲置/挪用/已拨付未完成 |
| **类似案例** | 2025年郫都区XX项目（H-packet X-ref #HJ-2025-017） |
| **建议** | 核查88.7% vs 95%差口的6.3个百分点对应资金去向及原因 |
| **人工确认点** | ☐ 确认完成率统计口径 ☐ 确认差口原因定性 ☐ 确认整改建议适用性 |
```

## 五、实施节点（嵌入一期30天实验）

| 时间 | 节点 | 可解释性动作 |
|:--|:--|:--|
| 第1-3天 | 形成检查清单 v1.0 | 每条检查规则预写「为什么这条构成风险」 |
| 第4-10天 | 构建最小复核器 | **输出格式必须按修订版规范**，不含解释的不算发现 |
| 第11-20天 | 业务骨干逐条校验 | 统计Level 1/2/3达标率，不达标的发现标记为"无效" |
| 第21-25天 | AI vs 人工盲测 | 盲测评审增加「可解释性」评分维度（1-5分） |
| 第26-30天 | 形成验证报告 | 可解释性单独成章，作为通过/不通过的核心指标之一 |

---

## 六、通过标准（修订版）

在原有一期通过标准基础上，增加：

| 新增标准 | 门槛 | 必须/建议 |
|:--|:--|:--:|
| Level 1 规则编号 + 触发条件覆盖率 | **100%** | 必须 |
| Level 2 文件级溯源率 | **100%** | 必须 |
| Level 2 页级溯源率 | **≥90%** | 必须 |
| Level 2 行/单元格溯源率 | **≥70%** | 必须 |
| Level 3 风险逻辑链完整率 | **≥60%** | 必须 |
| 人工可复现率 | **≥85%** | 建议 |
| 盲测中「可解释性」维度平均分 | **≥4.0/5.0** | 建议 |

**判定规则**：5项"必须"指标全部达标 → 可解释性通过。任一项不达标 → 一期暂不通过，整改后重新验证。
