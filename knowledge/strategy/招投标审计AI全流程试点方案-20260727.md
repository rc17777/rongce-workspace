# 融策·审盾一期：招投标审计AI全流程试点方案

> **日期**：2026-07-27
> **试点范围**：1个真实招投标审计项目
> **试点周期**：从审前调查到出具报告，全流程覆盖
> **目标**：验证AI在招投标审计中的实际效果，产出可复用的标准化流程

---

## 一、为什么选招投标审计做第一条试点线

| 优势 | 说明 |
|:--|:--|
| 数据标准化高 | 招标公告、投标文件、开标记录、评标报告都有固定格式 |
| 异常模式清晰 | 串标/围标有明确的行为特征（报价规律、文本雷同、关联关系） |
| 定量分析占比高 | 大部分分析可以数字化，AI替代效果最明显 |
| 融策已有基础 | L1-L23多层检测体系已建成，8项电子指纹等工具可用 |
| 报告结构固定 | 发现问题→证据→定性→建议的链条清晰，适合作为模板 |

## 二、试点全流程设计

### Phase 1：审前调查（AI增强版）

**输入材料**：
- 被审计单位3年招标台账（Excel）
- 招标管理制度文件
- 历史审计报告/内控检查报告
- 组织架构图+采购部门人员名单

**AI分析产出**：

| 产出 | 内容 | 预计时间 |
|:--|:--|:--|
| 风险热力图 | 按采购品类/部门/时间段标注高风险区域 | 5分钟 |
| 高频供应商名单 | 3年内中标≥3次的供应商+中标金额排名 | 2分钟 |
| 历史异常信号 | 从历史报告中提取的已知问题+整改状态 | 3分钟 |
| 数据采集清单 | 本次审计需要采集的数据类型、来源、格式要求 | 5分钟 |
| 审计重点建议 | 基于风险热力图推荐的审计重点+抽样策略 | 5分钟 |

**操作方式**：将输入材料提交给AI → 输出标准化的审前调查报告 → 审计经理确认/调整审计重点

### Phase 2：数据采集

**标准化数据源**：
- [ ] 招标公告/中标公告（从政府采购网导出或API获取）
- [ ] 开标一览表（报价数据）
- [ ] 评标报告（评委打分）
- [ ] 投标文件电子版（如有）/纸质扫描件

**非标数据处理**：
- 纸质投标文件 → PaddleOCR → 结构化提取
- 扫描版合同 → OCR → 关键条款提取
- 银行保函/保证金凭证 → OCR → 金额+时间+对方单位提取

### Phase 3：数据分析（AI全量检测 — 核心环节）

#### 检测清单（按照23层检测体系+五层穿透）

**第一轮：自动规则检测（秒级）**

| 检测项 | 方法 | 预期产出 |
|:--|:--|:--|
| L1 报价规律 | 所有投标人报价偏离度+报价模式聚类 | 异常报价模式组 |
| L2 IP/MAC | 如有投标平台日志则检测 | 同IP/MAC标记 |
| L3 文本雷同 | TF-IDF全文比对矩阵 | 雷同文件对+相似度分数 |
| L4 图片哈希 | 投标文件嵌入图片感知哈希 | 同图标记 |
| L5 元数据 | core.xml/WPS GUID提取比对 | 同源标记 |
| L7 打印机 | PDF Producer字段提取 | 同设备标记 |
| L8 工商关联 | 全量供应商天眼查穿透 | 关联关系图谱 |
| L18 电子指纹 | CPU/硬盘/网卡/机器码/文件GUID八项 | 同机标记 |

**第二轮：AI智能分析（分钟级）**

| 分析维度 | AI分析内容 | 穿透层级 |
|:--|:--|:--|
| 中标模式分析 | 全量中标记录→识别"中标专业户"+ "陪标专业户" | L15历史模式 |
| 报价协同分析 | 所有项目报价的协同变动模式（是否串通抬高/压低） | L1报价规律 |
| 时间异常分析 | 投标时间序列→截止前集中提交+异常时段提交 | 新维度 |
| 评委打分分析 | 逐项打分分布→识别对特定投标人的系统性偏高/偏低 | L10评标异常 |
| 利益流向分析 | 中标方股权穿透→实际控制人vs采购部门人员交叉 | L8+利益流向图 |
| 制度博弈分析 | 招标方式选择（公开/邀请/单一来源）的合理性检查 | 制度博弈论 |

**第三轮：根因分析（人工审核+AI辅助）**

| 分析内容 | 五层穿透对应 | 方法 |
|:--|:--|:--|
| 为什么这些供应商形成串标网络？ | 利益流向图 | 关联图谱→利益链→背后推手 |
| 为什么招标制度没有阻止？ | 制度博弈论 | 审批流程分析→制度漏洞定位 |
| 谁在推动定向招标？ | 决策现场还原 | 时间轴+权力轴交叉 |
| 市场环境是否也推高了价格？ | 宏观坐标系 | 同类项目价格对比+市场行情 |
| 最根本的原因是什么？ | 五问为什么 | LLM根因推理链 |

#### 产出标准

每个异常发现必须包含：

```json
{
  "finding_id": "BID-2026-001",
  "level": "L3-文本雷同",
  "description": "A公司、B公司、C公司投标文件技术方案文本相似度>85%",
  "similarity_scores": {"A-B": 0.87, "A-C": 0.89, "B-C": 0.85},
  "confidence": "高",
  "penetration": {
    "利益流向": "A公司实控人张某为B公司前股东",
    "制度博弈": "该项目采用邀请招标，仅5家受邀，3家雷同",
    "决策还原": "邀请名单由采购科长王某一人拟定",
    "宏观坐标": "同类项目同期市场均价低于中标价22%",

  },
  "evidence": [

```

### Phase 4：延伸取证

**AI生成核查要点清单**（取代大海捞针）：

| 异常发现 | AI生成的核查问题 | 取证目标 |
|:--|:--|:--|
| 文本雷同 | "这三家公司的投标文件是谁制作的？为什么技术方案几乎一模一样？" | 确认是否同一人/同一团队制作 |
| 关联控制 | "请采购科长王某解释：为什么他批准的邀请名单里有3家是他前同事控制的公司？" | 确认利益输送 |
| 价格异常 | "为什么中标价比同期同类项目市场均价高出22%？" | 确认价格操纵 |
| 评标异常 | "评委李某对所有A公司的评分都比其他评委高15-20分，请李某解释评分依据" | 确认评标不公 |

### Phase 5：出具报告

**AI初稿** → 审计经理审核 → 最终报告

报告按新版标准（手册v2.0第五章）的三个问题段结构编写。

## 三、试点检验指标（衡量AI有效性的硬数据）

| 指标 | 传统方式 | AI方式目标 | 测量方法 |
|:--|:--|:--|:--|
| 数据分析耗时 | 3-5天 | <4小时 | 计时 |
| 标书覆盖范围 | 抽查10-20% | 全量100% | 覆盖率统计 |
| 异常发现数量 | 5-15个 | 20-50个 | 统计 |
| 最终确凿发现（人工确认） | 3-8个 | 10-25个 | 统计 |
| 误报率（AI标记但人工排除） | N/A | <30% | 统计 |
| 漏检率（人工发现但AI没标记） | N/A | <10% | 审计经理复核 |
| 报告撰写耗时 | 2-3天 | <半天 | 计时 |
| 被审计单位质疑率 | 中等 | 降低（因为证据更充分） | 事后统计 |
| 审计经理满意度 | N/A | ≥4/5 | 评分 |

## 四、试点所需条件

### 4.1 人员

- 1名招投标审计业务骨干（全职投入试点期）
- 1名AI训练师（兼，可由业务骨干+AI助手配合）
- 平头哥（最终审核+质量把关）

### 4.2 数据

- 1个真实项目的完整招投标数据
- 天眼查/企查查API（已有）
- 最好有投标文件电子版（实现L3-L5全量检测）

### 4.3 工具

- Python脚本：全量TF-IDF比对、报价规律检测、工商关联穿透（已有/可复用）
- AI：DeepSeek V4 Pro（数据分析+根因推理）
- PaddleOCR（非标数据提取，已有）
