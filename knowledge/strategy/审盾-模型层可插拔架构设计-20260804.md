# 审盾·模型层 — 四层可插拔架构设计

> 编制时间：2026-08-04
> 依据：公众号「审计实践」文章「模型构建」环节——规则引擎+机器学习+知识图谱分层预警
> 用途：审盾路线图阶段2新增独立模型层模块，与Agent协作层平行运行

---

## 一、为什么Agent还不够，需要一个独立的模型层

审盾当前架构中，Agent（如 bid_hunter、performance_evaluator）直接在Prompt中混合了"业务逻辑"和"检测逻辑"。这带来三个问题：

1. **复用差**：同一个异常检测逻辑（如"报价偏离度检测"），bid_hunter用一次，settlement_auditor再用一次，需要写两套Prompt
2. **升级难**：想换一种检测算法（从阈值改到孤立森林），需要修改Agent Prompt——Agent应该只做业务编排，不应该绑定具体算法
3. **可解释性弱**：Prompt里出来的结论，解释往往笼统——"这个报价有点奇怪" vs 模型层的"报价X偏离中位数3.2σ，同类项目前5%极端值"

**解决方案：把检测逻辑从Agent中抽离出来，形成独立的模型层。Agent变成业务编排器，模型层变成检测引擎。**

## 三、各层详解

### L1：规则引擎

**定位**：解决"已知风险"。100%可解释，审计证据链完整。

**现有基础**：AgentDebugX 20条确定性规则 → 模型层接管

| 规则包 | 内容 | 来源 |
|:--|:--|:--|
| R0xx 格式协议 | 日期格式、数值单位标注、表格完整 | AgentDebugX |
| R1xx 逻辑一致 | 借贷平衡、合计校验、期间匹配 | AgentDebugX + 新增 |
| R2xx 审计专项 | 三公经费超预算、专项资金挪用标识 | 从Agent Prompt中抽取 |
| R3xx 多Agent交接 | H-packet完整性、版本号递增 | AgentDebugX |

**新增规则包**：

| 规则包 | 内容 | 对应业务线 |
|:--|:--|:--|
| R4xx 预算执行 | 预算调整率、结余率、超预算项目 | 预算执行、绩效 |
| R5xx 招投标 | 评标基准价偏离、技术分异常离散 | 招投标 |
| R6xx 工程结算 | 变更签证率、超概率、量价分离 | 工程 |

**接口**：
```python
# Agent调用方式
findings = rule_engine.check(
    data_sdf,          # 统一数据帧
    rule_packages=["R0xx", "R1xx", "R2xx", "R4xx"],  # 激活的规则包
    business_line="预算执行"
)
```

### L2：统计模型

**定位**：解决"统计意义上的异常"。半可解释（统计方法可解释，但"为什么异常"需要审计师判断）。

**现有基础**：部分已实现，散落在各Skill里

| 模型 | 用途 | 状态 | 可解释方式 |
|:--|:--|:--:|:--|
| Benford定律 | 财务数据首位数字分布检验 | ✅ financial-fraud-detection | 观测vs期望分布对比 |
| Z-score | 单指标极端值检测 | 🟡 部分Skill用 | 偏离均值σ数 |
| DBSCAN聚类 | 供应商/交易对手异常分组 | 🔴 待建 | 聚类成员+离群点距离 |
| 动态时间规整(DTW) | 支出时间序列异常 | 🔴 待建 | 与历史同期曲线对比 |
| FP-growth频繁模式 | 供应商伴随投标 | ✅ procurement-audit-models (L11) | 伴随概率+共现次数 |
| 线性回归残差 | 成本-收入关系异常 | 🔴 待建 | 残差≥2σ的数据点 |

**接口**：
```python
# Agent调用方式
findings = stats_engine.detect(
    data_sdf,
    models=["benford", "zscore", "dbscan", "fp_growth"],
    config={"zscore_threshold": 3.0, "dbscan_eps": 0.5}
)
```

### L3：机器学习

**定位**：解决"未知模式"——无监督异常检测发现规则引擎和统计模型都漏掉的线索。

**关键约束**：ML模型的"可解释性"必须通过L0输出层的解释生成器补偿——SHAP值、LIME、对比案例。

| 模型 | 用途 | 数据需求 | 可解释补偿 |
|:--|:--|:--|:--|
| 孤立森林(Isolation Forest) | 多维特征空间异常检测 | ≥500条记录 | SHAP特征重要性排名 |
| LOF(局部离群因子) | 局部密度异常 | ≥200条记录 | 邻近点距离排序 |
| XGBoost | 有标签场景(如果有历史疑点标签) | ≥1000条+标签 | 特征重要性+决策路径 |
| AutoEncoder | 高维特征降维异常 | ≥2000条 | 重构误差最大的特征 |

**适用条件**：
- 孤立森林/LOF：数据量≥500条时激活，<500条时回退到L2统计模型
- XGBoost：只有在有历史疑点标注数据时才激活，否则降级
- AutoEncoder：二期暂不启用，留给三期

**接口**：
```python
# Agent调用方式
findings = ml_engine.detect(
    data_sdf,
    models=["isolation_forest", "lof"],
    mode="unsupervised",  # 审盾一期/二期都是无监督
    explainability="shap"
)
```

### L4：知识图谱推理

**定位**：解决"关系异常"——不是某个实体本身有问题，而是实体之间的关系有问题。

**现有基础**：audit-knowledge-graph Skill + 串标L8工商关联穿透

| 推理类型 | 检测目标 | 状态 | 示例 |
|:--|:--|:--:|:--|
| 路径推理 | 隐藏关联 | 🟡 | A公司→B公司→C自然人→D公司(虽是不同供应商但同受C控制) |
| 环检测 | 循环交易 | 🔴 | A→B→C→A的资金循环 |
| 图异常检测 | 异常密集子图 | 🔴 | 多个供应商和多个项目形成异常密集投标网络 |
| 模式匹配 | 已知舞弊模式 | 🔴 | 识别已知的围标网络拓扑结构 |

**接口**：
```python
# Agent调用方式
findings = kg_engine.query(
    entity_ids=["C001", "C002", "C003"],  # 待分析的企业ID列表
    graph="bidding_network",
    queries=["path", "cycle", "density"],
    max_depth=4
)
```

## 五、Agent 调用模型层的典型流程

```
Planner 拆解任务
  │
  ├─→ 研究Agent: "检索绩效评价相关法规和案例"
  │      └─→ 知识库RAG查询
  │
  └─→ 执行Agent(performance_evaluator): "复核XX项目绩效评价报告"
         │
         ├─ Step 1: 数据入湖（适配器 → SDF）
         │
         ├─ Step 2: 按业务线选择模型组合
         │    model_config = {
         │      "rules": ["R0xx", "R1xx", "R4xx"],
         │      "stats": ["benford", "zscore"],
         │      "ml": ["isolation_forest", "lof"],
         │      "kg": null  // 绩效评价场景不启用图谱
         │    }
         │
         ├─ Step 3: 逐层运行模型
         │    findings_L1 = rule_engine.check(data, rules)
         │    findings_L2 = stats_engine.detect(data, models)
         │    findings_L3 = ml_engine.detect(data, models)  // if data.size >= 500
         │
         ├─ Step 4: 合并去重（模型层内部）
         │    all_findings = dedup(findings_L1 + findings_L2 + findings_L3)
         │
         ├─ Step 5: Agent做业务判断
         │    "哪些发现需要写入报告？严重程度调整？整改建议措辞？"
         │
         └─ Step 6: 输出到 H-packet → Reviewer
```
