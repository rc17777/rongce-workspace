> 基于 Superpowers（obra/superpowers, 262k ⭐）方法论重构审盾架构
> 来源: `knowledge/references/superpowers/`
> 日期: 2026-07-28

---

## 一、核心思想：从"AI 输出"到"AI 作业流程"

Superpowers 解决的核心矛盾：**AI 不是不够聪明，而是太急着证明自己能干活。**

审盾 v1.0（22 Agent 并行平台）解决了"谁来干活"的问题，但没有解决"怎么干活才能不出错"的问题。v2.0 引入 Superpowers 的**工程纪律层**：给每个 Agent 装上可执行的流程规则，让 AI 像审计老兵一样——先调查、再判断、验证后才下结论。

---

## 二、Superpowers → 审盾 映射

| Superpowers Skill | 核心理念 | 审盾映射 | 对应模块 |
|:--|:--|:--|:--|
| **brainstorming** | 先设计再实现，有 HARD-GATE | 审计需求澄清 | 业务承接→审前调查→方案确认 |
| **writing-plans** | 拆成可验证的小步 | 审计实施方案 | 程序表→底稿模板→人员分工 |
| **test-driven-development** | 先写测试再写代码 | 程序先行 | 先出底稿模板再现场取证 |
| **systematic-debugging** | 根因在前，修复在后 | 疑点穿透 | 五层穿透思考框架 |
| **verification-before-completion** | 证据先于结论 | 证据闭环 | 取证单→底稿→报告三级验证 |
| **subagent-driven-development** | 子智能体分工+审查 | 多Agent并行 | 22 Agent + 疑点融合中枢 |
| **requesting-code-review** | 两轮审查 | 三级复核 | 项目组→部门→质控 |
| **dispatching-parallel-agents** | 并行不干扰 | 5坐标系穿透 | 时空×物理×社会×行为×时序 |

## 三、审盾 v2.0 八大 Skill（可执行规则）

每个 Skill 采用 Superpowers 结构：
- YAML frontmatter（名称/触发条件/描述）
- Iron Law（铁律，不可违反）
- HARD-GATE（硬门槛，未满足不得继续）
- Checklist（按顺序执行）
- Anti-Patterns（常见错误）
- Verification（完成后验证）

---

### Skill 1：审前策划（brainstorming）

**触发条件：** 新项目启动 / 新增审计事项 / 变更审计范围

**Iron Law：**
```
方案未经确认，不得进场作业
```

**Checklist：**
1. 阅读项目背景资料（委托书/以前年度报告/被审单位信息）
2. 逐个澄清：审计目标、范围、时间、资源、风险
3. 提出 2-3 种审计策略（全覆盖/抽样/重点穿透）
4. 与委托方/项目负责人确认方案
5. 撰写《审计实施方案》并入库
6. 自动生成《审前检查表》——未确认项不得跳过

**Anti-Pattern：** "这个项目很熟，不用写方案直接干"
**验证：** 方案文件存在且包含目标/范围/程序/人员四项，否则 HARD-GATE 拦截

---

### Skill 2：程序先行（TDD 映射）

**触发条件：** 方案确认后 / 新发现疑点需新增程序

**Iron Law：**
```
先出底稿模板，再进场取证；先列程序，再收集证据
```

**Checklist：**
1. 按方案分解审计程序
2. 每个程序对应一张《审计底稿模板》（含取数口径/认定目标/预期结论）
3. 模板经负责人审核
4. 按模板进场取证
5. 证据填入模板后才可调整结论

**Anti-Pattern：** "先收资料再说，收完再想怎么用"
**验证：** 每个进场日的底稿模板数 ≥ 当日计划程序数

---

### Skill 3：疑点穿透（systematic-debugging）

**触发条件：** 发现异常/疑点/违规线索

**Iron Law：**
```
不完成根因分析，不得提出定性结论
```

**五层穿透流程（已入库 `knowledge/strategy/审计五层穿透思考框架.md`）：**
1. **利益流向图** — 钱从哪来、经过谁、到哪去
2. **制度博弈论** — 设计漏洞 vs 执行偏差 vs 故意规避
3. **决策现场还原** — 当时谁决定、依据什么、替代方案
4. **宏观坐标系** — 同样的政策在其他地方执行情况
5. **五问为什么** — 连续追问直到找到制度性根因（`scripts/five_whys.py`）

**HARD-GATE：** 未完成 Phase 1-3 不得写底稿结论
**验证：** 底稿中必须包含"根因分析"段落，否则复核告警

---

### Skill 4：证据闭环（verification-before-completion）

**触发条件：** 写底稿结论前 / 汇总问题前 / 出报告前

**Iron Law：**
```
没有当次验证证据，不得宣称"已确认"
```

**三级验证：**
| 级别 | 内容 | 执行人 | 验证要求 |
|:--|:--|:--|:--|
| V1 | 取证单→底稿 | 项目组成员 | 每项结论有对应取证单编号 |
| V2 | 底稿→汇总 | 项目组长 | 汇总表与底稿合计一致 |
| V3 | 报告→底稿 | 质控 | 报告每条发现对应底稿+取证单 |

**Red Flags（立即 STOP）：**
- 使用"应该""大概""看起来"等模糊词
- 未标记取证单编号
- 汇总数手算未交叉验证
- AI 说"已完成"但没附验证命令输出

**验证：** 每条底稿结论必须有证据类型标记（原件/复印件/访谈记录/系统截图）

---

### Skill 5：复核三关（code-review 映射）

**触发条件：** 底稿完成 / 汇总完成 / 报告征求意见前

**Iron Law：**
```
未经三关且修正，不得进入下一阶段
```

| 关卡 | 角色 | 检查重点 | 工具 |
|:--|:--|:--|:--|
| 第一关 | 项目组互查 | 程序是否执行到位、证据是否充分 | 底稿模板检查表 |
| 第二关 | 部门经理复核 | 定性是否准确、金额是否核对 | AI 复核15维检查 |
| 第三关 | 质控终审 | 报告表述、法规引用、重大风险 | 三级复核清单 |

**HARD-GATE：** 上关未签通过，下关不得启动
**Anti-Pattern：** "时间紧先出报告，复核补签"

---

### Skill 6：多Agent协作（subagent-driven-development）

**触发条件：** 多业务线交叉 / 海量数据 / 需并行推进

**Iron Law：**
```
每个Agent必须有明确的任务边界和交接标准
```

**执行流程：**
1. 5坐标系坐标映射 → 确定哪些 Agent 参与
2. 每个 Agent 接收 H-packet（标准化任务交接包）
3. 并行执行，输出 Finding JSON
4. 疑点融合中枢（`issue_fusion.py`）—— 去重→冲突消解→证据链
5. 融合后再进入人工复核

**HARD-GATE：** 交接包中必须有 goal + confirmed_facts + 验收标准
**验证：** `handover_hook.py --debug` 自动检查 H-packet 完整性

---

### Skill 7：结论确认（approval-gate）

**触发条件：** 每项认定/每条问题/首页汇总数

**Iron Law：**
```
结论可追溯，归责有依据
```

**Checklist：**
1. 金额结论：显示计算过程而非仅最终数字
2. 违规定性：引用具体法规条款
3. 责任归属：区分主观故意/制度缺陷/不可抗力
4. 整改建议：可操作、可验证、有时限

**验证：** 每项结论附"依据来源"（法规编号/访谈日期/系统路径）

---

### Skill 8：复盘沉淀（retrospective）

**触发条件：** 项目结项后 / 连续同类项目发现同一问题

**Iron Law：**
```
不沉淀教训的项目不算完成
```

**Checklist：**
1. 记录实际用时 vs 计划用时偏差
2. 识别本次踩坑（程序/方法/沟通/工具）
3. 输出改进项到 `knowledge/lessons/`
4. 如果本次有AI辅助，记录 AI 的漏判/误判/亮点
5. 更新知识库和 RAG 索引

## 四、HARD-GATE 实现机制

每个 Skill 的 HARD-GATE 在代码层面实现为**可执行的验证函数**：

```
check_gate(skill_name, context) → {
    "passed": True/False,
    "blocked_by": ["未完成审前策划"],
    "evidence": ["方案文件不存在"],
    "suggested_action": "请先完成审前策划...",
}
```

审计平台调用流程：

```
用户请求 → 意图识别 → Gate检查 → 未通过→返回提示
                                         ↓ 通过
                            加载对应Skill → 执行Checklist
                                         ↓
                            每步执行后Gate验证
                                         ↓
                            全部通过 → 产出批准
```
