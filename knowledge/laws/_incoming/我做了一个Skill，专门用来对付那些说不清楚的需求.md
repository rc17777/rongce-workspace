# 我做了一个Skill，专门用来对付那些说不清楚的需求

之前做 ERP、各种业务系统的时候，我越来越强烈地感觉到一件事。
很多项目真正难的地方，不是开发。是开发前面那一步——需求根本没被说清楚。
业务同事可能会说：“能不能做一个样衣借出功能？”
或者说：“款式资料库这里能不能优化一下？”
再或者说：“我们想要一个报表，可以看到业务情况。”
听起来都挺正常的。但你真往下追，就会发现：这些话只是一个入口，不是一个需求。
比如“样衣借出”——谁借？从哪里借？借出后算不算库存减少？要不要审批？能不能跨部门、跨公司、跨国家借？逾期不还怎么办？损坏丢失谁负责？
不问清楚，开发很快就会陷入一种很尴尬的状态：
业务说，我要一个功能。
产品说，好的我画页面。
开发说，好的我做出来。
结果上线以后，大家发现：页面有了，按钮有了，字段也填了，但真正的业务问题没解决，甚至更麻烦了。
因为系统一旦做出来，大家就会默认它是正确的。
错的流程被固化了。模糊的规则被固化了。临时拍脑袋的字段被固化了。
后面再改，就变成返工、扯皮、补丁，以及补丁上的补丁。
所以我做了一个小 Skill，叫 demand-detective，中文可以叫「需求侦探」。
它不是用来直接帮你写 PRD 的。
更准确地说，它是用来在写 PRD 之前，把那些模糊的、一句话的、靠感觉讲出来的需求，先拆成一组可以确认的业务决策。
我觉得这个东西，比很多人意识到的更重要。二、它到底好在哪里
先把目标说清楚：它解决的不是“写需求”，而是“把需求问清楚”这件事。
绝大多数 AI 工具在这个环节做的事，是你说一句模糊的话，它直接帮你扩写成一篇很漂亮的“需求文档”。
结果就是：文档看起来专业了，但里头的核心问题一个都没被确认过。
这个 Skill 不一样。它有明确的设计立场：不要一上来就给出方案，先把问题摆到桌面上。2.1 它不问你“你想怎么做”，它给你选择题
这是我做这个 Skill 最核心的思路转变。
比如用户说：样衣要支持借出。
普通的做法可能是直接问：“你想怎么借？”
但这个问题其实很难回答。业务方也未必知道自己想怎么借。他的脑子里没有产品模型。
更好的方式，是给他选择题。
样衣借出要不要审批？
A，必须审批后才能出库。
好处：责任清晰，库存安全，适合样衣价值高、跨部门借用多的公司。
代价：流程会变慢，业务员临时拿样不够灵活。
B，业务员可以直接扫码借出。
好处：快，推广效率高。
代价：容易出现样衣丢失、逾期不还、责任不清的问题。
你看，这样一问，需求就不再是“做个借出功能”了。
它变成了一个业务选择。而且每个选择背后都有代价。
这就是这个 Skill 的核心工作方式：
少问开放问题，多给 A/B 决策题。
因为很多时候，业务方不是不愿意讲清楚，而是你直接问他要方案，他会懵。
但你把两种方案摆出来，把利弊讲清楚，他反而很容易判断：
“对，我们公司就应该这样。”
或者：“不对，我们不能这么做，因为我们业务员经常要临时拿样。”
这时候，真正的需求才浮出来。2.2 它的工作方式：三步把模糊需求拆成决策清单
这个 Skill 的工作流程，我刻意设计成了三个克制但非常实用的步骤。
第一步，先反讲场景。
不急着写方案，先用自己的话把业务故事复述一遍。
假设有一位业务员，在客户临时要看样的时候，需要快速找到并借出某件样衣。他最关心的是样衣能不能及时拿到，同时公司又希望这个过程有记录，避免丢失和责任不清。
这句话里，已经有了角色、场景、动作、目标和风险。
比单纯一句“做个样衣借出”清楚太多。
第二步，把不确定的地方变成决策题，而且按影响范围从大到小问。
它不会一上来就跟你讨论按钮放左边还是右边。
它会先问大的边界问题：
这个系统到底服务总部统一管理，还是服务各子公司各自管理？
款式资料是全公司共享，还是按区域隔离？
样衣是统一资产，还是各地仓库自己管理？
这些问题不先确认，后面讨论字段、按钮、提醒方式，其实都容易跑偏。
边界确认完，再往下拆流程：
借出要不要审批？归还要不要质检？逾期怎么处理？丢失损坏怎么追责？
再往下才是字段和页面：
借出时客户是否必填？预计归还日期是否必填？是否要扫码？是否允许批量借出？
最后才是体验和报表：
要不要逾期提醒？要看样衣周转率，还是款式推广次数？要不要热门款式排行？
这个顺序很关键。
因为很多需求讨论最大的问题，就是一上来就陷入细节。
大家花半小时讨论一个按钮的位置，但系统到底要不要支持跨公司借样，没人确认。这就很危险。
第三步，输出一个分级开发任务单。
不是把所有东西都写成“必须实现”，而是分成两块：
一块是核心确定区，已经确认的业务规则，开发必须严格实现。
另一块是假设验证区，当前还不完全确定，但为了推进项目，先按默认方案做，并且系统必须做成可配置、易修改。
这对实际项目特别有用。
因为真实世界里，很多需求不可能一开始就完全确定。
但你不能因为不确定就不做，也不能假装它已经确定了。
比较好的做法是：承认它是假设，然后把它设计成后续能调整的地方。
比如逾期提醒：
一开始默认“提前1天提醒、逾期当天提醒、逾期3天提醒主管”。
但这个规则未来很可能会变。那它就不应该写死在代码里，而应该做成配置。
这就是“需求侦探”想解决的问题。
它不是为了让需求文档看起来更专业。
而是为了减少那种最常见、也最痛苦的情况：
业务以为自己说清楚了。产品以为自己理解了。开发以为自己做完了。上线以后，所有人发现，大家理解的根本不是同一件事。三、它本质上是一个需求前置澄清工具
我觉得一个好的需求分析工具，最重要的价值不是生成一堆漂亮文档。
而是帮大家更早地吵清楚。
把那些迟早会爆炸的问题，提前摆出来：
这个字段到底谁用？
这个流程到底谁负责？
这个状态变化会不会影响库存？
这个权限开放以后有没有风险？
这个异常情况没人处理会怎样？
这些问题越早问，成本越低。越晚问，代价越高。
所以 demand-detective 这个 Skill，本质上就是逼着 AI 不要急着给方案。
先像侦探一样，把现场还原出来：
谁在什么场景下，遇到了什么问题，想完成什么动作，最怕什么后果。
然后一层一层把问题拆开：
哪些是业务边界。哪些是流程规则。哪些是字段校验。哪些只是体验优化。
最后再把这些决策沉淀成开发能看懂、业务能确认、测试能验证的任务单。四、它特别适合什么，以及它不做的事
我自己做这个 Skill 的感受是，它特别适合 ERP、CRM、PLM、进销存、审批流、报表系统 这种业务逻辑很重的场景。
因为这类系统最怕的不是页面不好看。
最怕的是规则没想清楚。
规则没想清楚，页面越多，坑越多。
它也有明确不接的活：
纯 UI 体验优化、不需要业务规则决策的需求，不是它该出场的场景。
能力边界比能力本身更能定义一个产品。
如果你也经常遇到那种一句话需求，比如：
“能不能做个报表？”
“帮我优化一下流程。”
“我们想要一个资料库。”
“这个地方加个审批吧。”
那这个 Skill 应该会挺有用。
它不会替你做业务决策。
但它会把那些必须决策的问题，一个一个拎出来，摆在你和业务方面前。
这就够了。
很多时候，需求不是写出来的。是问出来的。
如果你也经常被一句话需求折磨，希望它能帮你省掉那些被模糊需求导致自我内耗的时间。
