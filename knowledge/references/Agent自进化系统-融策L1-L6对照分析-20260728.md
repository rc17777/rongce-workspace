## 三、实施策略

文章推荐落地节奏：可观测→可评估→可修改(受限)→可决策。

融策v3.0已有L1基础+L2部分观测，采取**并行推进**策略：

| 阶段 | 周期 | 目标 | 优先实现 |
|:--|:--|:--|:--|
| Phase 1 | 本次 | L1+L2+L6 打底 | 自探查接口+信号提取器+治理边界 |
| Phase 2 | 本次 | L3+L4 接入 | 修改提案(受限)+独立评估 |
| Phase 3 | 本次 | L5 决策 | 规则引擎驱动 |

## 四、实施记录（2026-07-28）

### ✅ 新建模块：`audit-blackboard/self_evolve/`（7个文件，~3,200行）

| 文件 | 层 | 功能 | 行数 |
|:--|:--|:--|:--:|
| `boundary.yaml` | L6 | 4条禁止+4道卡门线+4级mutation level | 160 |
| `governance.py` | L6 | 治理边界强制执行(检查/审计/卡门线/强制执行) | 360 |
| `signal_extractor.py` | L2 | 失败/效率/能力缺口三类信号提取(项目级+全局级) | 310 |
| `eval_runner.py` | L4 | 独立评估(回归13用例+能力4+对抗4) | 400 |
| `mutation_proposer.py` | L3 | 受限修改提案(快照/diff/PR流程/回滚) | 280 |
| `decision_engine.py` | L5 | 8条决策规则+分级自动触发策略 | 270 |
| `engine.py` | L1-L6编排 | 统一入口(observe→decide→propose→validate→apply) | 310 |

### ✅ 首轮运行结果

```
L2观测 → 6个项目 → 14条信号（3效率+11能力缺口）
L5决策 → 15条决策（8条P1: 4个Agent零发现 + 7条P2: 7个Agent从未被调用）
        → 全部标记"需人工审核"（决策策略: 仅P0自动触发）
L6治理 → 4条禁止 + 4道卡门线 就位
```

**关键验证**: L6治理层正确拦截所有修改——agent不能改L4/L5/L6层，所有修改必须人类审批。这就是文章说的"边界本身就是系统稳定性的承重墙"。
