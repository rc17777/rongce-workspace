## 二、核心观点：落不了地的根源是"场景定义能力"缺失

**关键区分**：

- **场景清单**（政策视角）：告诉你"可以用在哪些方向"，是宏观地图
- **场景能力**（企业视角）：回答"在业务流程里具体卡在哪个环节、触发条件是什么、到什么程度交给人、出错谁兜底"

> "场景清单是全国旅游指南，场景能力是你家后院通往山顶的小路到底怎么走。"

---

## 三、三个根子问题

| 根子 | 说明 |
|------|------|
| **场景定义是业务能力，不是IT能力** | 智能体要解决的问题，答案在一线员工脑子里，不在SOP文档里。张江城管落地是因为执法队员深度参与场景设计 |
| **场景是活的，项目是死的** | 项目思维=立项开发上线验收没人管。但审批权限、组织架构、供应链都会变，"上个月定义好的智能体这个月可能不适用了" |
| **真正检验水平的是"例外"** | 场景清单写的是理想态。现实全是例外：紧急订单绕不过审批怎么办？数据口径对不上怎么办？没想清楚例外分级就上线=一遇例外就卡死→退回Excel |

## 四、四大落地障碍（自我加强的怪圈）

```
认知偏差(业务不参与) → 场景定义模糊 → 数据需求不清楚 → 数据不通没产出 → 业务更不想参与
```

| 障碍 | 表现 |
|------|------|
| 认知偏差 | "这是IT的事"——启动会坐了一圈IT，业务负责人缺席 |
| 场景空白 | 19个场景是行业级清单，不是企业级方案，缺一次"翻译" |
| 数据壁垒 | ERP/OA/CRM彼此不通，数据都不通就上智能体=修高速没匝道 |
| 人才断层 | 缺的不是算法工程师，是能拆解业务痛点+想好例外方案+懂数据逻辑+能跟技术对话的人 |

---

## 五、方法论：以"场景"为单元的四步落地路径

### 第一步：挑一个"小而痛"的场景，别贪大
- 找数据基础好、业务痛点明确、容错空间大的具体环节
- "宁可一个点打穿十米，不要十个点各挖半米"

### 第二步：让业务部门定义场景，不是IT
- 业务负责人先回答三个问题：
  1. 触发条件是什么？
  2. 处理到哪一步必须交给人？
  3. 产出结果怎么接回现有工作流？
- 答不上来就别动。顺序：业务定义在前，技术实现在后

### 第三步：先通数据，再上智能体
- 数据不通就先通数据。数据打通本身就有独立价值
- 数据不通就硬上=沙地上盖楼

### 第四步：让结果被看见，沿价值链往下推
- 第一个场景价值亮出来（效率提升/人工节省/错误率下降），用业务语言说
- 第一场景成功是后续所有场景的"路条"
- 然后沿价值链走：一个点→一条链→一个面（美的案例）
