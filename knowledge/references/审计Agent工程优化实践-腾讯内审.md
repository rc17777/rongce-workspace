# 审计中信息与数据分析场景的Agent工程优化实践

> 来源: 微信公众平台 | 微信公众号 | 抓取日期: 2026-08-01

---

·导语·

随着模型能力提升，Agent已经能独立完成不少检索和数据处理任务，但在复杂任务中，覆盖是否全面、判断是否准确、过程能否复现，以及需要多少时间和Token，很大程度上取决于模型的临场发挥。在审计场景中，我们不仅要求Agent“会做”，更要求它做到稳定高效、过程可追溯。

用工程优化让 Agent 稳定高效地完成任务

具体来说，通用Agent面对复杂任务时，往往临场决定查什么、怎么查、如何分析，甚至直接通读大量材料，或自行编写代码和SQL来处理数据。它每次的思考路径、处理顺序和停止条件都可能不同，一次成功不代表下次还能走通；面对大批量数据，又容易在反复阅读和重复调用中消耗大量时间与Token。
为此，我们没有把任务完全交给Agent自由发挥，也不只依赖若干现成工具，而是围绕具体场景，分别为其设计配套的工程体系、工具和处理链路。这类围绕模型搭建配套工作系统的做法正受到越来越多关注，业界通常把这套工作系统称为Agent Harness，把搭建它的工程实践称为Harness Engineering。这一概念目前尚无统一定义，本文采用一种较宽泛的理解：它是围绕模型形成的配套工作系统，不仅包括工具、数据接口、工程链路、上下文与记忆、状态记录、质量反馈和权限边界，也包括让审计师能够随时介入和确认的通道。

这套系统不是把审计判断全部交给Agent，而是重新安排审计师、Agent与工程链路之间的分工。审计师负责提出核查目标、确定必查范围和业务口径，并确认歧义事项、关键判断和最终结论；Agent负责理解任务、组织步骤、处理模糊问题，并根据中间结果动态调整；工程链路则负责批量、重复和规则明确的处理，保证过程稳定、可记录、可复用。
基于上述思路，本文从三个审计中场景场景展开：深度检索关注信息如何查全、查实，智能分类关注如何从海量材料中看清结构并统一归类，数据分析关注如何先形成可复用的数据理解，再持续开展可信分析。

01

信息
检索

从“搜到一些资料”到
“形成有依据的结论”

我们日常遇到的许多问题，都是需要多方查证的开放问题。为了形成相对完整的判断，需要从多个内外网信源获取信息，针对不同角度设计查询，持续记录新线索及其出处，并随着检索推进不断补充查证、相互印证。仅靠人工完成，较难同时兼顾覆盖范围、处理效率和过程留痕。
将这项任务交给通用Agent，确实可以减少审计师在不同平台间往返查询的时间，但“查得快”并不等于“查得全”。在检索广度上，Agent可能只选择部分渠道，遗漏项目要求查询的信源，或在拿到少量结果后便停止检索；也可能在反复改写查询中迟迟无法收敛。
同时，直接使用Agent还会带来新的控制问题：当检索结果存在空白时，模型可能依据自身知识补写看似合理、却没有真实来源支撑的内容；若不预先限定可用工具，Agent还可能临时编写爬虫，使用未经统一管理的方式获取信息。前者影响结论的可信度，后者则使信息来源、访问方式和过程留痕难以统一管理。
针对这些问题，我们把深度检索的工程控制集中在四个环节：

1｜生成查询

将笼统问题拆成多个查证角度。

2｜控制来源与访问方式

检查规定信源是否覆盖，并只允许通过已完成接入、获得相应访问授权且符合各自访问规范的受控工具或接口（如MCP工具或API）获取信息，不开放临时编写、运行爬虫的路径。

3｜迭代检索

根据每轮的信息缺口和新线索生成下一轮查询。

4｜控制收敛与证据

设置停止条件和轮次上限，只依据实际查到、能够回溯来源的材料组织答案。

这套机制一方面发挥Agent根据中间结果动态规划下一步的优势，使检索能够逐层扩展；另一方面也通过信源、访问、轮次和证据约束，降低漏查、无效发散以及无来源信息进入结论的风险。

在审计场景中，我们经常需要校验合作伙伴直接关联情况，而上述机制在多家企业关联网络核查中体现得较为直观。单一来源通常只能提供局部信息，初始查询中未必能掌握全部关联企业。工商信息可以反映股权结构、对外投资、分支机构、注册地址和经营范围等企业层面的关系；互联网公开信息可能补充企业官网、招投标公告、公开报道和业务合作等线索；内网已有的数据服务和历史核查结论，还可能提供此前已经验证过的信息。
系统首先将笼统的核查目标拆成若干个需要分别查证的子问题，例如投资与持股关系、注册地址或联系方式重合、共同参与项目、公开业务合作等。随后按照预先设定的来源范围，通过相应的受控工具或接口（MCP工具或API）执行检索：外网信源用于获取工商与互联网公开信息，内网知识平台用于查询内部知识和历史结论；对于项目中预先列为必查的内网信源，系统会设置覆盖检查，减少模型自行跳过某一渠道的可能。
每一轮检索完成后，系统不会立即写答案，而是同时检查信息缺口和新增线索。例如，首轮工商查询发现几家已知企业存在共同的企业股东，下一轮便可以围绕该企业股东的对外投资和股权链条继续查询，从中识别初始名单之外的关联企业；若公开信息进一步显示其中多家企业共同参与某个项目，后续查询又可以转向项目公告、合作企业和时间关系。检索范围因此不是在开始时一次性固定，而是由Agent根据每轮真实结果逐步扩展。
与此同时，循环设有停止条件和轮次上限。信息覆盖达到要求时及时收敛；达到轮次上限仍存在缺口时，则如实说明尚未查清的内容，而不是继续无限搜索，或用模型自身的知识补齐空白。在当前实现中，形成答案前还需要至少完成一次真实检索，关键结论也需要能够找到对应来源。
在技术实现上，我们进一步增加了工具与信源白名单、信源分组、并行查询、结果去重、全文深读和引用校验等能力。粗略搜索主要用于发现候选材料；进入结论的关键信息需要经过全文读取，并尽量绑定来源编号，方便审计师回到原文核对。
这套工程机制把深度检索从一次不可预测的搜索行为，组织成一套有目标、有反馈、有停止条件的研究过程：第一轮查什么由原始问题决定，后续查什么由信息缺口和新发现的线索共同决定，查哪里由来源规则约束，最终结论由真实材料支撑。

02

数据
探索

先看清全貌，
再完成逐条归类

审计师面对数万行报销事由、付款说明或合同条款时，通常需要先回答两个问题：这批数据大致由哪些类型构成？每条记录分别属于哪一类？前者帮助审计师快速了解数据全貌，后者则为后续统计和核查提供结构化基础。但人工逐条阅读和归类不仅耗时，还很难在大批量材料中始终保持统一口径；更现实的是，分类体系往往无法在开始前一次定义完整，审计师需要在逐步了解数据结构后再作调整。
大模型较长的上下文窗口，恰好为这类问题提供了新的解法：它可以在一次处理里阅读较多记录，快速归纳其中反复出现的业务特征，形成初步的分类思路。这正是Agent的价值所在——帮助审计师在海量材料中快速形成“这批数据可能有哪些类型、可以从哪些维度观察”的初步框架。
不过，这个思路真正落地时首先受到上下文窗口的限制。面对海量数据，很难一次完整放入模型；如果只截取其中一部分，又可能遗漏低频或边界类型。与此同时，原始数据本身往往包含大量重复、近似和模板化内容，也可能存在缺失、表述不完整等质量问题。如果不加处理地直接塞进提示词，不仅会挤占有限的上下文空间，还会稀释真正有区分度的信息，影响模型对分类维度和业务特征的判断。
因此，要把模型的归纳能力用于海量数据，还需要同时解决两个问题：先通过工程方法减少重复与噪声，把有限的上下文留给更有信息量的内容；再通过相对固定的工作流明确关键阶段和产出，避免分类维度、处理顺序和停止条件完全由Agent临场决定。基于这一思路，整个过程分为预打标、构建分类体系、全量分类三步。

（智能分类三步逻辑示意图，配图为作者使用AI生成）

Step1：预打标

Agent理解分类目标并触发工程链路。系统先将相似记录归组、抽取代表性样本，再批量生成候选维度和标签，并完成标准化与去重。这样既减少重复模型调用和Token消耗，也提高了大规模数据的处理效率。

Step2：构建分类体系

Agent根据代表性样本和候选标签形成分类体系，并结合覆盖率、集中度等指标提出补充维度、拆分或合并类别的建议。审计师主要在这一阶段确认分类维度、类别定义和适用边界，形成全量分类使用的统一标准。

Step3：全量分类

工程链路按照确认后的分类体系处理全量记录，低置信、未归类或存在冲突的记录再交给Agent复判。如果同类问题集中出现，则返回第二步调整分类体系，最终输出全量分类结果和分布统计。

这套方案的重点不在某一种算法，而在于分工与步骤串联：工程链路负责相似记录归组、抽样和批量分类，减少重复调用与Token消耗；Agent负责理解目标、归纳体系和处理不确定性；审计师确认分类口径和关键调整。分类结果还可结合金额、频次等信息补充重要性视角，并通过标准类别编号保持输出一致。

03

智能
问数

先理解数据，
再持续分析

结构化数据是审计证据的重要载体，无论来自Excel还是数据库表。围绕它开展的控制测试和实质性分析，通常都从同一件事开始：搞清楚这张表一行记录代表什么、每个字段是什么意思、几张表之间怎么对上；然后再按业务对象、时间范围和统计口径去筛选、汇总、比对。数据理解这一步如果出了偏差，后续分析结果就难以保证准确。
通用Agent并不具备一套体系化的数据理解能力。它获取数据理解的途径主要有三种：依赖用户提前维护的数据集知识库、在交互过程中由用户提供字段说明和口径定义，或者自己通过查看字段和样例进行临场探索。前两种需要持续投入人力维护，第三种则消耗大量Token把整份表反复读入上下文——无论哪种方式，都容易因为信息遗漏、口径不一致或探索不充分导致理解不够全面和准确，口径也难以在不同次分析中保持一致。
针对这个缺口，我们把数据理解前移，建立了一套结构化的数据理解底座及配套链路。一端通过相对固定的工程链路识别并沉淀数据结构、业务含义和关键口径，稳定形成可复用的数据理解档案；另一端让Agent在分析时自动获得必要的核心理解，并能按需查询更详细的信息。分析中确认的新关系、新口径和修正内容还会回写到底座，逐步形成“生成—使用—校正—再使用”的闭环。在这套底座之上，再分别支撑交互式分析和规则驱动的自动化分析。

（智能数据分析整体框架图，配图为作者使用AI生成）

数据理解底座的构建，主要由一条相对固定的工程化处理链路完成，而不是让通用Agent自由决定每一步。结构扫描、数据画像、语义识别、口径校验和结果沉淀按照明确顺序执行，每一步都有约定的输入和产出；工程链路先批量提取字段类型、分布、样本和关联候选等确定性事实，在需要语义判断的环节调用模型，结合场景知识理解业务对象、字段角色和统计口径。这样既能利用模型处理语义和模糊问题的能力，也能让海量数据按照相对一致、可控的方式完成理解。
数据理解的结果不会整份塞进每一次分析的上下文，而是分层保存和加载。表格粒度、主要业务对象、关键字段角色、核心表间关系和已确认口径构成“核心理解”，在后续分析开始时自动注入；完整字段画像、值分布、样本记录、数据质量细节、关联依据和历史修正记录则作为“详细证据”，由Agent遇到具体问题时按需查询。审计师可以按需调整字段含义和业务口径，分析交互中进一步确认的新关系、新口径和修正信息也会持续回写和优化数据理解档案，并在后续使用中优先于机器推断。只要数据结构和业务含义没有明显变化，系统便直接复用已有理解；只有发现结构变化、事实冲突或现有信息不足时，才重新进入对应环节。这样的分层既控制了上下文和Token消耗，也避免每次分析都从头探索数据。
有了这套可复用的数据理解之后，交互式分析和规则驱动的自动化分析便可以各自运行。前者由审计师主动提问，再由Agent工作流自动加载核心理解、按需查询详细证据，组织查询、调用工具并检查结果；后者由定时任务、数据更新或预设条件触发，通过工程链路批量执行已经沉淀的分析规则，再调用模型汇总异常、依据和必要说明，形成初步分析报告。两条路径触发方式和组织形态不同，但使用的是同一套经过持续校正的数据理解。
如果过程中发现数据口径不清、缺少必要字段或查询执行失败，系统不会勉强拼出答案，而是明确说明当前缺少什么信息，必要时请审计师确认；如果问题来自数据理解本身，则回到数据理解底座更新对应档案。这里的重点不只是提高SQL或脚本生成的成功率，更在于建立“理解可复用、执行有校验、无法确认不贸然出数”的边界。
这套工程设计把“能够生成查询”与“能够可信地开展数据分析”区分开来：工程链路负责数据理解和规则分析中的批量、确定性处理，Agent工作流负责组织用户发起的交互式分析，模型在需要语义理解、灵活判断和结果解释的环节发挥作用，审计师只在歧义口径和关键判断处介入。

·结语·

让 Agent 在清晰边界内稳定高效完成任务

文章分享三个场景虽然解决的问题不同，但背后采用的是同样的思路：从具体任务场景出发，先找出容易导致结果不稳定、质量偏差的环节，以及制约处理效率的瓶颈，再有针对性地配置工具、工程链路和人工确认机制。深度检索中的信源、迭代和证据控制，智能分类中的批量预处理、体系校验和人机确认，以及智能数据分析中的数据理解与持续复用，都是这一思路在不同任务中的具体应用。
这套方法并不是把Agent的每一步写死，而是根据工作性质进行分工：语义理解、模糊判断和动态调整交给模型与Agent工作流；批量、重复和规则明确的工作沉淀为工程链路；业务口径和关键判断保留给审计师，再通过明确的输入输出和反馈机制把各部分连接起来。
Harness原本有“马具、挽具”之意，带有连接、引导和约束的意味；但如果只看到约束，仍然过于狭窄。与其把Agent Harness理解为一套束缚Agent的“马具”，不如理解为围绕具体任务搭建的一套“外骨骼”：它不替审计师作出专业判断，而是把审计师、Agent和工程链路连接起来，既增强Agent的感知与执行能力，也让原本依赖临场发挥的任务运行在清晰、可控、可回溯的边界内。只有模型能力、工程机制和审计师判断相互配合，Agent才能从偶尔“做对”，走向持续“做好”。
