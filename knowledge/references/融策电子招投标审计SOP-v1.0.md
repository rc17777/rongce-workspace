# 融策电子招投标审计标准作业程序（SOP）

> 版本：v1.0 | 编制日期：2026-06-30 | 编制依据：融策L1-L11串标检测体系 +《投标文件元数据自查清单》（老友呢2026）
> 适用业务线：招投标审计（6号业务线）、政府采购审计（12号业务线）、工程竣工决算财务审计（10号业务线-招标合规部分）
> 更新记录：初始版本，集成攻防双视角

---

## 一、总则

### 1.1 编制逻辑

本SOP采用**"攻防倒置法"**构建：以投标人端5步合规自查清单为防御基准，反推审计端的6大检测阶段。投标人越是严格遵守自查清单，越不可能触发的异常信号——反过来说，这些信号就是串通投标的可靠指征。

核心原则：**"无法合理解释"是认定的前提。我们的任务不是替AI下判断，而是穷尽技术手段找到那些"客观上无法合理解释"的事实，并将其转化为审计证据。**

### 1.2 适用项目类型

| 项目类型 | 审计重点 | 适用检测阶段 |
|---------|---------|:--:|
| 单一项目招投标审计 | 本项目内多家投标人间串通 | 阶段一至五 |
| 跨项目串标分析 | 同一批投标人在多个项目中的规律性行为 | 阶段六（行为模式） |
| 政府采购监督检查 | 供应商围标串标、采购人/代理机构合谋 | 全部阶段 |
| 工程竣工决算-招标合规 | 招标程序合规性+投标人间串通 | 阶段一至四、六 |

### 1.3 审计目标

1. **发现**：识别投标人间可能存在的串通投标行为
2. **定性**：区分"异常一致"（需要解释）与"无法合理解释"（可以认定）
3. **取证**：形成可追溯、可核验的完整证据链
4. **报告**：输出符合行政监督和司法移送要求的审计发现

| 替代数据源 | 可信度 | 说明 |
|-----------|:--:|------|

| 向交易平台主管单位（发改委/公共资源交易中心）投诉 | ⭐⭐⭐⭐ | 行政手段施压 |

## 三、六阶段审计检测程序

### 阶段一：硬件指纹交叉比对 🔴 铁证级
> **对标**：投标人自查步骤一「硬件环境隔离」→ 凡是自查清单要求隔离的，就是审计必须检测的

#### 1.1 检测目标

判断不同投标人是否使用同一台物理设备制作投标文件。

#### 1.2 检测工具

| 工具 | 用途 | 命令/路径 |
|------|------|------|
| ExifTool | 提取文件元数据 | `exiftool -a -G1 投标文件.docx` |
| python-docx | 提取.docx core.xml | `from docx import Document` |
| Python zipfile | 解压.docx查看OLE元数据 | `zipfile.ZipFile()` |
| olefile | 读取.doc OLE2元数据 | `olefile.OleFileIO()` |

#### 1.3 检测项

| 检测项 | 来源文件 | 提取方法 | 判定标准 |
|-------|---------|---------|---------|
| **MAC地址** | .docx core.xml / OLE2流 | ExifTool或python-docx | 两个及以上投标人完全相同 → 🔴红色预警 |
| **CPU序列号** | 编制工具嵌入（部分文档格式） | ExifTool MakerNotes | 同上 |
| **硬盘序列号** | 编制工具嵌入（部分文档格式） | ExifTool MakerNotes | 同上 |
| **WPS版本GUID** | .docx `docProps/core.xml` AppVersion字段 | python-docx提取 | GUID后缀完全相同 → 🟡黄色预警（可能同版本巧合，需结合其他指标） |
| **Office版本字串** | .docx `docProps/app.xml` Application字段 | python-docx提取 | 版本号+内部build号完全一致 → 🟡黄色预警 |
| **计价软件加密锁序列号** | 🆕 计价软件输出文件 | 计价软件文件格式解析 | 同一加密锁 → 🔴红色预警 |

#### 1.4 判定规则

```
IF MAC地址相同 AND CPU序列号相同 AND 硬盘序列号相同:
    → 🔴 认定为"由同一台设备编制"（除非投标人提供独立设备采购证明+使用记录）
    
IF 仅MAC地址相同（其他硬件不同）:
    → 🟡 合理怀疑（需进一步核实是否为同一局域网/同一品牌网卡巧合）
    
IF WPS版本GUID完全相同 AND 至少一项其他指标异常:
    → 🟡 强化信号（同一安装源部署的多台设备）
    
IF 计价软件加密锁序列号相同:
    → 🔴 认定为"共用加密锁"（加密锁是物理设备，不存在巧合可能）
```

#### 1.5 操作流程

```
1. 将所有投标文件.docx解压（zipfile）
2. 提取每个文件的 docProps/core.xml
3. 从core.xml中提取：creator, lastModifiedBy, created, modified, AppVersion
4. 如有.doc格式：用olefile读取SummaryInformation流
5. 如有计价软件文件（.gcz/.gczj等）：解析加密锁信息
6. 生成硬件指纹交叉矩阵（N×N）
7. 标记所有匹配项 → 填入《检测结果汇总表》
```

### 阶段二：元数据残余交叉比对 🟠 强信号级
> **对标**：投标人自查步骤二「元数据深度清理」→ 凡是自查清单要求清除的字段，存在残留即是有价值的审计证据

#### 2.1 检测目标

判断不同投标文件的创建者、编辑者、编辑时间线是否存在不应有的关联。

#### 2.2 检测项

| 检测项 | 法律意义 | 异常判定 |
|-------|---------|---------|
| **作者/创建者账户名** | 同一人编制的直接证据 | 两个及以上投标人完全相同 → 🔴 |
| **最后保存者** | 同上 | 同上 |
| **公司名称** | Office注册时填写的组织名 | 显示为同一公司名 → 🔴 |
| **创建时间/修改时间线** | 编制协调行为的间接证据 | 多个文件的编辑时间在2小时内高度集中 → 🟡 |
| **编辑总时长** | 同上 | 多个文件编辑总时长高度一致（如都在30-40分钟） → 🟡 |
| **修订版本号** | 编制流程的间接证据 | 版本号序列规律一致 → 🟡 |
| **模板路径** | 使用了同一模板 | 路径一致且为非默认模板 → 🟡 |
| **字体库指纹** | 同一设备/同一安装源的间接证据 | 使用相同的非系统自带字体组合 → 🟡 |

#### 2.3 "清除行为本身"的检测 🆕

**关键洞察**：元数据被清除这件事，如果有统一的清除模式，本身就是一个信号。

| 检测项 | 检测方法 | 意义 |
|-------|---------|------|
| **字段全部为空且空值模式一致** | 检查所有投标文件的core.xml中creator/lastModifiedBy/company字段是否同步为空 | 个人通常不会逐项清除元数据，多份标书同步为空 → 可能是同一人/同一指令批量清除 |
| **ExifTool清除痕迹** | 检查PDF元数据中是否有ExifTool的特征残留 | 多份标书被同一工具批量处理 → 🟡 |
| **Office文档检查器清除痕迹** | 检查.docx内部XML中是否有文档检查器的特征标记 | 同上 |

#### 2.4 操作流程

```
1. 提取所有投标文件的完整元数据字段（见阶段一1.5）
2. 构建元数据交叉矩阵
3. 特别关注：
   a) 作者/创建者为真实人名的 → 直接比对
   b) 字段为空白的 → 检查是否多份文件同步空白（清除行为信号）
   c) 创建/修改时间 → 计算所有投标人的编辑时间线并行度
4. 标记异常 → 填入《检测结果汇总表》
5. 注意：.doc格式的SummaryInformation经常为空（WPS不写入），空值在此情况下不应作为信号
```

### 阶段三：文本内容雷同检测 🟠 强信号级
> **对标**：投标人自查步骤三「内容差异化审查」→ 凡是自查清单要求差异化的，雷同就是异常

#### 3.1 检测目标

判断不同投标文件是否存在不应有的文本雷同。

#### 3.2 检测方法

| 方法 | 适用对象 | 阈值 | 工具 |
|------|---------|------|------|
| **TF-IDF全文余弦相似度** | 技术标/商务标全文 | ≥80% 高度可疑 / ≥90% 基本认定 | `procurement-audit-models/03_tfidf_similarity.py` |
| **连续字串匹配** | 全文 | 连续20-30字以上完全相同 → 标记  | Python difflib / SequenceMatcher |
| **异常一致错误** | 全文 | 发现2处及以上相同错别字/错误数据 → 🔴 | 双人交叉盲审 |
| **段落级匹对** | 全文分段 | 特定段落高度相似但其他段落完全不同 → "分工协作"信号 | Python + 段落拆分 |
| **规范引用裸复制** | 技术标 | 连续引用国标/行标条文超过50字且无项目化解读 → 🟡 | 人工复核 |

#### 3.3 TF-IDF操作流程

```
1. 预处理：提取所有.docx的纯文本
2. 去除招标文件要求的模板化文本（承诺函、声明书等公告格式）
3. 去停用词，分词处理
4. TF-IDF向量化 → 计算所有文件对的余弦相似度
5. 生成N×N相似度热力图
6. 标记≥80%的文件对 → 人工复核内容
7. 特别检查：技术方案的核心计算数据是否雷同（数字雷同比文字雷同更有力）
```

#### 3.4 规范引用检测规则

| 场景 | 判定 | 理由 |
|------|:--:|------|
| 两家均引用同一国标条文，但各自加了项目化解读 | ✅ 正常 | 标准条文表述固定，有解读说明独立编制 |
| 两家引用同一国标条文，均未加任何解读，且条文选择完全一致 | 🟡 存疑 | 选择哪些条文引用本身是独立判断，高度一致不合理 |
| 三家中至少两家在同一处出现同样的规范性文件编号错误 | 🔴 高危 | 错误不应具有趋同性 |

#### 3.5 AI工具指纹检测 🆕

```
检测项：
1. 检查文本中是否有AI工具的特征输出模式（如特定格式标记、温度参数留下的痕迹）
2. 检查技术方案中是否存在伪数据（AI生成的"示例数据"而非真实计算数据）
3. 检查多处是否出现相同的AI"幻觉"（虚构的规范条文号、不存在的地名）

判定：
- 多份标书出现相同的AI特征痕迹 → 🟡 可能使用同一AI工具（需结合其他指标）
- 多份标书出现相同的虚构内容 → 🔴 同一模板/同一AI session输出的强信号
```

### 阶段四：图片与资源哈希检测 🟠 强信号级

#### 4.1 检测目标

判断不同投标文件是否使用了完全相同的嵌入图片（资质证书扫描件、盖章页、现场照片、设备图片等）。

#### 4.2 检测方法

```
1. 将所有投标.docx文件解压为ZIP
2. 提取 word/media/ 目录下所有图片
3. 计算每张图片的MD5和SHA1哈希值
4. 构建图片哈希交叉矩阵（N家公司 × M张图片）
5. 标记哈希完全相同的图片对
```

#### 4.3 判定标准

| 发现 | 判定 |
|------|:--:|
| 不同投标人的资质证书扫描件MD5完全相同 | 🔴 使用同一份扫描件 → 同一单位编制 |
| 不同投标人的盖章页图片MD5完全相同 | 🔴 印章不应跨公司复制 |
| 不同投标人的设备图片/现场照片MD5相同 | 🔴 同上 |
| 仅招标文件要求的统一格式图表MD5相同 | ✅ 正常（可能是招标文件提供的模板） |

#### 4.4 EXIF信息检测 🆕

从图片EXIF中提取：
- Make/Model：相机/扫描仪型号
- GPS坐标：拍摄地点
- DateTimeOriginal：拍摄时间
- Software：编辑软件

**判定**：不同投标人的照片显示同一相机型号 + 同一时间段拍摄 → 🟡 可能是同一人在同一场景拍摄。

### 阶段五：网络指纹与上传行为分析 🟡 辅助信号级
> **对标**：投标人自查步骤四「上传环境管控」→ 凡是自查清单要求隔离网络环境/错峰的，同步行为就是异常

#### 5.1 检测项

| 检测项 | 数据源 | 异常判定 |
|-------|------|---------|
| **上传公网IP地址** | 交易平台日志 | 两个及以上投标人IP完全相同 → 🟡 |
| **上传时段集中度** | 交易平台日志 | 多人在截止前1小时内集中上传 → 🟡 |
| **上传时间差规律性** 🆕 | 交易平台日志 | 多份标书上传间隔恰好都>2小时（错峰策略痕迹） → 🟡 |
| **浏览器User-Agent** 🆕 | 交易平台日志 | 多个投标人使用完全相同的浏览器版本 → 🟡 |
| **浏览器指纹一致性** 🆕 | 交易平台日志（如有） | 多个投标人浏览器指纹完全一致 → 🔴 |

#### 5.2 网络环境合理性的判断框架

| IP相同的情况 | 可合理解释？ | 审计判断 |
|-------------|:--:|------|
| 同产业园区/众创空间内不同公司 | 可能需要解释 | 要求提供独立办公场所证明+网络拓扑图 |
| 同一写字楼不同楼层不同公司 | 可能需要解释 | 询问是否共用宽带出口 |
| 完全不同的注册地址 | ❌ 无法解释 | 涉嫌协调上传 |
| 同一家庭宽带IP下多个"不同公司" | ❌ 几乎无法解释 | 高度怀疑实际控制人为同一人 |
| 移动4G/5G热点IP相同 | 较难解释 | 移动网络IP池虽共享但概率极低 |

### 阶段六：行为模式与制度评测 🟡 背景级
> **对标**：投标人自查步骤五「数字卫生常态化机制」→ 没有制度建设的投标主体，串标风险系统性偏高

#### 6.1 跨项目行为模式分析

| 分析维度 | 方法 | 信号意义 |
|---------|------|---------|
| **同批次投标人重复出现** | 统计同一组投标人在多个项目中的共现频率 | 3个项目以上共现 → 🟡 |
| **报价排名规律** | 统计各投标人在多个项目中的报价排名分布 | 某投标人永远是第二名且分差固定 → 🔴 |
| **中标轮换模式** | 统计同一组投标人是否轮流中标 | 明显的轮流坐庄 → 🔴 |
| **项目类型聚集** | 分析同一组投标人的投标项目类型 | 仅在同一类型项目中抱团 → 🟡 |

#### 6.2 投标人制度评测（现场审计阶段用）

对被审计单位的投标管理制度进行评测，重点检查：

| 评测项 | 检查方法 | 缺失信号 |
|-------|---------|---------|
| 有无投标专用设备台账 | 查阅设备管理记录 | 无 → 设备交叉使用风险不受控 |
| 有无元数据清理SOP | 查阅内部制度文件 | 无 → 元数据泄露风险不受控 |
| 有无关联企业投标隔离制度 | 查阅与关联企业的协议 | 无 → 母子公司同时投标风险 |
| 有无投标文件版本管理 | 查阅文件归档 | 无 → 无法追溯编制过程 |

## 四、证据标准与认定规则

### 4.1 信号等级体系

| 等级 | 名称 | 定义 | 单层能否定案 |
|:--:|------|------|:--:|
| 🔴 | 铁证级 | 物理事实，无法通过解释消除 | ✅ 可以（如三硬件完全相同、加密锁相同） |
| 🟠 | 强信号级 | 高度异常，需要有力解释 | ❌ 需2个以上强信号叠加 |
| 🟡 | 辅助信号级 | 存在异常但可能有合理的技术解释 | ❌ 需结合更强信号 |
| 🟢 | 背景级 | 系统性风险评估，不单独使用 | ❌ 仅作为背景参考 |

### 4.2 多信号叠加认定规则

```
🔴 铁证级（任一项） → 直接认定为"同一单位编制"
🟠+🟠 两项强信号叠加 → 认定为"异常一致"
🟠+🟡 一强+两辅助 → 认定为"涉嫌串通投标"
🟡+🟡+🟡 三项辅助信号叠加 → 合理怀疑，需进一步调查
仅🟡 单项辅助信号 → 不构成认定，记录为观察项
```

### 4.3 证据链完整性检查

每项认定必须满足：

- [ ] 技术检测有可复现的脚本和原始数据
- [ ] 异常判定有明确的法规依据（注明法条）
- [ ] 已考虑并排除合理的技术解释
- [ ] 相关证据已截图/导出/存档（含时间戳和哈希）
- [ ] 关键证据已由双人交叉验证

### 4.4 不得认定为串标的情形

1. 仅单一辅助信号（如仅IP地址相同），有合理技术解释
2. 规范条文的正常引用（不含异常一致错误）
3. 招标文件提供的统一格式模板相同
4. 同一办公设备供应商安装的软件版本一致（需有其他独立证据排除串标可能）

## 六、审计报告撰写指引

### 6.1 串标发现的报告结构

```
发现标题：[投标人A]与[投标人B]涉嫌相互串通投标

一、事实陈述
1. 项目基本情况（项目名称、编号、招标人、代理机构、投标人数量、中标情况）
2. 检测过程和发现的技术事实（逐项陈述，配数据）

二、判定依据
1. 技术层面：[列明具体检测结果，如"MAC/CPU/硬盘序列号三者完全相同"]
2. 法律层面：《招标投标法实施条例》第四十条第（X）项
3. 行业标准层面：引用适用的省级雷同认定细则（如黔发改法规〔2024〕296号）

三、问题定性
[明确认定为"涉嫌相互串通投标"还是"存在串通投标嫌疑需进一步调查"]

四、已排除的合理怀疑
[列举考虑过但可以排除的合理解释，如"非同一办公场所共用网络，因注册地址不同"]

五、证据清单
[列明所有支撑证据的文件名、哈希值、存档位置]
```

### 6.2 关键表述规范

| ❌ 不规范的表述 | ✅ 规范表述 | 理由 |
|---------------|-----------|------|
| "AI检测发现串标" | "经技术检测，两份投标文件的硬件序列号完全相同" | 工具不是主体，检测事实才是 |
| "肯定是同一人做的" | "依据《条例》第四十条第（一）项，该情形可视为由同一单位编制" | 用法律语言而非日常推断 |
| "三家公司围标" | "投标人A、B、C的投标文件存在[具体事实]，涉嫌相互串通投标" | 正式术语是"串通投标"，且应表述为"涉嫌" |
