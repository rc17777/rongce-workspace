# 两篇AI Agent文章深度分析

> 分析日期：2026-07-28 | 分析人：融策右护卫

## 文章一：AgentSpace — 把Agent当员工管

**来源**：微信公众号（审天审地审空气）  
**项目**：HKUDS/AgentSpace（港大数据智能实验室）  
**定位**：团队级Agent共享工作空间  
**协议**：Apache-2.0 | 864星 | TypeScript

### 核心思路

AgentSpace 解决的不是"Agent怎么更强"，而是"一个团队怎么把十个Agent当同事用，还不至于失控"。

它把Agent从"某人终端里的一个进程"升级为**组织资源**：
- 有职务、有负责人、有技能和知识
- 能借给同事、动敏感的东西要人批
- 每一步留痕

### 六大设计要点

| 设计 | 说明 | 审计启示 |
|:--|:--|:--|
| **数字员工档案** | 每个Agent带一份档案：职务、负责人、技能、知识页、执行环境、就绪状态 | 相当于Agent的"执业资格证"，可追溯 |
| **六个执行环境** | 同一份档案可落到Claude Code/Codex CLI/OpenClaw等6个引擎 | 执行层可换，身份不变——类似审计人员换工具不换方法论 |
| **人工审批闸门** | 工具调用、文档访问、往外发东西、动预算→路由进人工审批 | 高风险动作必须有人确认，和审计的"三级复核"异曲同工 |
| **统一控制面** | 角色、频道、授权、daemon token、文档角色→一处管理 | 权限集中管控，避免"谁都能干啥"的混乱 |
| **OpenAgent名片** | Agent可导出签名名片，默认脱敏，显式加参数才带敏感信息 | 对外共享时的安全边界设计 |
| **飞书集成** | 在飞书会话里调AgentSpace的Agent，治理留在AgentSpace | 企业IM+Agent的融合模式 |

### 深层判断：AgentSpace改变的是“控制平面”

AgentSpace的价值不在于让单个Agent变聪明，而在于把原来散落在终端、聊天记录和个人配置中的控制信息集中起来。它实际上拆出了四个层次：

1. **身份层**：Agent是谁、由谁负责、具备什么能力；
2. **调度层**：任务交给哪个执行环境、哪台机器、哪种模型；
3. **授权层**：能访问哪些文档、工具和频道，什么动作需要审批；
4. **审计层**：谁发起、谁批准、Agent做了什么、产出了什么。

这四层如果混在一起，系统就会出现三个典型问题：换模型等于换身份、权限跟着CLI账号漂移、出了问题无法重建责任链。AgentSpace试图把它们分离，这是企业级Agent治理的正确方向。

但“数字员工”只是一个管理隐喻，不等于真正完成了组织治理。真正需要验证的是：权限是否能在工具层强制执行，审批是否不可绕过，日志是否包含足够的输入、输出、版本和凭证信息，多个Agent之间是否有真实的隔离。文章已明确提到沙箱和存储隔离仍在计划中，因此目前更适合作为治理架构参考，不宜直接视为生产级安全边界。

### 证据边界与潜在风险

- 项目较新，星标数量只能证明关注度，不能证明稳定性、性能或安全性。
- 多执行器统一契约很有价值，但上游CLI的登录态、工具语义、错误码和版本变化会造成适配成本。
- “审批”如果只是界面上的确认，而不是服务端对工具调用的硬拦截，就只是流程提示，不是控制措施。
- “留痕”如果没有保存任务快照、Agent版本、Skill版本、模型版本和审批依据，事后仍然无法复核。
- 共享工作空间会扩大数据泄露半径。审计资料尤其需要项目级、角色级、字段级隔离，不能只靠Agent名称区分权限。

### 对融策的启示

1. **Agent身份管理**：在现有`agent_registry.json`中增加负责人、适用业务线、输入数据范围、禁止事项、输出责任人、版本和有效期。
2. **审批闸门**：把对外发送、金额结论、法规定性、责任归因、删除或覆盖原始证据列为强制人工确认事项，并由服务端拦截。
3. **可重放留痕**：现有H-packet之外，保存任务输入摘要、数据指纹、Agent/Skill/模型版本、工具调用、审批记录和最终输出。
4. **权限最小化**：按项目目录和数据类别分配访问权，原始证据只读，派生结果与原始资料分离。

**结论**：AgentSpace最值得融策借鉴的是“身份、授权、执行、责任分离”，不是它的界面或技术栈。

## 文章二：EvoMap — Agent经验传递与蜂群协作

**来源**：微信公众号（审天审地审空气）  
**项目**：EvoMap/EvoX  
**核心人物**：张昊阳  
**论文**：arxiv.org/abs/2604.15097

### 核心问题

> 现在的大模型能力越来越强，但每个新启动的Agent都是全新的。Agent踩坑学到的经验，怎么传给其他Agent？

**Skill的局限**：Skill是人提前编写好的操作手册，不能解决"Agent在实际工作中刚学到的经验怎么快速传递"。

### EvoMap的解法：经验即基因

把Agent运行中学到的有效经验提炼成"基因"（Gene）：
1. Agent找到解决办法 → 提炼出来 → 验证 → 上传到网络
2. 其他Agent遇到类似问题 → 直接继承经验 → 不用从头摸索

**核心判断**：AI的经验，也可以成为一种能够流通的资产。

### 蜂群实验：同一模型从26%到71%

**实验设计**：563道题（逻辑/数学/物理），全部用Claude Haiku 4.5

| 方式 | 正确率 | 说明 |
|:--|:--:|:--|
| 单Agent | 26.29% | 一个Agent处理全部题目 |
| Sub-Agent模式 | 38.54% | 主Agent拆解分配，Sub-Agent执行，主Agent汇总 |
| EvoX蜂群 | **70.69%** | 原子任务拆分，独立上下文，程序直接收集答案 |

**关键发现**：
- 蜂群核心不在于数量，而在于**任务怎么拆、执行怎么隔离、结果怎么汇合**
- Sub-Agent模式里，373道题中间答对了，但最终只交付217道——**正确答案保留率仅55.5%**
- 失败不在执行阶段，而在**信息传递和结果汇总**

### 三个关键设计

| 设计 | 说明 | 审计启示 |
|:--|:--|:--|
| **原子任务拆分** | 每个Agent只处理一个边界清楚的问题 | 审计疑点拆分到最小可验证单元 |
| **独立上下文** | 每个Agent只看到自己负责的部分，不用记住全局 | 避免上下文污染，降低幻觉风险 |
| **程序收集结果** | Agent负责推理，程序负责合并——不让大模型二次加工 | 确定性环节用代码，模糊环节用AI |

### 自组织实验

24个配置完全相同的Agent，没有预设角色：
- 每处理一道题→总结经验→记录到Memory（Gene）
- 8轮后→原本相同的Agent开始有不同经历和专业侧重
- 选择伙伴时→看到关系信息→找熟人；看到能力信息→找更合适的

**结论**：Agent的组织方式受**可见信息**影响。系统展示什么信息、奖励什么行为，就形成什么样的组织。

### 深层判断：EvoMap改变的是“学习平面”和“协作平面”

EvoMap文章实际上提出了三个不同层次的问题，不能混成一个“蜂群更强”的结论：

1. **经验层**：一次任务中发现的有效做法，能否被验证、封装、检索和复用；
2. **协作层**：多个Agent如何拆任务、隔离上下文、传递结果；
3. **组织层**：Agent能否根据能力、信用、成本和历史表现形成动态分工。

其中，第一层是Gene机制，第二层是EvoX实验，第三层是自组织实验。文章最有说服力的是第二层，因为它给出了对照实验和中间损耗数据；第一层和第三层仍主要是研究设想或早期验证，不能直接推导出“Agent会自动进化”或“蜂群必然优于中心调度”。

### 如何正确理解26%到71%

这个结果的重要意义是：**系统架构可能比单纯更换模型更能决定任务表现**。但它不是普遍规律，至少有几个条件：

- 任务可以拆成相互独立、边界清楚的原子任务；
- 每个子任务可以用固定编号映射到固定输出位置；
- 结果合并不需要复杂的全局推理；
- 评价标准是明确的、可自动核验的；
- 并行带来的成本和调度开销可以接受。

在审计项目中，数据核对、重复性异常检测、合同字段提取、金额勾稽等任务比较接近这种结构；但法规适用、责任定性、问题重要性判断和整改建议，通常需要跨证据、跨时间、跨业务的综合判断，不能简单按题号拆开后直接拼接。

因此，不能把“蜂群模式”照搬为所有审计任务的默认架构。更准确的原则是：**可验证、可隔离、可编号的任务用并行原子Agent；需要全局判断的任务保留受控的综合复核层。**

### 信息损耗是多Agent系统的核心风险

Sub-Agent中间答对373道，最后只保留217道，说明总失败率不能只看Agent的单次准确率，还要拆成链路指标：

`最终正确率 = 执行正确率 × 结果保留率 × 汇总正确率`

在工程实现中至少应分别统计：

- 任务完成率：是否按时产生结果；
- 局部正确率：单个Agent的结论是否正确；
- 传递保真率：结构化结果是否完整到达；
- 汇总保留率：正确结果是否被最终交付；
- 冲突处理准确率：矛盾结果是否被正确标记和解决；
- 成本效率：每个有效结论消耗多少Token、时间和人工复核资源。

这对融策现有H-packet体系尤其重要：交接包不能只传一段自然语言摘要，还应传结构化事实、证据定位、计算过程、置信度、未决事项和禁止推断项。

### Gene机制的真正难点：不是生成，而是认证

“经验即资产”方向正确，但未经验证的经验传播会把偶然成功、错误归因甚至模型幻觉扩散到整个系统。审计场景不能把Agent自己总结的内容直接写入知识库，至少要经过：

1. **经验提取**：记录问题、环境、失败尝试、最终解法和适用条件；
2. **脱敏处理**：去除项目名称、企业名称、身份证号、账号、未公开金额等敏感信息；
3. **独立复现**：在同类数据或模拟数据上重复验证；
4. **人工确认**：由业务骨干确认法规适用、定性和边界；
5. **版本管理**：记录来源项目、验证日期、适用版本和失效条件；
6. **效果追踪**：上线后统计命中率、误报率、采纳率和负面案例。

所以融策应建设的是“审计经验单元”，而不是无门槛的Gene市场。经验单元可以包含：触发条件、适用范围、核查步骤、所需证据、反例、输出模板和验证记录。

### 自组织的边界

Agent根据历史正确率和专业侧重选择伙伴，说明信息设计会塑造组织行为。但这不是无条件的智能涌现：如果历史正确率存在样本偏差，系统就会过度偏好早期高分Agent；如果只奖励结论命中率，Agent可能回避困难任务；如果没有成本和失败惩罚，网络会形成少数枢纽过载。

因此，自组织系统必须配套：能力评分的样本量门槛、时间衰减、任务难度校正、成本指标、负面反馈、负载上限和人工干预。对融策而言，当前不宜直接开放自主认领生产审计任务，先在脱敏历史案例上做离线模拟。

## 三、两篇文章的共同命题：Agent系统的瓶颈正在从“智力”转向“组织”

两篇文章表面上一个讲治理、一个讲蜂群，底层其实在回答同一个问题：当单个模型已经具备足够的执行能力后，系统的上限不再只由模型参数决定，而由以下四个组织变量决定：

1. **任务边界**：任务是否拆到了可验证的粒度；
2. **上下文边界**：每个Agent看到了什么、没有看到什么；
3. **权责边界**：谁可以调用工具、修改资料、做出最终结论；
4. **结果边界**：什么由模型判断，什么由程序校验和合并。

AgentSpace主要解决第三项，兼顾第二项；EvoMap主要解决第一、二、四项，并进一步探索动态分工。二者合起来，可以形成一个比“多Agent编排”更完整的架构：

`治理控制平面 → 任务分解平面 → Agent执行平面 → 结构化结果平面 → 证据与经验平面`

这也是对融策现有平台的一个重要修正：现在的平台已经有Agent注册、路由、黑板和H-packet，但还需要把“权限治理”和“结果保真”提升为与任务编排同等重要的基础能力。

## 四、对融策AI审计中台的具体映射

| 文章提出的能力 | 融策现有组件 | 现状判断 | 应补的能力 |
|:--|:--|:--|:--|
| Agent档案与负责人 | `agent_registry.json` | 有注册，组织治理不足 | 负责人、版本、权限、有效期、适用业务线 |
| 任务路由 | `agent_router.py` | 已有关键词和业务线路由 | 增加数据类型、风险等级、历史表现和成本 |
| 并行执行 | `orchestrate_v3.py` | 已有5坐标系并行 | 原子任务模板、依赖关系、超时和重试 |
| 状态交接 | `handover_protocol.py` | 已有H-packet | 增加证据定位、计算依据、禁止推断、数据指纹 |
| 疑点融合 | `issue_fusion.py` | 有融合、去重、冲突消解 | 保留原始发现，禁止融合过程覆盖证据 |
| 规则调试 | `agent_debug_rules.py` | 已有确定性规则 | 增加结果保留率、交接丢失率、重复率指标 |
| 经验沉淀 | 知识库/RAG | 主要按文档入库 | 建立经验证的审计经验单元，不直接收录裸输出 |
| 人工确认 | 目前依赖流程约定 | 缺统一闸门 | 对金额、法规、定性、责任、对外表述强制审批 |

## 五、建议的最小验证项目

不建议马上重做整个多Agent平台，也不建议直接引入完整自组织蜂群。可以用一个小型离线实验验证文章中的关键判断。

### 实验A：验证“程序合并是否优于模型汇总”

- 样本：10份已完成的绩效评价报告；
- 任务：从每份报告中抽取问题、金额、法规依据、整改建议；
- 对照组：多个Agent输出后交给主Agent汇总；
- 实验组：多个Agent输出结构化JSON，由程序按项目、问题编号直接合并；
- 指标：问题保留率、金额保留率、法规引用保留率、重复率、人工修订时间。

通过标准可暂定为：实验组重大问题漏失为0，关键金额保留率100%，人工合并时间下降30%以上。

### 实验B：验证“经验单元能否跨项目复用”

- 从3个历史项目中提取20条经过人工确认的经验单元；
- 在另外5个项目上分别测试“无经验库”和“调用经验库”；
- 记录命中率、误报率、人工采纳率、节省时间和不适用案例；
- 对每条经验标注适用条件和失效条件，防止经验被过度泛化。

### 实验C：验证“自组织是否值得引入”

先不让Agent自主处理真实项目，只做离线路由模拟：

- 给Agent提供不同的历史能力、成本、响应速度和负载信息；
- 比较固定路由、按历史表现路由、按综合评分路由三种方案；
- 检查是否出现枢纽过载、能力垄断、困难任务逃避和早期偏差放大；
- 只有当动态路由在准确率、成本和稳定性上同时改善，才进入受控试运行。

## 六、最终判断

1. **AgentSpace的现实价值高于其技术新颖性**：它把Agent纳入组织治理，这正是企业真正落地时绕不开的基础设施问题。
2. **EvoMap的工程发现比“蜂群”概念更重要**：原子任务、独立上下文、结构化输出和程序合并，是可以立即验证的工程原则；自组织和基因传播仍需严格实验。
3. **26%到71%不能简单宣传为普遍提升**：它证明架构设计可能产生巨大收益，但收益依赖任务可拆分性、评价可计算性和结果可直接合并等条件。
4. **审计场景必须把“经验传播”放在“经验认证”之后**：错误经验一旦进入知识库，传播效率越高，风险扩散越快。
5. **融策的优先顺序应是：先治理，再保真，后进化**：先建立Agent责任、权限和审批；再降低交接和汇总损耗；最后才探索经验自动传播与自组织。

## 两篇文章的对比

| 维度 | AgentSpace | EvoMap |
|:--|:--|:--|
| **解决什么问题** | 团队怎么管理多个Agent | Agent经验怎么传递和协作 |
| **核心隐喻** | Agent=员工（人事制度） | Agent=蜂群（生物进化） |
| **组织方式** | 中心化管控（档案/审批/留痕） | 去中心化自组织（Gene/蜂群/自选择） |
| **适用场景** | 企业日常运转、合规要求高 | 复杂任务拆解、大规模并行 |
| **成熟度** | 产品可用（864星），隔离未完成 | 实验阶段，结论需继续验证 |
| **对融策价值** | 短期可借鉴（Agent管理/审批/留痕） | 长期可探索（经验沉淀/蜂群协作） |

## 融策行动建议

### 短期（1-3个月）
1. **借鉴AgentSpace的Agent档案设计**：给22个Agent增加"负责人""技能清单""借用记录"字段
2. **增加审批闸门**：高风险动作（对外发送/金额调整）系统化审批流
3. **细化留痕**：H-packet传递增加更细粒度的操作日志

### 中期（3-6个月）
4. **建立审计经验库（Gene机制）**：每个项目结束后，提炼关键经验→验证→入库→跨项目复用
5. **优化任务拆分**：把大任务拆成更原子的子任务，每个Agent只做一个边界清楚的小任务
6. **程序收集结果**：汇总阶段减少AI二次加工，确定性环节用代码

### 长期（6-12个月）
7. **探索自组织**：让Agent在执行中发现擅长方向，逐渐形成稳定分工
8. **经验即资产**：把审计经验产品化，未来甚至可以对外输出

## 一句话总结

> AgentSpace解决"怎么管"，EvoMap解决"怎么进化"。  
> 对融策而言：**短期学AgentSpace的管控，长期学EvoMap的进化。**
