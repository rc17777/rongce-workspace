# 从案例到审计规则的提炼流程

## 一、目标

把 Obsidian/资料库/历史底稿/公开案例中的已验证问题，转化为高质量审计规则。

不是摘关键词，而是抽取：

```text
问题为什么成立
需要哪些资料
用什么特征能提前发现
怎么核实
什么证据能进底稿
报告怎么写
```

## 二、适用来源

| 来源 | 价值 | 注意事项 |
|---|---|---|
| 历史审计底稿 | 最高，已经形成证据链 | 必须脱敏 |
| 已出具审计报告 | 高，能提炼报告表述 | 注意问题事实和定性依据 |
| Obsidian 案例库 | 高，覆盖面广 | 需判断案例是否真实可验证 |
| 审计署/地方公开案例 | 高，权威性强 | 注意地区政策差异 |
| 政策法规 | 中，需要转成可执行规则 | 不能直接把法规全文当规则 |
| 项目复盘记录 | 高，能优化误报和漏报 | 需要持续维护 |

## 三、提炼步骤

### Step 1：筛选案例

优先选择满足以下条件的案例：

1. 问题事实清楚。
2. 涉及资料明确。
3. 证据链完整。
4. 能映射到五个模块之一。
5. 问题具有复用价值，不是极端个案。

### Step 2：标注案例元数据

每个案例先标注：

| 字段 | 说明 |
|---|---|
| 案例来源 | Obsidian 文件名/底稿编号/报告名称/法规名称 |
| 审计类型 | 经责、预算执行、工程、采购、补贴、绩效等 |
| 业务领域 | 资金、合同、人员、采购、资产、项目等 |
| 问题标题 | 原案例中的问题标题 |
| 问题金额 | 如有则记录 |
| 责任主体 | 单位、部门、供应商、个人 |
| 资料类型 | 会议纪要、合同、凭证、台账、名单、报告等 |

### Step 3：抽取问题表现

把案例中的问题事实改写成结构化表达。

示例：

```text
原文：某单位在项目尚未验收的情况下，提前向施工单位支付工程款80万元。
问题表现：付款日期早于验收日期，且合同约定验收后付款。
```

### Step 4：抽取命中特征

命中特征分四类：

| 类型 | 示例 |
|---|---|
| 文本特征 | “验收后付款”“补充研究”“专项资金用于日常办公” |
| 字段特征 | 付款日期、验收日期、合同金额、身份证号 |
| 关系特征 | 同一供应商、同一人员、同一地址、同一电话 |
| 时序特征 | 付款早于合同、会议晚于实施、验收晚于付款 |

### Step 5：设计检测逻辑

检测逻辑必须能被程序或人工执行。

推荐格式：

```text
若 <资料/字段/文本> 满足 <条件>，且 <排除条件> 不成立，则输出 <风险等级> 疑点。
```

示例：

```text
若合同文本中包含“验收合格后付款”等表达，且付款台账中的付款日期早于验收报告日期，则输出“验收前提前付款”疑点；若存在合法预付款条款或阶段性验收资料，则降级或排除。
```

### Step 6：定义证据链

每条规则必须说明形成底稿需要哪些证据。

证据链模板：

```text
1. 证明规则命中的原始资料；
2. 证明事实发生的业务资料；
3. 证明违反依据的制度/法规/合同条款；
4. 证明金额或影响的台账/凭证；
5. 被审计单位说明或访谈记录。
```

### Step 7：定义误报场景

每条规则必须写误报，否则现场会被疑点淹没。

示例：

| 规则 | 常见误报 |
|---|---|
| 验收前提前付款 | 合同允许预付款、阶段性验收、补充协议调整付款节点 |
| 投标文件雷同 | 招标文件统一模板、法定格式条款、政策原文引用 |
| 专项资金用途偏离 | 项目实施方案允许列支必要办公耗材 |
| 财政供养人员领取补贴 | 政策并未排除该类人员，或人员状态已变更 |

### Step 8：确定规则级别

| 级别 | 判断标准 |
|---|---|
| A底稿级 | 资料齐全后可直接形成底稿或报告问题 |
| B疑点级 | 有明确核查价值，但必须补证据 |
| C提示级 | 只能提示方向，用于审前调查 |

### Step 9：生成规则卡

按 `rule-template.md` 回填完整字段。

### Step 10：试运行与迭代

每条规则在项目中运行后记录：

| 指标 | 说明 |
|---|---|
| 命中次数 | 系统输出疑点数量 |
| 人工确认次数 | 审计人员确认有核查价值的数量 |
| 排除次数 | 误报或无价值线索数量 |
| 形成底稿次数 | 最终进入底稿的问题数量 |
| 形成报告次数 | 最终进入报告的问题数量 |
| 涉及金额 | 如有则统计 |
| 误报原因 | 用于调整规则 |
| 漏报原因 | 用于新增规则 |

## 四、规则状态流转

```text
草稿
  ↓
试运行
  ↓
有效 / 高误报 / 停用
  ↓
升级 / 合并 / 拆分
```

| 状态 | 含义 |
|---|---|
| 草稿 | 已从案例提炼，但未运行 |
| 试运行 | 可用于项目，但结果仅作参考 |
| 有效 | 多个项目验证有效，可正式使用 |
| 高误报 | 命中多但确认少，需要调整 |
| 停用 | 政策变化、规则失效或价值低 |
| 升级 | 从提示级升级为疑点级或底稿级 |

## 五、抽取提示词

用于让 AI 从案例中提取规则时，可使用以下提示：

```text
请从以下审计案例中提炼一条可执行审计规则。不要只提关键词，要按以下字段输出：
1. 规则名称
2. 所属模块
3. 审计类型
4. 风险主题
5. 案例摘要
6. 问题表现
7. 命中特征
8. 所需资料
9. 数据字段
10. 检测逻辑
11. 风险等级
12. 证据链要求
13. 建议核查动作
14. 常见误报
15. 报告表述模板
16. 规则级别：A底稿级/B疑点级/C提示级

案例原文如下：
<粘贴案例>
```

## 六、质量控制清单

规则入库前逐条检查：

- [ ] 是否有明确案例来源或法规依据？
- [ ] 是否能映射到五个模块之一？
- [ ] 是否说明了所需资料？
- [ ] 是否说明了必要字段？
- [ ] 检测逻辑是否能执行？
- [ ] 是否有证据链要求？
- [ ] 是否写了常见误报？
- [ ] 是否区分提示级、疑点级、底稿级？
- [ ] 是否有输出表述？
- [ ] 是否有试运行记录位置？

## 七、首批执行建议

第一轮不要追求数量，先做 15 条高质量规则，优先选：

1. 已在融策项目中高频出现；
2. 容易通过现有资料验证；
3. 证据链清楚；
4. 能直接服务文本分析工具一期模块；
5. 审计经理看了能马上理解价值。

完成 15 条后，再扩展到 50 条。
