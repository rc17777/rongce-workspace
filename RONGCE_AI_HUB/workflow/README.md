## 六阶段详细设计

### ① 资料导入与智能分类（Import → Classify → Archive）

**用户操作**：把客户给的所有资料扔进 `projects/<项目名>/raw_data/`

**Agent自动执行**：

| 步骤 | Agent | 动作 | 输出 |
|:--|------|------|------|
| 1.1 文件扫描 | `data_scout` | 遍历raw_data，识别文件类型/编码/页数 | `status.json` 更新 |
| 1.2 内容分类 | `data_classifier`(new) | 按12业务线+资料类型自动打标签 | `raw_data/.meta.json` |
| 1.3 智能归档 | 脚本 | 按分类复制到Obsidian对应目录 | `obsidian-vault/<业务线>/<项目>/` |
| 1.4 RAG索引 | `rag_rebuild.py` | 增量更新RAG知识库 | `rag_index/` |

**分类逻辑**：
- 财务数据（含科目编码+金额）→ `财务/`
- 合同文件（含编号+金额+日期）→ `合同/`
- 招投标文件 → `招投标/`
- 制度文件 → `制度/`
- 项目资料（立项/可研/批复）→ `项目/`
- 资产/绩效/往来/工程 → 对应专项目录

**关键改进**：Phase ① 的产出物自动成为 Phase ② 的输入上下文。

### ② 实施方案与资料清单（Plan → Checklist）

**用户确认Phase ① 分类结果后触发。**

| 步骤 | Agent | 动作 | 输出 |
|:--|------|------|------|
| 2.1 方案生成 | `plan_writer`(new) | 读取①的分类结果+RAG同类项目模板，生成实施方案 | `实施方案_<项目>_v1.docx` |
| 2.2 重难点标注 | `plan_writer` | 基于历史案例库，自动标注高风险领域+审计重难点 | 方案中的「审计重难点」章节 |
| 2.3 资料清单 | `plan_writer` | 基于DATA_SPEC.md的业务线取数规范，生成差异化资料清单 | `资料清单_<项目>.xlsx` |
| 2.4 方案复核 | `review_sentinel` | 检查方案完整性（重难点是否覆盖/清单是否遗漏） | 复核意见 |

**输入依赖**：
- Phase ① 的分类结果（`.meta.json`）
- `DATA_SPEC.md` 中对应业务线的取数清单
- RAG中同类项目的实施方案模板
- `SCENARIO-SKILL-MAP.md` 中该业务线的技能推荐

**输出物**：
- `projects/<项目>/实施方案_<项目>_v1.docx` — 含审计目标、范围、重难点、方法、人员安排
- `projects/<项目>/资料清单_<项目>.xlsx` — 分级（已提供/待补充/建议索取）

|:--|:--|:--|

### ④ 现场核实与取证底稿（Verify → Evidence → Working Paper）

**用户拿到Phase ③ 问题清单后，带问题去现场核实。**

| 步骤 | 操作人 | 动作 | 工具 |
|:--|:--|------|------|
| 4.1 现场核实 | 审计人员 | 带着问题清单逐项核实，标注「确认/排除/存疑」 | 问题清单（打印版/平板） |
| 4.2 补充取证 | 审计人员 | 对确认的问题补充原始凭证/截图/访谈记录 | 手机拍照→导入raw_data |
| 4.3 取证单生成 | `workpaper_crafter` | 基于确认的问题+审计厅取证单模板，自动填充 | `取证单_<编号>.docx` |
| 4.4 底稿生成 | `workpaper_crafter` | 基于审计厅底稿模板，自动填充审计过程+结论 | `底稿_<编号>.docx` |
| 4.5 底稿复核 | `review_sentinel` | 检查取证单↔底稿↔问题清单三方一致性 | 复核报告 |

**取证单自动填充逻辑**：
```
问题清单条目 ──→ 取证单模板
  ├─ 问题描述 → 「审计发现」
  ├─ 违规法条 → 「违反规定」
  ├─ 涉及金额 → 「问题金额」
  ├─ 证据文件 → 「附件清单」
  └─ 现场确认 → 「被审计单位意见」
```

**底稿自动填充逻辑**：
```
问题清单 + 取证单 ──→ 底稿模板
  ├─ 审计事项 → 「审计目标」
  ├─ 审计过程 → 「检查方法+抽样范围」
  ├─ 审计发现 → 「问题描述+金额+法规」
  ├─ 审计结论 → 「定性+建议」
  └─ 附件索引 → 「取证单编号+证据清单」
```

### ⑤ 报告撰写（Draft → Review → Consultation）

| 步骤 | Agent | 动作 | 输出 |
|:--|------|------|------|
| 5.1 报告初稿 | `report_writer` | 汇总所有底稿→按审计报告结构组织 | `审计报告_初稿.docx` |
| 5.2 15维复核 | `review_sentinel` | 正文10维+交叉5维全面检查 | 复核报告（P0/P1/P2） |
| 5.3 修改完善 | `report_writer` | 根据复核意见修改 | `审计报告_v2.docx` |
| 5.4 征求意见稿 | 脚本 | 生成征求意见函+报告附件 | `征求意见稿.docx` |

**报告结构自动组装**：
```
底稿 ──→ 按问题类型分组 ──→ 按重要性排序 ──→ 套报告模板
                                    │
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
              基本情况       审计发现及问题     审计评价/建议
              (从Phase②中取)  (从底稿中取)      (从问题+法规中生成)
```

**审计建议撰写规则（report_writer 必读）**：

> 📋 完整清单：`knowledge/references/高质量审计建议撰写要点-研究型审计-20260810.md`（2026-08-10 归档，含可直接复制的 Prompt 片段）
> 📄 原文：`knowledge/literature/2026-08/研究型审计思维撰写高质量审计建议-江夏审计-20260810.md`

| # | 规则 | 要求 |
|:--:|:--|:--|
| 1 | 具体可操作 | 每条建议紧扣问题核心、分门别类、精准施策，禁止"大而化之、笼而统之"的空洞表述 |
| 2 | 分层分类 | **政策层面→制度完善 / 管理层面→流程优化 / 操作层面→具体整改**，让被审计单位对号入座 |
| 3 | 成因三辨 | 区分**管理不当/制度缺陷/政策偏差**三种成因，穿透表象找根源 |
| 4 | 三个区分开来 | 区分无意过失与明知故犯、探索性失误与违纪违法、体制机制问题与个人责任；既纠违规、又促机制健全 |
| 5 | 前瞻全局 | 跳出个案指向体制机制优化，而非仅指某个具体问题 |
| 6 | 逆向校验 | 用"资金—项目—政策—政治"链条校验建议逻辑：微观针对性 + 宏观建设性并重 |
| 7 | 四要素结构 | 每条建议 = 问题定性 → 成因分析 → 具体措施 → 预期效果 |

**建议质量纳入复核**：5.2 15维复核中增加"建议质量检查"——对照上表 7 条规则逐条校验（重点：是否分层分类、是否三个区分开来、是否具体可操作），不合格打回 5.3 重写。

### ⑥ 反馈闭环（Feedback → RAG → Skill → Rule）

**客户确认问题清单、底稿、取证单后，触发知识沉淀。**

| 步骤 | 动作 | 产出 | 位置 |
|:--|------|------|------|
| 6.1 案例沉淀 | 问题→案例化（问题表现+命中特征+检测逻辑+证据链+报告表述） | 结构化案例 | `obsidian-vault/cases/` |
| 6.2 规则提取 | 按 `rule-template.md` 格式，从案例中抽取审计规则 | A/B/C级规则 | `RONGCE_AI_HUB/rule-library/` |
| 6.3 技能更新 | 如果发现新的分析方法/检测模型，更新对应技能 | 技能强化 | `skills/` |
| 6.4 RAG同步 | 增量重建RAG索引 | 索引更新 | `rag_index/` |
| 6.5 方案模板优化 | 更新实施方案模板中的重难点库 | 模板库 | `RONGCE_AI_HUB/business-lines/` |
| 6.6 知识图谱更新 | 关联项目→企业→人员→问题类型 | 图谱扩展 | `audit-knowledge-graph` |

**闭环核心逻辑**：
```
确认的问题 ──→ 案例化 ──→ 规则化 ──→ 下次同类项目自动匹配
                                          │
                          ①资料分类时自动推荐相关案例
                          ②方案撰写时自动提示历史重难点
                          ③Agent分析时自动加载历史检测规则
                          ⑤报告撰写时自动引用相似案例表述
```

## 使用方式（一次完整的审计项目）

```bash
# === Phase ①: 创建项目 + 导入资料 ===
# 1. 用户：把客户资料扔进 projects/<项目名>/raw_data/
# 2. 对我说："开始XX项目，业务类型是XX审计"
# 3. 我自动：
#    - 创建项目目录结构
#    - 扫描raw_data，分类打标签

#    - 增量更新RAG索引

python -X utf8 ai-workflow/engine.py project_init --name "XX项目" --type "经责"

# === Phase ②: 生成实施方案 + 资料清单 ===

python -X utf8 ai-workflow/engine.py phase2_plan --project "XX项目"

# === Phase ③: 多Agent分析 ===
```

## 关键设计决策

1. **Agent不是独立跑，是嵌入六阶段的执行器** — Phase ③ 是多Agent最密集的阶段，但①④⑤⑥也需要Agent支撑
2. **模型路由按Agent分配，不是按阶段分配** — 合同审查用sonnet（合规风险高），数据扫描用v4-pro（量大批处理），法规匹配用qwen（中文原生）
3. **Phase ⑥ 是长期价值的放大器** — 每做一个项目，下一次同类项目就更智能
4. **用户始终在回路中** — Phase ①④⑥ 需要用户确认，②③⑤ Agent出初稿后用户把关
