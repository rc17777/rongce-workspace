# A2A多智能体通信协议三层架构速查

> 整理自：微信公众号技术文（2026-07-21）
> 适用场景：多Agent系统架构设计、AI审计中台Agent编排

---

## 一、三层架构总览

```
┌─────────────────────────────────────────┐
│  ③ 状态交接层：任务移交（Goal+上下文+记忆）   │
├─────────────────────────────────────────┤
│  ② 能力对齐层：元协商→契约→JSON Schema验证   │
├─────────────────────────────────────────┤
│  ① 服务发现层：注册/注销/健康检查/标签匹配    │
└─────────────────────────────────────────┘
```

## 二、各层关键要点

### 第一层：服务发现
| 要素 | 说明 |
|:----|:----|
| 功能 | Agent互相知晓存在与位置 |
| 机制 | 动态注册/注销、健康检查、负载感知 |
| 实现 | 中央注册中心（Consul等）+ 标签匹配 |
| 示例 | Agent A广播 `capability: sql_exe, scope: busidata_read`，符合条件者响应 |

### 第二层：能力对齐
| 要素 | 说明 |
|:----|:----|
| 功能 | 用契约杜绝幻觉传染，消除语义漂移 |
| 流程 | 元协商 → 交换Schema → 签署契约 → 运行时校验 → 正式交互 |
| 契约内容 | 输入Schema、输出JSON Schema、错误码定义、SLA承诺 |
| 校验机制 | 所有请求在进入LLM推理前通过JSON Schema验证器 |
| 核心价值 | 模糊自然语言 → 确定性机器合约 |

### 第三层：状态交接
| 要素 | 说明 |
|:----|:----|
| 功能 | 任务跨Agent连续执行的信息传递 |
| 交接内容 | ①任务目标（Goal） ②共识上下文 ③个性化记忆快照 |
| 存储方式 | 嵌入向量 + 键值对混合结构 |
| 管理方 | 协调者（Orchestrator）统一管理版本与生命周期 |
| 防丢策略 | 避免Agent重启导致上下文丢失 |

## 三、协议层级对比

| 协议 | 类比 | 功能 | 适用场景 |
|:----|:----|:----|:----|
| A2A | 脑脑协作 | Agent间高层次协作交互 | 多Agent任务编排 |
| MCP | 脑控手 | 模型调用工具 | 单Agent工具链 |

## 四、组网模式选型

| 模式 | 优点 | 缺点 | 适用场景 |
|:----|:----|:----|:----|
| 中心化调度 | 开发简单、易管控、可追溯 | 单点故障风险 | 中小规模（<100 Agent） |
| P2P去中心化 | 无单点、高容错 | 开发复杂、治理难 | 大规模分布式集群 |

## 六、对融策AI审计中台的启示

1. **服务发现** → 审计Agent池需要统一的注册中心，按能力标签（如"绩效评价复核""经责审计核查"）动态调度
2. **能力对齐** → 审计Agent之间传递数据时应使用结构化JSON Schema而非自由文本，避免"审计结论被Agent B误解"
3. **状态交接** → 审计任务跨Agent流转时需保留完整的审计底稿上下文+项目共识，避免"换个Agent就不知道审到哪了"
