# 融策·审盾 RAG + LLM Wiki 整体框架设计

## 背景
融策事务所正在构建"审盾"——一个面向政府财政资金审计的专业能力体系。核心是知识库驱动的审计复核与问题发现系统。

## 现有知识库
- 12,617 chunks，1,374 文件
- 向量引擎：text2vec-base-chinese（768 维）
- Web 界面：Flask @ localhost:5005
- 数据源：政策法规 / 项目经验 / 问题整改 / 前沿技术（四库）

## 框架设计：三阶段演进

### 一审盾一期（RAG-first 复核器）— 进行中
- 纯向量检索 + 规则引擎 + 人工确认
- 不构建知识图谱
- 复核流程：上传报告 → 提取审计主题 → 向量检索匹配法规/案例 → 规则引擎检查（错别字/金额/日期/法规引用等9项）→ LLM 15维深度复核 → 分级输出（P0/P1/P2）
- 一期不承诺图谱能力，但数据结构预留实体标签字段
- 验收标准：Accuracy ≥ 80%，False Positive ≤ 20%，重大错误漏检为 0

### 二审盾二期（KG-enhanced RAG）— 规划中
- 从高频实体抽取知识态实体（问题类型 / 定性依据 / 整改建议）
- 用实体关系扩展检索 Query，提升召回精准度
- 确认边 vs 推断边质控机制（见下）
- 推断边人工确认机制上线

### 三审盾三期（Agentic RAG + 微调）— 远期
- 智能体 → 检索 → 评分 → 重写循环（自纠错检索链路）
- 社区摘要回答全局问题
- 微调负责"审计报告语感"，RAG 负责"定性依据内容"

## 确认边 vs 推断边机制
- 确认边：置信度 1.0，人工校验 / 权威来源（法规原文、入库底稿），可直接引用
- 推断边：默认置信度 0.5，LLM 抽取 / RAG 自动补全，仅在无确认边可达时使用，报告必须标注"基于推断"
- 升级规则：2 个独立来源交叉验证 + 人工确认

## RAG 技术选型
- 分块策略：固定 512 字符（一期），计划升级为递归切分 800-1000 + 语义切分混合
- 向量模型：text2vec-base-chinese（一期），计划升级为 BGE-large-zh-v1.5
- 当前无重排（Reranker）环节，计划二期加入
- 检索：余弦相似度，Top-K 检索

## LLM Wiki 预编译层（规划中）
- 将高频稳定的法规条款、常见问题类型、标准整改建议预编译为结构化 Markdown 页面
- 页面间双向链接，形成知识网络
- 查询时优先读取预编译 Wiki，而非实时向量检索
- 动态/更新的知识仍走 RAG 实时检索
- 工具：QMD 搜索引擎（BM25 + 向量混合搜索 + LLM 重排序，本地运行）

## 核心设计假设
1. 审计场景 = 根因分析（RCA）——问题定性、归因、追溯与工业 RCA 同构
2. 审计知识可拆为两类实体：运行态（被审计单位/项目/资金）和知识态（问题类型/法规/整改）
3. 审计复核必须溯源——每条意见必须能追到具体法规和项目底稿
4. 先做 RAG 再做图谱，不做"完美图谱"——从高频实体逐步积累
5. AI 输出是辅助，人工确认是红线——所有高风险的推断必须人工确认
