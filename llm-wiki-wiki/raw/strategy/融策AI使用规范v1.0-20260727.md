# 融策AI使用规范 v1.0

> **生效日期**：2026-07-27
> **适用范围**：融策会计师事务所 / 融策工程咨询公司 全体员工
> **性质**：强制性制度（违反底线条款视为严重违规）

---

## 一、总则

### 1.1 定位

本规范界定融策团队在使用AI工具开展审计工作时的行为边界。AI是效率工具，不是决策主体。审计师永远是审计责任的第一和唯一承担者。

### 1.2 核心原则

> **AI是助理，人是责任主体。这个定位永远不能颠倒。**

---

## 二、三大安全底线（🔴 红线，触碰即严重违规）

### 2.1 底线一：敏感数据不出域

#### 2.1.1 绝对禁止

| 禁止行为 | 示例 |
|:--|:--|
| 将原始财务数据直接输入公共AI平台 | 把客户完整的预算执行表复制到ChatGPT/公共AI对话框 |
| 将含个人隐私的员工/客户数据上传 | 把包含身份证号、电话号码的员工名单提交AI分析 |
| 将投标文件原始电子版上传公共AI | 把竞争对手投标方案全文粘贴给AI |
| 将银行流水/账户信息提交公共AI | 把含完整银行账号的交易明细提交分析 |

#### 2.1.2 脱敏标准

**数据必须经过脱敏处理才能提交AI分析**：

| 字段类型 | 脱敏方式 | 示例 |
|:--|:--|:--|
| 企业名称 | 编号替代 | "成都市XX建设公司" → "E001" |
| 个人姓名 | 编号替代 | "张三" → "P001" |
| 金额 | 区间替代 | "1,235,678.00元" → "100-150万" |
| 银行账号 | 完全删除 | — |
| 身份证号 | 完全删除 | — |
| 手机号码 | 完全删除 | — |
| 详细地址 | 城市级保留 | "成都市武侯区XX路XX号" → "成都市" |

#### 2.1.3 脱敏后方可提交AI的数据

- 数据分析指令（如"找出以下交易记录中的异常"）可以包含脱敏后的数据
- 报告草稿（不含敏感字段）可以提交AI润色
- 制度文件、法规文件属于公开信息，可直接分析

#### 2.1.4 现有AI工具的合规分级

| 工具 | 安全级别 | 使用限制 |
|:--|:--|:--|
| 本地PaddleOCR | ✅ 安全 | 数据不离开本机，可直接处理原始文件 |
| 本地RAG知识库 (127.0.0.1:5001) | ✅ 安全 | 仅本地访问，可直接处理 |
| DeepSeek API (HTTPS) | ⚠️ 需脱敏 | 数据传至DeepSeek服务器，必须脱敏后使用 |
| 天眼查/企查查API | ✅ 安全 | 公开工商数据查询，正常使用 |
| 公共AI (ChatGPT等) | 🔴 原则上禁止 | 除非完全脱敏且经项目经理批准 |

### 2.2 底线二：AI输出不盲信

#### 2.2.1 AI输出校验三步法

**任何AI输出在采纳前，必须完成以下三步校验**：

```
第一步·逻辑校验：这个结论在业务上能解释通吗？
  ├─ 有没有违反常识？
  ├─ 有没有逻辑跳跃？
  └─ 用一句话向非专业人士解释，能说通吗？

第二步·法规校验：支撑这个结论的法规真实存在且适用吗？
  ├─ 用RAG知识库交叉验证法规条文
  ├─ AI引用的法规文号、条款是否真实存在？
  └─ 法规的适用范围是否覆盖当前情境？

第三步·数据校验：支撑这个结论的数据能在原始数据中找到吗？
  ├─ 每个数字都可以追溯到原始数据源
  ├─ 不存在AI编造的"看起来合理"的虚构数据
  └─ AI引用的案例/先例是否有可查的出处？
```

#### 2.2.2 审计场景AI常见幻觉

| 幻觉类型 | 表现 | 如何发现 |
|:--|:--|:--|
| 法规幻觉 | 捏造不存在的法规文号、条款、罚则 | 用RAG知识库逐条交叉验证 |
| 数字幻觉 | 生成"看起来合理"的金额、比例、日期 | 每个数字要求回溯到原始数据 |
| 逻辑幻觉 | 把相关性当因果性，推理链条有跳跃 | 逐链审查逻辑，标注"推断"vs"事实" |
| 案例幻觉 | 编造"同类案例""行业惯例"来支撑结论 | 任何案例引用必须有可查出处 |
| 默认值幻觉 | 数据缺失时AI自动填充"合理默认值" | 标记所有数据来源，缺数据的标注"未知" |

#### 2.2.3 高风险AI输出需升级审签

以下类型的AI输出需经**项目经理+质量负责人双重审签**方可使用：
- 涉及金额≥100万的异常发现
- 涉及刑事/纪律责任的定性
- 涉及被审计单位主要负责人的分析
- AI输出与审计组初步判断相悖的结论

### 2.3 底线三：分析过程可追溯

#### 2.3.1 每个AI辅助生成的审计发现必须携带元数据

```json
{
  "finding_id": "项目编号-发现序号",
  "data_source": "具体文件/系统/表名及路径",
  "analysis_method": "使用的分析方法、模型、参数",
  "threshold": "异常判定标准和阈值",
  "matching_records": ["可追溯的记录编号清单"],
  "ai_model": "使用的AI模型名称",
  "ai_prompt_hash": "提交给AI的提示词哈希值（可选）",
  "human_reviewer": "审核人姓名",
  "human_review_date": "审核日期",
  "verification_result": "校验三步法的执行结果（通过/不通过/修正后通过）"
}
```

#### 2.3.2 被审计单位质疑时的回答标准

当被审计单位质疑"AI分析的结果凭什么说我有问题"时，审计师必须能够：

1. **出示原始数据**：异常标记的来源数据是什么
2. **说明分析方法**：用了什么方法、什么基准、什么阈值
3. **展示对比参照**：正常情况是什么样的，当前的偏离程度
4. **出具人工确认**：AI标记后经过了哪些人工验证步骤

**禁止回答**："这是系统/模型自动检测出来的"——这等于自毁审计结论的可信度。

## 三、人机协同操作规范

### 3.1 角色和责任划分

| 环节 | AI做 | 人做 | 不可颠倒 |
|:--|:--|:--|:--|
| 审前调查 | 制度解析+风险清单生成 | 确认审计重点+调整风险排序 | 人 |
| 数据预处理 | 格式转换+去重+缺失标记 | 确认清洗逻辑正确 | 人 |
| 数据分析 | 全量扫描+异常检测+关联分析 | 定义"什么叫异常"+设置阈值 | **人** |
| 异常标记 | 输出可疑记录清单 | 逐条判断+降噪+排除误报 | **人** |
| 根因分析 | LLM生成追问链 | 验证根因正确性+补充遗漏维度 | **人** |
| 延伸取证 | 生成核查要点清单 | 实际执行取证+访谈+调阅 | **人** |
| 报告撰写 | 起草初稿+图表生成 | 审核修正+注入专业判断+定稿 | **人** |
| 审计定性 | ❌ 禁止 | ✅ 审计师独家责任 | **人** |
| 审计定责 | ❌ 禁止 | ✅ 审计师独家责任 | **人** |

### 3.2 AI输出的标记标准

所有AI辅助生成的内容，在内部工作底稿中应明确标注`[AI辅助]`。对外报告中不需要标注，但内部底稿必须留痕。

## 四、团队能力要求

### 4.1 全员基础要求（1个月内达标）

- 能用自然语言向AI下达数据清洗和分析指令
- 能区分AI生成的可靠输出和可疑输出
- 掌握脱敏操作和数据安全常识
- 熟悉本规范的三大底线和校验三步法

### 4.2 AI训练师专项要求（3个月内达标）

- 掌握提示词工程基础（能针对不同分析场景编写精准提示词）
- 能复盘AI输出质量，识别系统性误判并调整参数
- 能为本业务线维护≥10条AI分析规则
- 理解常用分析方法的原理（不要求编程，但要理解逻辑）

## 五、违规处理

| 违规等级 | 行为 | 处理 |
|:--|:--|:--|
| 🔴 严重违规 | 将客户敏感数据直接提交公共AI平台 | 通报批评+暂停AI使用权限+赔偿损失 |
| 🔴 严重违规 | AI输出未校验直接作为审计结论 | 通报批评+项目返工+扣发绩效 |
| 🟡 一般违规 | 未按要求完成脱敏操作 | 警告+限期改正 |
| 🟡 一般违规 | 审计发现缺少元数据标记 | 限期补充+流程提醒 |
| 🟢 轻微违规 | 内部底稿未标注AI辅助标记 | 提醒+限期改正 |

## 六、附录

### A. 脱敏操作快速参考

```
脱敏前检查清单：
□ 是否包含完整企业名称？→ 编号替代
□ 是否包含个人姓名？→ 编号替代
□ 是否包含精确金额？→ 区间替代
□ 是否包含银行账号/身份证号/手机号？→ 完全删除
□ 是否包含详细地址？→ 保留城市级
□ 脱敏后的数据是否仍满足分析需求？→ 如不满足，将分析拆分为可脱敏和不能脱敏两部分
```

### B. AI校验三步法快速参考

```
1. 逻辑校验 → 用一句话向非专业人士解释这个结论，说得通吗？
2. 法规校验 → 引用的每一条法规，能查到原文并确认适用吗？
3. 数据校验 → 结论里的每个关键数字，能在原始数据里找到吗？
```
