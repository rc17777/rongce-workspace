# 开源 25k 星的 Cognee：给 AI Agent 做记忆，并把数据织成一张知识图谱

> Source: https://mp.weixin.qq.com/s/hcql_HJrsvAB_r_ttKNVLg
> Author: Sanmist / Lab | Ingested: 2026-07-15

cognee.remember()：把一句话变成 Agent 能推理的记忆图谱（图源：项目仓库）给 AI Agent 做长期记忆，大多数工具的思路是「存进去、查出来」：把文本切块、嵌入、入库，查的时候按相似度捞回来。cognee 多做了一步——它把你喂进去的数据，持续织成一张自托管的知识图谱，让记忆不只是能按语义搜，还能顺着实体之间的关系连起来。它的自我介绍是「面向 Agent 的开源 AI 记忆平台」：任意格式的数据丢进去，cognee 把它变成一张跨会话留存的知识图谱，让每个 Agent 都能带着完整上下文去回忆、关联、行动。Apache-2.0 协议，Python 写成，从 2023 年做到现在，目前 25.3k 星，背后还有一篇论文（arXiv 2505.24478，讲怎么优化知识图谱与大模型之间的接口来做复杂推理）。四个动作：remember / recall / forget / improvecognee 的 API 收敛成四个动作，几行代码就能跑：import cognee# 永久存进知识图谱（内部跑 add + cognify + improve）await cognee.remember("cognee 把文档变成 AI 记忆。")# 存进会话记忆（快缓存，后台再同步进图谱）await cognee.remember("这个用户喜欢详细的解释。", session_id="chat_1")# 查询，自动选最合适的检索策略results = await cognee.recall("cognee 是做什么的？")# 先查会话记忆，不够再回落到图谱results = await cognee.recall("这个用户喜欢什么？", session_id="chat_1")# 用完删掉await cognee.forget(dataset="main_dataset")两个细节值得留意：remember 不只是写入，它内部连着跑了 cognify（把数据加工成图谱）和 improve（优化）；recall 会自己挑检索策略，而不用你指定。另外它分了「会话记忆」和「永久图谱」两层——会话记忆是一块快缓存，先答得快，再在后台慢慢并进永久图谱。也有等价的命令行 cognee-cli remember / recall / forget，以及一个本地 UI。核心：它不止存记忆，它 cognifycognee 和一众「存了再查」的记忆工具最不一样的地方，在 cognify 这一步：它不是把文本原样塞进库，而是从里面抽出实体和它们之间的关系，长成一张图。回到开头那张图：写入时，一句「Vasilije 在柏林创立了 cognee」会被拆成三个节点（Vasilije、cognee、柏林）和两条带标签的边（founded、based in），并入你已有的记忆图谱。查询走的则是另一个方向：问「cognee 在哪」，它顺着图里 cognee 到柏林的那条「based in」边，给出一个落在图谱上、有出处的答案，而不是凭一段相似文本去猜。这背后是三样东西合在一起：向量嵌入（按语义搜）、图推理（按关系连）、以及一套有认知科学依据的本体生成（给实体和关系定结构）。文档因此同时变得「可按意思搜」和「可顺着关系走」——这正是单纯向量库给不了的那部分。普通向量库存一块块孤立文本、按相似度捞；cognee 抽出实体与关系连成图和普通向量库摆在一起，差别就清楚了：向量库把文本切成一块块、各自独立，查询时捞回最像的几段，但块与块之间没有关系，你问「A 和 B 是什么关系」它答不上；cognee 把数据抽成实体和边连成一张网，既能按语义搜，又能顺着关系把来龙去脉串起来。cognee 1.0：整个记忆层塞进一个 Postgres这是 1.0 版本里最实在的一个变化，也最值得单拎出来说。按传统做法，搭一套「图记忆」要同时养一堆数据库：关系靠图数据库（Neo4j 之类）、嵌入靠专门的向量库、会话靠 Redis、元数据再来一个关系库——Agent 还没开始记东西，这一摞服务就得先部署好、配好安全、付好钱。传统四件套 vs cognee 1.0 单 Postgrescognee 1.0 把这一整层收进一个 Postgres 实例：图用 Postgres 自带的图后端、嵌入用 pgvector、会话用 SQL 缓存、元数据还在同一个 Postgres 里。图还是那张图，只是和文本、元数据、嵌入住进了同一处，检索在「相似度」和「结构」之间切换时不用再跨服务。官方称在自家 CI 基准里，Postgres 方案比「图库 + 向量库」分开搭的快约 10%。pip install "cognee[postgres]"它没有把路堵死：真有需要，照样能换上专用后端——图可以用 Neo4j / Neptune，向量可以用 pgvector / LanceDB，社区适配器还接了 Qdrant、ChromaDB、Weaviate、Milvus。本地开发则全程嵌入式（SQLite、LanceDB、Kuzu），不用额外起任何服务。接 Claude Code 和其他 Agent对用编码 Agent 的人，最顺手的是它的 Claude Code 记忆插件。从 Claude Code 的 marketplace 装：claude plugin marketplace add topoteretes/cognee-integrationsclaude plugin install cognee-memory@cogneeexport LLM_API_KEY="sk-..."   # 本地模式只要这一个；云模式则配 COGNEE_BASE_URL + COGNEE_API_KEYclaude这个插件深挂进了 Claude Code 的生命周期：会话开始时选模式、建身份，每次你发提示时注入相关上下文，工具调用后记下轨迹，回答出来后写进会话记忆，上下文要被压缩前先把记忆保住，会话结束时再统一同步进永久图谱。本地模式默认在 localhost 起一个本地 cognee API，只要一个 LLM_API_KEY，连云都不用。除此之外，它还有 MCP server、OpenClaw 插件，以及官方的 Rust 和 TypeScript 客户端，部署上提供了 Cognee Cloud 托管版和 Modal / Railway / Fly.io 等一键自托管配置。它的成绩cognee 公布了一组 BEAM 长上下文基准——这个测试看的是系统能不能在一段不断变化的长对话里始终跟得上，比常见的「大海捞针」更贴近 Agent 记忆的真实需求。官方称只用默认设置和标准开源功能（没上自定义模型、没为 BEAM 调专门的管线）：基准设置cognee此前 SOTARAG 基线BEAM100K token0.790.735~0.33BEAM10M token0.670.641~0.33难得的是，官方自己把话说在前头：这组数字是方向性信号，不是定论，完整的方法、前提和该怎么解读，得看他们的说明。看个大致水平即可。几条要注意的• 建图靠大模型，默认要云 LLM 的 key。cognify 那一步是用 LLM 把数据抽成实体和关系的，所以默认得配 OpenAI 等供应商的 key（也支持换别的 provider，包括本地模型，见文档）。数据量一大，建图本身就是一笔不小的 LLM 调用开销。• 图的质量，取决于抽取这一步。 实体和关系抽得准不准、本体定得合不合理，直接决定这张图好不好用——这部分仍依赖底层模型，不是免费午餐。• 国内直接用要过两关。 一是默认的云 LLM，二是 Cognee Cloud 托管版；想全本地，得自己配本地 LLM provider + 嵌入式后端。• 它偏「平台」而非「小工具」。 功能面大（多后端、多语言客户端、租户隔离、审计、OTEL），上手简单，但真要用全套，是按一套基础设施在运维，不是装个库就完事。它在记忆赛道里站哪最近这一批 Agent 记忆方案，差异大体在两个问题上：记忆存成什么形态，以及靠什么检索。cognee 的位置很清楚——它是知识图谱那一派。别家多数是把记忆存成向量（按相似度捞）或存成文件（人能翻看），cognee 则把数据连成一张实体加关系的图，检索时既能按语义搜、又能顺着关系走。它要解决的，是「相似」之外的那部分：A 和 B 到底是什么关系、一件事的来龙去脉怎么串。放成一句话：如果你的场景是「捞回最像的几段文本」就够了，向量库类的方案更轻；如果你需要的是「把分散在各处的数据连成一张能推理的网」，cognee 这种图结构的思路才用得上。写在最后cognee 给 Agent 记忆的答案，是把数据 cognify 成一张知识图谱——记忆不再是一堆可被搜到的片段，而是一张能顺着关系走、能推理的网。代价是建图依赖大模型、运维上更像在管一套基础设施；但 1.0 把整层收进一个 Postgres，确实把门槛降了一截。Apache-2.0 协议，25.3k 星。仓库地址：github.com/topoteretes/cognee。近期推荐文章更适合中国宝宝体质的 AI PPT Skill：17
