# 审计报告AI复核 — 15+6维度检查法（12场景校准 v2.0）

## 概述

审计报告质量复核中，文字校对只是最浅层。真正经不起追问的是：逻辑断点、证据链缺失、定性失准、整改靶心偏移——这些才是"逻辑炸弹"。

本技能将10套AI提示词封装为可随时调用的复核框架，覆盖审计报告质量的全部关键维度。

**来源**：「审计实践」公众号 2026-06-09《用AI"审"了一篇审计报告，结果把组长藏了3个月的5个逻辑炸弹全挖出来了》

**核心原则**：AI审报告，审的是"漏"，不是"错"。最终判断永远归审计人。

**nigo方案参考**：「审计实践」2026-07-04《我用 AI 做了一个审计报告复核 Skill，误报问题终于解决了》。核心理念：三层架构分离——AI做结构理解 → 代码做机械核对 → AI做终审去伪。Skill优于固定工具箱：规则可调教、格式自适应、跨事务所复用。

### 三层职责表

| 层 | 执行者 | 任务 | 输出 | 不可替代性 |
|:---|:-------|:-----|:-----|:---------|
| **结构理解** | AI（Claude/GPT） | 读懂报告结构：报表位置、列布局、科目映射 | manifest.json + note_map.json | 🔴 无结构映射→机械核对无法启动 |
| **机械执行** | 代码（Python脚本） | 按manifest抽数、逐项加减、expected/actual/diff | 差异清单（含噪音） | 🟡 代码比AI快10倍且零幻觉 |
| **终审去伪** | AI（带原文上下文） | 判定差异是"数字错了"还是"结构特殊" | 最终复核报告 | 🔴 误报过滤核心——代码无法区分真假矛盾 |

### nigo方案的四个核心洞察（直接引用）

1. **"以前工具误报率高，是因为没有终审"**——代码检出的差异里，很多是表格特殊结构（如合并报表中同一科目在不同口径下数字不同），必须有AI回到原文做上下文判定
2. **"代码出expected/actual/diff，完全可复现"**——机械层必须是确定性的，不能依赖AI做算术
3. **"Skill优于固定工具箱"**——不同事务所报告格式差异极大，规则文件可改、可扩展、可让AI帮你加规则
4. **"准确度高，但效率低了很多"**——三层架构比单次AI扫描慢，但误报率断崖式下降。这是合理的trade-off

### nigo四类检查 ↔ 融策15维度 映射

| nigo四类检查 | 融策对应维度 | 执行方式 | 工具 |
|:------------|:------------|:-------:|:-----|
| **报表间勾稽**（资产=负债+权益、利润表推导链、现金流量表合计） | ⑪ 数据一致性 + ⑮ 全链路金额追踪 | 机械执行 | calculator.py |
| **表注勾稽**（41个科目如应收账款=账面余额-坏账准备） | ⑪ 数据一致性 + ⑬ 取证单↔附表 | 机械执行 | calculator.py + note_map.json |
| **附注内勾稽+横加竖加**（变动表reconcile、明细之和=合计行） | ⑪ 数据一致性 + ① 逻辑一致性 | 机械执行→AI终审 | calculator.py → Claude/GPT |
| **文本与格式**（错别字、病句、公司名统一、页码连续） | ⑩ 措辞 + ② 定性 + ⑧ 摘要 | AI判定 | Claude/GPT + FP白名单 |

### 12场景适配三层架构的要点

nigo针对财务报表（四表一注）设计了三层架构。融策12条业务线中：
- **结构层**需要适配不同报告格式：经责审计报告是人物+事件结构，不是四表；绩效评价是评分+指标结构；工程决算是概算→决算链条
- **机械层**的calculator.py需要为每个场景定制计算逻辑（经责查责任定性→问题→金额链条，不是科目→附注链条）
- **终审层**需要场景化的FP规则库（已在`references/false-positive-rules-v2.md`实现）

### 效率问题与解决思路

nigo提到"准确度高但效率低很多"。针对此，建议：
- **场景锁定时**跳过结构层（12条业务线有固定报告模板，manifest可以预置而非每次生成）
- **批量同质报告时**一份manifest复用
- **增量复核时**只跑变更维度，不全量重跑

## 三条安全红线（每次复核必须遵守）

1. **脱敏**：含敏感信息的底稿和报告草稿不得输入公网AI工具，须脱敏或在内网私有化环境中操作
2. **人工验证**：AI所有结论性输出必须经过人工逐条验证——AI是初审工具，不是终审法官
3. **不替代签批**：AI辅助审核结论不可替代项目负责人和质量复核人的专业判断和签字责任

## 🚩 核心升级：两阶段过滤 + 误报抑制机制（2026-07-04 参考nigo方案更新）

### 问题背景

原版10+5维复核体系实际使用中，**⑩措辞情绪化**、**①逻辑一致性**两个维度的误报率较高（>40%），根源在于：
- 关键词匹配 ≠ 语义理解（"但""却"是公文标配，不是情绪化）
- 不看上下文就判定（"部分""个别"在无量化时是问题，在有量化数据时是正常表述）
- 无门槛值过滤（金额差异<0.01%的尾差也要报，淹没真正问题）

### 两阶段过滤架构

```
                        原始报告/附表/取证单
                               │
                     ┌─────────┴─────────┐
                     ▼                   ▼
              第一阶段：全面扫描        第二阶段：误报过滤
              （高召回率≥90%）          （高精度≥85%）
                     │                   │
              标记所有可疑项            上下文二次判定
              附置信度(高/中/低)        白名单规则匹配
                                        量级门限过滤
                                        置信度>中才报P0
                     │                   │
                     └─────────┬─────────┘
                               ▼
                        分级输出结果
                🔴 P0 确定问题 | 🟡 P1 可能问题 | ⚪ P2 低概率
```

### 6条误报抑制规则（所有维度通用）

| # | 规则 | 抑制对象维度 | 说明 |
|:--|:-----|:------------|:-----|
| FP-1 | **白名单过滤** | ⑩情绪化 | "但""却""仍然""依然""始终"在公文正文中为客观转折/持续态表述，仅当整段无客观事实、纯主观判断时才标记 |
| FP-2 | **量化门限** | ②定性/⑪数据 | 金额差异<0.01%或<1000元标记为"可接受尾差"非P0；"部分""个别"后跟具体数字的不标记 |
| FP-3 | **上下文锚定** | ①逻辑 | 同一概念在不同章节使用不同近义词（如"措施"↔"对策""方式"↔"手段"）不视为逻辑矛盾 |
| FP-4 | **类型感知** | ⑨跨项目 | 不同类型项目（经责vs专项vs绩效）允许不同定性口径，仅同类项目才比对一致性 |
| FP-5 | **置信度门槛** | 全部 | 置信度"低"的发现不进入输出主表，仅附在"仅供参考"附录中 |
| FP-6 | **反向验证** | ⑭取证单闭环 | "取证单有但报告无"的问题，先检查是否被合理归纳到同类问题中，不直接标遗漏 |

### 输出格式升级

每次复核输出增加两组件：

**① 分级主表**（用户第一眼看到的）
```
| 序号 | 复核维度 | 发现 | 置信度 | 风险等级 | 修改建议 |
|:-----|:---------|:-----|:-------|:---------|:---------|
| 1 | ⑪数据一致性 | 正文532.8万≠附表528.3万 | 高 | 🔴 P0 | 需追溯到取证单核实 |
| 2 | ⑩情绪化 | "但"连续使用3次 | 低 | ⚪ P2 | 公文允许，无需修改 |
```

**② 处理统计**（复核人效率工具）
```
本轮复核摘要：
  - 总检出：17项（P0:3 / P1:5 / P2:9）
  - 误报过滤：8项（已移入附录）
  - 最终输出：9项（P0:3 / P1:3 / P2:3）
  - 通过核验：21项（详见通过项清单）
```

## 12业务线场景化误报抑制规则库

> ⚠️ **核心参考文件**：`references/false-positive-rules-v2.md`（本文档为概览，完整规则见参考文件）

### 双层架构

```
FP规则体系
├── 通用层（FP-G1~G6）：6条全局规则，所有场景生效
│   白名单过滤 | 量化门限 | 近义词放行 | 跨类型隔离 | 低置信度过滤 | 归纳合并检查
│
└── 场景层（FP-1A~FP-12C）：12条业务线 × 2~5条专属规则
   经责(4条) | 收支(3条) | 预算(3条) | 专项(3条) | 往来款(3条)
   招投标(3条) | 国企(3条) | 成本(3条) | 能源(3条) | 工程(3条)
   绩效(4条) | 补贴(3条) → 共38条场景专属规则
```

### 12场景速查表

| 业务线 | 最大误报源 | 核心敏感词（不可过滤） | 规则数 | 参考 |
|:------|:----------|:-------------------|:------:|:-----|
| 经责审计 | ⑩情绪化→标准定性词被误标 | 失职/渎职/负有直接责任 | 4条 | FP-1A~1D |

### 使用方式

**单场景**：执行通用层FP-G系列 + 对应场景的FP-N系列

**多场景混合**：通用层 + 取所有涉及场景的规则（冲突时取最严格）

**不确定场景**：仅执行通用层FP-G1~G6（6条基础规则）

### 报告复核清单（基层审计报告常见问题）

| 复核项 | 检查要点 | 典型风险 |
|---|---|---|
| 基本情况复核 | 被审计单位基础数据是否经复核计算，是否避免照抄工作总结、履责报告 | 直接照抄导致事实失真和审计风险 |
| 表达规范 | 文字是否准确、客观、简洁，是否避免口语化、修饰性、情绪化表达 | 表述空泛、模糊，报告使用者难以理解 |
| 金额勾稽 | 元、万元、亿元等单位是否统一，分项与合计、百分比、四舍五入关系是否一致 | 数字关系打架，直接损害报告可信度 |
| 问题排序 | 是否按性质归类、按重要性排序，重要问题、突出问题、共性问题是否在前 | 简单照搬底稿，主次不分、层次混乱 |
| 问题结构 | 每个问题是否包含事实、定性依据及结论、处理处罚依据、建议或整改要求 | 只写事实不定性，或者定性依据与事实脱节 |
| 法规引用 | 是否写明发文机关、文件标题、文号、具体条款，是否排除失效法规 | 引用不完整、过时或错误法规 |
| 审计建议 | 建议是否基于事实和证据，是否针对被审计单位，是否具体可执行 | 空话套话、脱离事实、向非被审计对象提建议 |
| 审计评价边界 | 评价是否限于已审计事项，是否有底稿和证据支撑，是否避免绝对化用词 | 超范围评价、评价与审计决定矛盾 |
| 报告与底稿一致 | 报告问题、金额、定性、责任、依据是否与底稿、取证单、附表一致 | 报告无据、漏报、有据不报或口径冲突 |
| 复核实质性 | 复核意见是否指出具体问题和修改要求，是否避免只写“无意见” | 复核流于形式，质量控制失效 |

**报告复核输出格式**：

```markdown
## 报告复核结果

| 序号 | 复核项 | 发现问题 | 风险等级 | 修改建议 | 对应位置/证据 |
|---|---|---|---|---|---|

风险等级：
- P0：事实、金额、法规、定性、证据链存在重大矛盾，提交前必须修改
- P1：问题排序、建议可操作性、评价边界、复核意见存在明显缺陷
- P2：表达、格式、口径说明、术语使用等可优化事项
- √：已核验通过，应列明通过项，避免重复复核
```

## 使用方式

### 场景一：纯报告复核

当用户说"帮我复核这份报告"、"审一下这个报告"、"检查报告质量"时：

1. **先确认报告类型**：经济责任审计 / 预算执行审计 / 专项审计 / 绩效评价 等
2. **根据报告类型推荐维度组合**
3. **询问用户优先级**：先跑哪几个维度？
4. **执行复核**：逐一维度运行提示词，汇总发现

### 场景一-B：三方材料齐全（报告+附表+取证单）

当用户同时提供了Word报告、Excel附表、取证单时：

1. **先建立索引**：以取证单编号为锚点，建立三方映射关系
2. **优先跑致命层**：⑪⑭⑮（数字打架/漏报/核心指标断点）→ 这三个任何一个出问题直接打回
3. **再跑证据层**：⑫⑬（结论有根/统计可靠）
4. **最后跑文本层**：①②③④⑤⑥⑦⑧⑨⑩（常规复核）

如果用户没给取证单清单（只有零散的扫描件），先提醒整理出"单号+问题摘要+金额"清单。没有索引的三方复核是低效的。

### 场景二：用户指定维度

当用户说"检查一下逻辑一致性"或"看看问题定性有没有问题"时，直接运行对应维度。

## 三方对应复核：报告(Word) ↔ 附表(Excel) ↔ 取证单

### 场景说明

审计报告复核最常见的真实场景不是审一份纯文本——而是三份材料交叉验证：

```
   Word报告正文           Excel附表数据         取证单（Word/扫描件）
  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
  │ 问题描述      │     │ 明细数据表     │     │ 单号: ZQ-001  │
  │ 定性结论      │     │ 汇总统计表     │     │ 问题: ...     │
  │ 金额引用      │     │ 分类汇总表     │     │ 金额: ...     │
  │ 取证单引用    │     │ 对比分析表     │     │ 证据: ...     │
  └──────────────┘     └──────────────┘     └──────────────┘
         ↕                    ↕                    ↕
         └────────────────────┼────────────────────┘
                     三方交叉核对
```

### 复核前准备

**第一步：统一提取**

将三份材料的关键信息提取为可比对的结构：

| 材料 | 提取内容 | 提取方式 |
|:-----|:---------|:---------|
| Word报告 | 全部段落文本 + 表格数据 | 直接复制粘贴或 Python docx 提取 |
| Excel附表 | 所有Sheet的关键列/行/汇总值 | 粘贴为文本表格，或 Python pandas 读取 |
| 取证单 | 单号、问题摘要、涉及金额、证据描述 | 逐份提取关键字段，汇总为清单 |

**第二步：建立索引**

以取证单编号为锚点，建立三方映射关系：

```
取证单编号 → 报告中的引用段落 → 附表中的数据位置
```

如果报告未引用取证单编号，先让AI从报告中提取"问题清单"，再与取证单清单做匹配。

### 三方复核优先级

```
紧急（报告提交前必做）
  ⑪ 报告↔附表数据一致性 ── 数字打架直接打回
  ⑭ 取证单→报告完整闭环 ── 漏报问题是最大风险

重要（复核出问题概率最高）
  ⑫ 报告↔取证单证据对应 ── 结论有根
  ⑮ 全链路追踪         ── 核心指标三环一致

补充（数据质量提升）
  ⑬ 取证单↔附表数据溯源 ── 统计基础可靠
```

## 核对引擎核心原则（借鉴 cross-document-auditor）

> 来源：GitHub [lennonli/cross-document-auditor](https://github.com/lennonli/cross-document-auditor)，MIT协议
> 这些原则从IPO跨机构底稿核对实战中提炼，可适配到政府审计三方复核场景。

### 四条防呆原则

| # | 原则 | 说明 | 审计场景对应 |
|:--|:-----|:-----|:------------|
| 1 | **禁止全文逐字对比** | 报告、附表、取证单的格式/行文完全不同，全文比对产生95%无效噪音 | 不要用Beyond Compare对比.docx和.xlsx；必须提取结构化字段后再比对 |
| 2 | **强制执行双向集合核查** | 清单类数据必须计算"A独有"和"B独有"的差集，单向检索必定漏报 | 取证单问题清单 vs 报告问题清单 → 两边都要算差集 |
| 3 | **禁止复杂表格扁平化** | 财务数据不能转为纯文本搜索，极易发生行列错位 | Excel附表必须保留[科目, 年度, 金额]三维坐标，不能"摊平"成纯文本 |
| 4 | **强制拦截重大性遗漏** | "A有B无"的信息不能机械忽略，须引入常识判断 | 取证单有但报告未写的问题，必须逐条评估是否属于重大遗漏 |

### 五步核对SOP（适配审计场景）

```
第一步：深度提取 ──→ 报告提取段落+表格 / 附表提取Sheet+行列 / 取证单提取字段清单
                          ⚠️ 保留结构，不能全摊平为纯文本
    │
    ▼
第二步：内部自洽   ──→ 同一份材料内部先排除矛盾
                          同一问题在报告不同章节的定性是否一致？
                          同一科目的金额在附表不同Sheet是否一致？
                          同一取证单的金额/日期在不同位置是否一致？
    │
    ▼
第三步：双向差集   ──→ 清单类数据必须两边都算
                          取证单问题集 - 报告问题集 = 疑为漏报
                          报告问题集 - 取证单问题集 = 疑为无据
                          报告金额集 - 附表金额集 = 疑为数据打架
                          附表科目集 - 取证单科目集 = 疑为归类错误
    │
    ▼
第四步：结构化对撞 ──→ 相同对象的相同属性做KV校验
                          [某项目, 违规金额] = 报告532.8万 vs 附表528.3万 vs 取证单536.1万
                          [某单位, 问题定性] = 报告"较重" vs 取证单"一般"
                          建立"实体别名词典"处理简称/全称不一致（如"XX局"↔"XX市XX局"）
    │
    ▼
第五步：重大性过滤 ──→ 对不一致项做三级分类，避免被琐碎差异淹没
                          P0级：实质性矛盾（金额不一致、定性相左、名录缺漏）
                          P1级：重大遗漏（有据无报、关键风险点未披露）
                          P2级：口径差异（含税/不含税、时间窗口差异）
```

### 四级输出分级体系

核查结果不应该是平铺的"问题清单"，而应该按严重程度分级输出，让复核人一眼看到要害：

| 等级 | 定义 | 审计场景示例 | 处置要求 |
|:-----|:-----|:------------|:---------|
| **P0 实质性矛盾** | 三方数据互斥，存其一必否其二 | 报告写"违规金额532.8万"，附表汇总528.3万，取证单加总536.1万 | 🔴 立即打回修改，不可提交 |
| **P1 重大遗漏** | 该有但没有，影响报告完整性 | 取证单记录了5笔政府采购规避招标，报告只提了2笔 | 🔴 强制补入报告 |
| **P2 口径差异** | 有差异但可解释 | 报告按"项目口径"统计，附表按"年度口径"统计，导致数字不同 | 🟡 补充口径说明即可 |
| **√ 验证通过** | 已严格核对且100%一致 | "经核对，报告中12处金额引用均与附表一致" | 🟢 列示清单，给予审查安全感 |

> ⚠️ 输出报告时，必须列出√级验证通过项。只列问题不列通过项，会让审查者产生"全篇都有问题"的错觉，降低复核效率。

### 实操建议

1. **别一次全跑**：三方五维度全部跑一遍太耗时。按优先级分层：先⑪+⑭（防打回和漏报），有问题再展开⑫⑬⑮。
2. **先内后外，再双向**：①先在每份材料内部做自洽检查 → ②再做报告↔附表/报告↔取证单正向对应 → ③最后做反向差集（取证单→报告）。这个顺序能避免"拿着矛盾数据去对比，越比越乱"。
3. **取证单先做清单化**：如果取证单是扫描件/图片，先用OCR或手工整理出"单号+问题摘要+金额"清单，再喂给AI。
4. **Excel附表保留结构**：提取关键Sheet的关键行列，保留[科目, 年度, 金额]三维坐标作为文本表格嵌入提示词。不要"摊平"成纯文本，否则行列错位是必然的。
5. **建别名词典**：三方材料对同一单位的称呼可能不同（"XX局""XX市XX局""被审计单位"），先统一命名再对撞，否则会出现大量假阳性差异。
6. **金额差异分级处理**：
   - 尾差（<0.01%）→ 标注即可，通常可接受
   - 小差异（0.01%-1%）→ 查四舍五入和口径
   - 大差异（>1%）→ 🔴 P0级，必须追溯到原始凭证
7. **建立索引是前提**：三方材料之间如果没有统一的编号体系（取证单号↔报告引用号↔附表行号），先花时间建索引，不然AI也找不到对应关系。
8. **输出必须含√级**：每次复核输出必须包含"已验证通过项"清单，给后续审查者提供安全感，也防止重复劳动。
