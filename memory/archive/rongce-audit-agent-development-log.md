### 待实施阶段细化（2026-07-21更新）

#### 反馈学习 8d — 知识保鲜 + 自演进

参考阿里技术《面向复杂业务场景的智能分析 Skills 架构设计与演进实践》的设计范式，补充融策审计智析的知识生命周期管理能力。

**背景问题**：
- 当前知识库（法规/司法解释/审计方法模板）全部手动维护，缺少系统化的更新机制
- Agent运行时产生的用户纠错、追问等信号未被采集利用
- 同一个业务事实（如某条款的适用范围）可能在多个文件中被引用，修改一处漏掉其他处会导致版本不一致

**核心设计原则**（借用阿里文章第六条原则）：
> Token 经济性是架构的硬约束。每一个设计决策都要回答“这会消耗多少 context 窗口”。
> 反馈机制应该是轻量级的后台进程，不是另一个推理任务。—— 弱模型友好

##### ① 知识保鲜机制（评测闭环）4d

知识分层（阿里原则二：按变更频率分层）：
- **稳定层**（低频变更）：政策法规库、司法解释、会计准则、行业规范 — 文件级管理
- **时效层**（高频变更）：审计方法模板（AP/AR/EXP/FA）、检测规则（围标串标/关联交易）、工具参数

六步更新流程（对标阿里团队的 Eval→Diagnose→Register→Review→Re-eval）：

| 步骤 | 内容 | 产出 |
|------|------|------|
| 评测 | 定期用标准评测题集验证 Agent 各模块输出质量 | 差距清单（哪题错→错在哪） |
| 诊断 | 基于差距清单分析根因、影响范围、优先级 | 修改计划 |
| 登记 | ⚠️ 修改前先登记：旧值→新值→波及文件列表 | 变更登记表 |
| 修改 | 按计划执行知识更新 | 修改后的文件 |
| 校验 | 扫描所有知识文件，检查旧值已清除、新值到位、无残留 | 校验报告 |
| 复测 | 跑同一套评测题，验证分数提升，检查回归问题 | 评测对比报告 |

登记环节是关键创新点（阿里原文强调过）：同一法规条款可能在RAG库、Agent KB、底稿模板等多处被引用，登记确保全局一致性。

**评测题集构建（3类）**：
1. 知识类 — 法规原文调用、口径定义问答
2. 分析类 — 套用审计方法的正确性
3. 综合类 — 跨模块、跨Agent的联合推理

##### ② 反馈自演进 4d

采集→候选区→晋升→固化 四阶段（阿里原文设计）：

| 阶段 | 机制 | 说明 |
|------|------|------|
| 采集 | 静默识别 | 用户纠错（"不对，应该是XX"）、追问补充（"你漏了XX"）、重复提问、放弃对话 — 全自动不打断用户 |
| 候选区 | 多次确认后才生效 | 同一类反馈累计N次后晋升；单次噪声不触发 |
| 晋升 | 从候选区→正式区 | 达到阈值后影响Agent行为 |
| 固化 | 从运行态→知识库 | 将高频修正沉淀为正式知识文件 |

**弱模型友好设计**：所有操作（信号识别、去重判断、晋升决策）用关键词匹配+规则判断实现，不消耗LLM推理资源。反馈机制是轻量级后台进程。

**审计场景的特殊信号**：
- 审计结论被用户直接否定（高价值信号）
- 引用法规条款被纠正（知识层更新信号）
- 分析方法选择被手动调整（方法层路由优化信号）
- 用户反复使用同一对话模板（高频场景，可考虑固化到模板层）
