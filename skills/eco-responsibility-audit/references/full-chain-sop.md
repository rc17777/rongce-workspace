# 融策8环节全链条SOP（实操级）

> 来源：宁津县审计局8环节全链条模式 + 济南"双主审"模式 + 融策已有工具技能
> 版本：v1.0 | 2026-05-31
> 适用：经济责任审计 / 预算执行审计 / 专项资金审计

---

## 体系总览

```
政策法规 → 审计方法 → 数据采集 → 数据分析 → 疑点核查 → 问题落实 → 问题反馈 → 数据归档
   └─── 法规库 ──┘ └─── 工具链 ──┘ └─── 规则库 ──┘ └─── 整改库 ──┘ └─── 知识库
```

---

## 环节一：政策法规（定依据）

### 做什么
在项目开始前，梳理该项目适用的全部法规依据，建立"法规包"。

### 谁做
数据主审 + 业务主审联合

### 输入
- 审计项目类型（预算执行/经济责任/专项资金/绩效）
- 被审计单位行业（教育/医疗/物业/投资）
- 项目时间范围

### 输出
《项目法规包》— 按审计类型分组的法规清单，每个法规标注重点条款

### 操作步骤

| 步骤 | 操作 | 工具 |
|------|------|------|
| 1.1 | 匹配审计类型 → 调取对应法规目录 | AuditKB wiki/rules/ + index.md |
| 1.2 | 匹配行业 → 调取行业法规 | AuditKB wiki/fields/ |
| 1.3 | 逐条检查：法规是否仍在有效期 | 检索废止/修订公告 |
| 1.4 | 标记本项目的"红线条款"（违反即追责） | 红色标注 |
| 1.5 | 输出《项目法规包》 | 审计工作底稿附件 |

### 融策工具对接

| 法规来源 | 对接方式 | 使用场景 |
|---------|---------|---------|
| AuditKB法规库 | 直接读取 | 常用审计法规（审计法/政府采购法/预算法） |
| audit-law-check skill | 输入问题描述→自动匹配法规条款 | 需要快速引法规时 |
| smart-audit-builder RAG | 语义检索+法规出处引用 | 查新法规或不常用的条款 |
| rongce-gov-audit regulations-database | 读取常用法规完整条款 | 底稿引用需要完整条款时 |

### 避坑指南
- ❌ 不要只依赖一个法规库 → ✅ 交叉比对多个来源
- ❌ 不要引用已被废止的法规 → ✅ 审计法规快速看时效性
- ❌ 经济责任审计不要漏了《规定》（2019年7月中办国办印发）

## 环节二：审计方法（定方案）

### 做什么
根据法规包，制定具体的审计方法和程序清单。

### 谁做
业务主审主导，数据主审提数据分析可行性意见

### 输入
- 环节一的《项目法规包》
- 项目基本信息和时间表
- 被审计单位业务特点

### 输出
《审计实施方案》— 包含检查程序、取证方法、数据分析方案、时间安排

### 操作步骤

| 步骤 | 操作 | 工具 |
|------|------|------|
| 2.1 | 按审计目标拆解为若干个"检查方向" | eco-responsibility-audit/focus.md |
| 2.2 | 每个方向匹配审计方法（程序性+数据性） | audit-sop-master skill |
| 2.3 | 标注"哪些可以用数据验证、哪些只能人工核查" | 数据主审做可行性评估 |
| 2.4 | 设计数据需求清单（需要哪些表、哪些字段） | 模板式发出数据采集通知 |
| 2.5 | 确定疑点阈值（多大金额/偏差算异常） | 参照AuditKB规则库 |

### 融策工具对接

| 场景 | 工具 |
|------|------|
| 生成底稿模板 → | eco-responsibility-audit/working-papers.md 或 rongce-gov-audit/templates.md |
| 生成审计方案 → | eco-responsibility-audit/audit-plan.md |
| 查SOP规范 → | audit-sop-master skill |
| 生成访谈提纲 → | eco-responsibility-audit/interview-guide.md |

### 避坑指南
- ❌ 方案定得太粗（"检查预算执行情况"— 查什么、查哪个时间、用什么标准？）
- ✅ 方案要落到具体数据表和字段：例如"检查'三公经费'科目，与预算批复逐笔比对，超预算20%标红"
- ❌ 数据需求发得太笼统（"请提供财务数据"）
- ✅ 数据需求要明确文件名、表名、字段、时间范围、格式要求

## 环节三：数据采集（拿数据）

### 做什么
从被审计单位获取所需数据，完成清洗、校验、入库。

### 谁做
数据主审执行，业务主审确认数据是否齐全

### 输入
- 环节二的《数据需求清单》
- 被审计单位提供的原始数据

### 输出
标准化后的《项目数据集》（清洗版+原始版分开存储）

### 操作步骤

| 步骤 | 操作 | 工具 | 耗时参考 |
|------|------|------|---------|
| 3.1 | 发出正式数据采集通知 | 数据需求清单（环节2产出） | 0.5天 |
| 3.2 | 接收数据 → 初步校验完整性 | 缺字段、缺记录、格式错误检查 | 0.5-1天 |
| 3.3 | 数据清洗（缺失值/异常值/格式统一） | audit-data-analyst Python模板 | 0.5-1天 |
| 3.4 | 数据标准化（字段名统一+日期格式统一+编码映射） | Python pandas脚本 | 0.5天 |
| 3.5 | 数据质量评估 → 输出《数据质量报告》 | audit-data-quality skill | 0.5天 |
| 3.6 | 数据入库（原始版+清洗版分开存储） | `audit_data_schema.py` | 0.5天 |

### 常见数据来源（政府审计项目）

| 数据类型 | 来源 | 常见格式 | 处理难点 |
|---------|------|---------|---------|
| 财务账套 | 财政一体化系统导出 | Excel/DBF/access | 编码不统一、科目体系不同 |
| 业务数据 | 业务系统导出 | CSV/Excel/数据库SQL | 字段含义不清、关联键缺失 |
| 预算批复 | 财政批复文件 | PDF/Word | 非结构化需手动录入或OCR |
| 合同/招投标 | 采购平台/文档归档系统 | PDF/扫描件 | OCR质量影响数据准确性 |
| 人员信息 | 人事系统/编办 | Excel/数据库 | 脱敏要求高，权限控制严 |
| 会议纪要 | 秘书处归档 | PDF/Word | 阅后即焚式记录，需尽早取到 |

### 避坑指南
- ❌ 拿到了直接开始分析 → ✅ 必须先做数据质量评估
- ❌ 只拿到了清洗版本 → ✅ 原始版+清洗版分开保存，方便追溯
- ❌ 不问清楚字段含义就开始用 → ✅ 先找业务人员确认每个字段的意思
- ❌ 等所有数据到齐才开工 → ✅ 边等边做先到数据的预处理
- ⚠️ 政府审计数据获取常有延迟，提前留出2-3天缓冲

## 环节四：数据分析（筛疑点）

### 做什么
用规则库+算法+工具，对标准化数据全量扫描，输出疑点清单。

### 谁做
数据主审执行

### 输入
- 环节三的《项目数据集》（清洗版）
- AuditKB规则库（30条规则）
- 项目特定的分析阈值

### 输出
《疑点清单》— 每条疑点含：问题描述/涉及金额/涉及单位/风险等级/数据来源

### 操作步骤

| 步骤 | 操作 | 工具 | 产出 |
|------|------|------|------|
| 4.1 | 匹配适用规则库 → 筛选与本项目相关的规则 | AuditKB index.md | 项目规则子集 |
| 4.2 | 运行规则1：预算执行偏离度 → 预算vs决算比对 | Python脚本 | 偏离度清单 |
| 4.3 | 运行规则2：三公经费超标 → 逐笔vs预算比对 | Python脚本 | 超标清单 |
| 4.4 | 运行规则3：往来款长期挂账 → 挂账>3年 | Python脚本 | 挂账清单 |
| 4.5 | 运行规则4...（根据项目类型继续） | 依次执行 | ... |
| 4.6 | 异常检测：Z-score/IQR/Benford（适用于大样本数据） | audit-anomaly-detect 或 benford_analysis.py | 异常值清单 |
| 4.7 | 重复检测：同一供应商/同一收款人/同一金额重复出现 | Python重复检测脚本 | 重复项清单 |
| 4.8 | 关联分析：跨表交叉比对（合同vs付款、发票vs验收） | SQL/Python JOIN | 不匹配项清单 |
| 4.9 | 人工复核：数据主审逐条确认疑点有效性 | 人工判断 | 有效疑点+无效疑点（标注原因） |
| 4.10 | 疑点分级：按风险等级标注🔴🟡🟢 | 自动+人工 | 分级疑点清单 |

### 输出格式要求

每条疑点清单应包含：
```
[风险等级] 疑点描述
- 涉及单位/部门：XXX
- 涉及金额：¥XXX,XXX.XX
- 具体情况：...（简要描述，引用具体数据行）
- 数据来源：XXX表，行XXX
- 分析规则：RULE-XXX（链接到规则定义）
- 置信度：高/中/低（自动判定+人工确认）
```

### 避坑指南
- ❌ 不区分"有异常的疑点"和"真的能定性的问题"
- ✅ 疑点清单是"可能性"，不是"结论"，需要人工核查
- ❌ 把所有分析结果一股脑输出
- ✅ 宁津经验：疑点覆盖率92%，但只有7-15%的疑点最终变成审计问题
- ❌ 分析结果用技术术语（"Z-score=3.2，p<0.01"）
- ✅ 翻译成业务语言（"该供应商收款频次是行业平均的3倍"）

## 环节五：疑点核查（去现场）

### 做什么
数据主审输出疑点清单后，业务主审到现场逐条核实，补齐证据链。

### 谁做
业务主审主导，数据主审提供数据支撑

### 输入
- 环节四的《疑点清单》（已分级）
- 被审计单位的业务凭证/原始单据/访谈记录

### 输出
《问题确认表》— 每个疑点的核查结果（确认属实/排除/需补充）

### 操作步骤

| 步骤 | 操作 | 工具 | 时长参考 |
|------|------|------|---------|
| 5.1 | 疑点优先级排序（先查🔴高风险的，再查🟡🟢） | 疑点清单的风险等级排序 | 0.5h |
| 5.2 | 到疑点单位现场核实（调取原始凭证、业务档案） | 现场核查 | 2-5天 |
| 5.3 | 访谈关键岗位人员（了解业务背景和操作流程） | eco-responsibility-audit/interview-guide.md | 0.5-1天/场 |
| 5.4 | 补充取证（拍照、复印、截屏、签字确认） | audit-evidence-three-point skill | 随核查进行 |
| 5.5 | 确认：疑点属实 → 转为审计问题；疑点被排除 → 标注排除原因 | 人工判断 | 每个疑点10-15min |
| 5.6 | 每个问题补充：违反的法规条款（精确到条） | 回查环节一的法规包 | 随确认进行 |
| 5.7 | 证据链完整性检查（三个点齐全：问题描述+法规依据+佐证材料） | audit-evidence-three-point skill | 随确认进行 |

### 证据链三要素（audit-evidence-three-point skill）

```
问题描述                   法规依据                   佐证材料
"XX单位2023年三公经费      = 《预算法》第XX条       = 原始凭证复印件
实际支出XX万元，超预算     + 预算批复文件             + 预算执行台账
XX%，超支XX万元"           + 该单位财务制度           + 财务人员签字确认
```

### 核查常见场景及应对

| 场景 | 应对 |
|------|------|
| 被审计单位说"系统问题导致数据不准" | 要求提供证明材料+说明具体原因 |
| 被审计单位说"已整改" | 要求现场验证整改效果，不看书面报告 |
| 被审计单位不配合 | 保留沟通记录，上报审计组负责人 |
| 线索指向上级单位或外单位 | 如实记录，通过审计机关协调调取 |

### 避坑指南
- ❌ 只听一面之词 → ✅ 交叉验证：找不同的人聊同一个事
- ❌ 只看书面材料 → ✅ 现场看原始实物流转过程
- ❌ 觉得"查得差不多了"就收工 → ✅ 每份疑点都要有明确的"确认/排除"结论

## 环节六：问题落实（定结论）

### 做什么
将已经确认属实的问题，逐条定性和定责。

### 谁做
业务主审主导，必要时主审计师/组长介入

### 输入
- 环节五的《问题确认表》
- 环节一的法规包（精确到条款号）

### 输出
《审计发现问题汇总表》— 带定性和定责的最终结论

### 操作步骤

| 步骤 | 操作 | 评估维度 |
|------|------|---------|
| 6.1 | 问题定性：属于哪类问题 | 预算执行/三公经费/采购违规/资产流失/决策违规... |
| 6.2 | 问题分级：按严重程度 | 🔴重大/🟠较重/🟡一般/🟢轻微 |
| 6.3 | 责任认定：直接责任/主管责任/领导责任 | 依据经责审计规定 |
| 6.4 | 金额确认：损失/违规/挪用金额 | 精确到元 |
| 6.5 | 交叉审核：另一个审计人员复核 | 减少个人判断偏差 |
| 6.6 | 汇总输出：《审计发现问题汇总表》 | 标准格式 |

### 问题定性参考（参照 gov-audit-problem-classify skill）

```
经责审计常见问题类型：
├── 预算执行类（超预算、无预算支出、预算调整不合规）
├── 三公经费类（超标准、超范围、虚假发票报销）
├── 采购类（未公开招标、串标围标、拆分采购）
├── 资产类（资产流失、资产闲置、处置程序缺失）
├── 决策类（未集体研究、违规决策、造成损失）
├── 专项资金类（挪用、虚报、截留、超期闲置）
└── 内控类（制度缺失、执行流于形式、不相容岗位未分离）
```

### 避坑指南
- ❌ 问题定性太模糊（"管理不规范" → 具体是哪个环节不规范？）
- ✅ 定性要精确到：违反什么规定、什么行为、造成什么后果
- ❌ 责任认定一刀切要求"追究责任"
- ✅ 区分主客观因素：制度不健全 vs 明知故犯
- ❌ 问题的金额只算大概 → ✅ 每个问题的金额精确到元

## 环节七：问题反馈（出报告）

### 做什么
将已落实的问题形成审计报告和整改要求，反馈给被审计单位。

### 谁做
业务主审撰写，组长审核，数据主审提供数据复核

### 输入
- 环节六的《审计发现问题汇总表》
- 环节一的法规包（引用条款）
- 审计报告模板

### 输出
- 审计报告（正文）
- 审计决定书（需要追究的）
- 整改要求清单（随报告一并送达）

### 操作步骤

| 步骤 | 操作 | 工具 |
|------|------|------|
| 7.1 | 撰写审计报告初稿（问题+事实+依据+结论） | audit-report-structured 或 audit-report-writer skill |
| 7.2 | 每个问题标注"AI辅助生成/需人工复核" | 统一标注 |
| 7.3 | 组长审核：事实是否清楚、定性是否准确、依据是否充分 | 人工审核 |
| 7.4 | 审计组集体讨论 | 会议讨论 |
| 7.5 | 被审计单位征求意见（法定程序） | 按要求送达 |
| 7.6 | 根据反馈意见修改（确认/反驳/补充） | 整改反馈流程 |
| 7.7 | 出具正式审计报告+审计决定书 | 红头文件/正式用印 |
| 7.8 | 生成《审计发现问题及整改要求清单》 | rectification库 templates.md |

### 反馈时效要求

| 事项 | 时限 | 依据 |
|------|------|------|
| 征求意见稿送达 | 审计实施结束后10-15个工作日内 | 《审计法》 |
| 被审计单位反馈 | 收到征求意见稿后10个工作日内 | 《审计法》 |
| 正式报告出具 | 反馈处理后5个工作日内 | 内部要求 |

### 避坑指南
- ❌ 报告只有定性的描述没有定量的数据支撑
- ✅ 每个问题都要有：金额、笔数、期间、占比等量化数据
- ❌ 引用的法规条款不精确（"违反相关法律规定"→ 哪条？）
- ✅ 精确到法规名称+条款号+款项
- ❌ 写得太技术化（用AI分析的专业术语）
- ✅ 报告要能被审计单位看懂：语气专业但表达通俗

## 环节八：数据归档（留痕迹）

### 做什么
项目结束后，将所有数据、文件、规则、方法沉淀归档，完成知识固化。

### 谁做
数据主审主导归档，业务主审确认完整性，知识管理员（如需要）

### 输入
- 本项目所有产出物（环节三~七的全部输出）
- 审计底稿和工作记录

### 输出
完善后的 AuditKB 知识库（新案例+新规则+新经验）

### 操作步骤

| 步骤 | 操作 | 目标 | 工具 |
|------|------|------|------|
| 8.1 | 项目数据集归档 → `AuditKB/data/projects/{项目代号}/` | 可追溯可复现 | 目录结构标准 |
| 8.2 | 原始数据+清洗后数据+分析脚本+中间结果全量存档 | 便于后续复查 | Python脚本+CSV |
| 8.3 | 审计底稿扫描/整理 → 按问题编号归档 | 完整档案 | 电子扫描 |
| 8.4 | 审计报告（征求意见稿+正式稿+反馈意见）归档 | 历史可查 | PDF存档 |
| 8.5 | 检查本项目中是否有可沉淀的新规则 | 补充规则库 | 见下方规则沉淀检查表 |
| 8.6 | 检查本项目中是否有值得案例化的典型问题 | 补充案例库 | 见下方案例沉淀检查表 |
| 8.7 | 检查本项目中使用的分析方法是否可模板化 | 补充方法库 | 新增Python脚本/代码模板 |
| 8.8 | 编写《项目经验总结》 → 存入AuditKB | 组织学习 | audit-knowledge-card skill |
| 8.9 | 更新AuditKB index.md | 索引最新 | index.md新增条目 |
| 8.10 | 更新历史项目整改跟踪记录（如果尚未归档） | 闭环完成 | rectification库 |

### 规则沉淀检查表

```
每次项目结束后，逐条检查：
[ ] 这个项目中发现了新的异常模式？
    → 如果是 → 新建 RULE-XXX.md → 注册到 index.md
[ ] 这个项目验证了某条规则的有效性？
    → 如果是 → 更新该规则的"参考案例"字段
[ ] 这个项目推翻了某条规则的设定（误报太多）？
    → 如果是 → 调整规则的阈值或删除规则
[ ] 这个项目中有3个以上同类问题但没对应规则？
    → 如果是 → 新建一条通用规则
```

### 案例沉淀检查表

```
每次项目结束后，逐条检查：
[ ] 这个项目有没有值得写案例的典型问题？
    → 关键标准：1）问题新颖；2）发现方法有特色；3）整改效果好
[ ] 这个案例的"发现过程"是否能被其他人复制？
    → 关键：不只是写结论，要写"怎么发现""用了什么数据""用了什么方法"
[ ] 这个案例的法规引用是否精准？
    → 关键：每条结论都要有对应的法规条款
```

### 方法沉淀检查表

```
每次项目结束后，逐条检查：
[ ] 这个项目新写了分析脚本/Python代码？
    → 如果是 → 模板化 → 存入 skill 的 references/ 目录
[ ] 这个项目新配置了SQL查询模板？
    → 如果是 → 标准化 → 存入 audit-data-analyst SQL场景库
[ ] 这个项目修改了底稿模板？
    → 如果是 → 更新模板 → 更新对应 references 文件
[ ] 这个项目踩了什么坑？
    → 如果是 → 记录到本文件的避坑指南中
```

### 避坑指南
- ❌ 项目结束了就不归档了 → ✅ 项目结束后7个工作日内必须完成归档
- ❌ 归档 = 把文件塞到一个文件夹 → ✅ 按标准目录结构+命名规范
- ❌ 只归档最终报告，不归档中间过程和原始数据 → ✅ 全部留存
- ❌ 沉到个人笔记里就完了 → ✅ 必须沉淀到团队共享的AuditKB
