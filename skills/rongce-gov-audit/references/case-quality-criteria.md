# 审计案例质量标准——与融策9大方法模块融合

> 来源：审计实践公众号《审计人最怕的不是查不出问题，而是年底写总结时发现：那些查出来的问题，没一个能写进案例》
> 融合时间：2026-07-17
> 用途：在9大方法模块中嵌入案例质量闸门，让"查问题"自动导向"产案例"

---

## 为什么需要这个融合

融策9大方法模块定义了**怎么做审计**。这篇文章定义了**审计做完后什么值得留下来**。

两者的关系：
- 9大模块 = 生产线（前中后台协同、作业验证、持续监测……）
- 5条案例标准 = 质检闸（不是什么产出都进知识库，只有合格的才能入库）

融合后的效果：在审计执行过程中就带上"案例思维"，让高质量案例从"运气"变成"必然"。

## 五条案例标准→融策模块映射

### 标准一：能暴露系统性漏洞

**原文精要**：
> "这个人做错了" vs "这套制度让谁来做都会错"。前者不值得写，后者是绝佳案例素材。

**融策模块映射**：

| 对应模块 | 如何嵌入 | 具体动作 |
|---------|---------|---------|
| **模块① 前中后台协同** | 中台分析时增加"根因追问"环节 | 每个异常不满足于"谁违规"，必须追问"为什么能违规" |
| **模块④ 作业验证** | 模型输出的疑点增加"根因分类"标签 | `偶发失误` vs `制度漏洞`，后者自动标记为案例候选 |
| **模块⑤ 关口前移** | 发现制度漏洞后自动触发制度修订建议 | 不是等到报告里提，而是发现时就写《制度风险提示》 |

**融合后的操作指引**：

```
异常发现 → 三问根因：
  Q1: 这个问题是这个人特有的，还是换了谁在这个岗位都可能发生？
  Q2: 制度里有没有能堵住这个漏洞的条款？（有但没执行 vs 根本没有）
  Q3: 同类的漏洞在别的单位/部门会不会也存在？
  
  如果Q1="换了谁都可能"+ Q2="根本没有" → 🔴 案例候选
  如果Q1="这个人特有"+ Q2="有但没执行" → 🟡 普通问题
```

**案例模板**（丁某挪用公款1800万）：
- 错误写法："丁某违规挪用公款"——这是个人问题
- 正确写法："一把手兼任下属企业负责人+无大额资金双签制度+代理记账不附银行对账单 = 系统性制度漏洞"——这是案例

### 标准二：涉及新领域、新风险

**原文精要**：
> "业务跑在了制度前面"，旧规则在失效，新规则还没建立——每一个新发现都可能成为全行业风向标。

**融策模块映射**：

| 对应模块 | 如何嵌入 | 具体动作 |
|---------|---------|---------|
| **模块⑥ 模型探索隔离** | 新领域发现直接进入开发环境 | 不套用旧规则，先建探索模型再验证 |
| **模块② 持续监测** | 新领域加入监测范围 | 一旦确认是新风险类型，加入季度监测清单 |
| **模块⑨ 监管信息采集** | 新领域触发政策扫描 | 发现新领域风险后，自动搜索该领域的法规空白/最新政策 |

**融合后的操作指引**：

```
遇到新业务/新领域审计时：
  1. 先问：有没有现成的制度依据？（有→对照审 / 没有→做记录）
  2. 制度空白本身就是一个发现："目前XX业务在XXX环节无明确制度约束"
  3. 完成的审计程序+发现的风险点 = 天然案例素材
  
  注意：新领域案例的价值不在于问题大小，而在于"填补空白"
```

**情景案例**：
智能投顾算法参数无审批→这个发现的价值是它定义了"AI治理审计"这个新品类的问题，后续所有涉及AI系统的审计都可以复用这个框架。

### 标准三：审计手法巧妙

**原文精要**：
> "原来还能这么审"的顿悟感。街景回溯揭穿摆拍、试剂耗材反推实验真实性——跨领域技术应用于审计。

**融策模块映射**：

| 对应模块 | 如何嵌入 | 具体动作 |
|---------|---------|---------|
| **模块④ 作业验证** | 发现方式标注为"创新方法" | 人工核查后记录："本疑点使用XX创新方法发现" |
| **模块⑥ 探索→生产** | 创新方法验证通过后固化为规则 | 同样的手法在≥2个项目验证有效→写入规则库 |
| **模块⑧ 可视化** | 创新方法的逻辑过程做可视化 | 画流程图让同行看懂"怎么想到的""怎么做到的" |

**融合后的操作指引**：

```
审计方法创新检查表：
  □ 这个方法是否跨领域？（地图→审计、化学试剂→审计、门禁数据→审计）
  □ 这个方法是否可以被复用？（换成别的场景也能用）
  □ 这个方法是否突破了常规审计手段？（不是翻凭证/看合同/问经办人）
  
  3项都打勾 → 🔴 方法型案例（重点不是问题大小，是方法巧妙）
```

**融策已有方法型案例对应**：

| 已有案例 | 方法创新点 | 对应标准 |
|---------|-----------|---------|
| 教科院附中串标 | PDF元数据提取设备指纹 | ✅ 跨领域技术应用 |
| 金川医保分解住院 | 入院≤3天+同病种7日内再入院 | ✅ 可复用的SQL规则 |
| 街景回溯（文中案例） | 地图历史影像比对验收照片 | ⬜ 待实践 |
| 试剂反推（文中案例） | 耗材采购量反推实验真实性 | ⬜ 待实践 |

### 标准四：推动制度性整改

**原文精要**：
> 终极价值不是查出多少违规金额，而是推动了什么样的组织变革。让一套制度重生。

**融策模块映射**：

| 对应模块 | 如何嵌入 | 具体动作 |
|---------|---------|---------|
| **模块① 后台沉淀** | 整改案例写入AuditKB整改库 | 跟踪：审计建议→制度修订→同类问题归零 |
| **模块⑤ 关口前移** | 制度修订后更新监测规则 | 新制度生效后，旧问题的监测规则可以移除 |
| **模块⑦ 智能文书** | 审计建议模板内置"制度修订建议"区块 | 每个报告的问题→对应一个具体的制度修订条款 |

**融合后的操作指引**：

```
问题的三层价值判断：
  L1 "治标"：追回资金/处罚个人 → 只写进问题清单
  L2 "治病"：修补单个制度条款 → 写进审计报告
  L3 "治根"：推动整套制度体系调整，同类问题从此消失 → 📌 写进案例
  
  判断标准：这个问题下一年还会不会再出现？
  会 → 整改不到位，继续跟进
  不会 → 制度改了、漏洞堵了 → 这就是案例素材
```

**虚构案例→真实能力对照**：
文章中的"集团资金集中管理矛盾→修订制度→同类问题彻底消失"这个逻辑，放到融策场景就是：
- "两新补贴同一商家被多地重复申报"→修订申报核验流程→所有地市上线统一核验→问题归零

### 标准五：具有普适性和可推广性

**原文精要**：
> 一个审计发现如果能提炼出一套可复用的审计程序，它的价值就从"一个问题的解决"升级为"一类风险的系统排查"。

**融策模块映射**：

| 对应模块 | 如何嵌入 | 具体动作 |
|---------|---------|---------|
| **模块④ 模型反哺** | 验证后的方法写入规则库 | 差旅×门禁→推广到会议费/培训费/招待费 |
| **模块② 持续监测** | 可推广方法加入季度体检清单 | 每个季度自动跑一次这个方法 |
| **模块③ 双维考核** | 知识贡献度计分 | 一个方法被≥3个项目复用→加分 |

**融合后的操作指引**：

```
可推广性检验表：
  □ 这个方法换个审计对象还能用吗？
  □ 这个方法换个审计类型还能用吗？
  □ 这个方法换个行业还能用吗？
  □ 这个方法能不能写成"输入A→处理B→输出C"的标准流程？
  
  推广度分级：
  4项全打勾 → 通用型案例（跨类型、跨行业可用）🔴
  2-3项打勾 → 领域型案例（同一领域内可复制）🟡
  0-1项打勾 → 项目型案例（仅本项目参考）🟢
```

## 融合后的工作流：带"案例意识"做审计

### 完整闭环

```
┌──────────────────────────────────────────────────────────────────┐
│                      融策审计案例生产线                            │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ① 审前（模块①前中后台）                                          │
│     ├─ 查：这个被审计单位/领域以前出过什么案例？                    │
│     └─ 预判：本项目最可能产出什么类型的案例？                       │
│                         ↓                                        │
│  ② 审中（模块④作业验证+模块⑥探索隔离）                             │
│     ├─ 每个发现打"案例潜力分"（1-5分）                             │
│     ├─ 4分以上的发现：额外做"根因追问"+"方法记录"+"推广性评估"       │
│     └─ 创新方法：记录完整的发现过程（不是只记结果）                  │
│                         ↓                                        │
│  ③ 审后（模块①后台沉淀+模块⑦智能文书）                             │
│     ├─ 案例潜力≥4分的发现 → 按本文5标准逐一打分                     │
│     ├─ 满足≥3条的 → 正式入库AuditKB案例库                          │
│     └─ 不满足的 → 作为普通问题归档，不浪费精力包装                   │
│                         ↓                                        │
│  ④ 持续（模块②持续监测+模块③双维考核+模块⑤关口前移）                │
│     ├─ 入库案例的方法 → 固化为监测规则                             │
│     ├─ 入库案例的整改 → 跟踪是否真改了                              │
│     └─ 团队成员的案例产出 → 纳入知识贡献考核                        │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 每个发现都打"案例潜力分"

| 分数 | 标准 | 动作 |
|------|------|------|
| ⭐⭐⭐⭐⭐ 5分 | 同时满足≥3条标准 | 立即启动案例编写流程，指定负责人 |
| ⭐⭐⭐⭐ 4分 | 满足2条标准 | 补充调查和证据，看能否升到5分 |
| ⭐⭐⭐ 3分 | 满足1条标准 | 在底稿中标注，项目结束后复核 |
| ⭐⭐ 2分 | 部分满足1条 | 普通审计发现，正常写入报告 |
| ⭐ 1分 | 零满足 | 操作瑕疵，列为管理建议，不值得写成案例 |

## 对AuditKB入库规范的更新建议

结合原有入库规范（必须包含"发现问题逻辑链"），新增以下检查项：

### 入库前5问（新增）

```
1. 这个案例满足了5条标准的哪几条？   → 标注在frontmatter
2. 这个案例的"不可替代性"是什么？     → 换成别的审计组也能发现吗？
3. 这个案例的方法能被复制吗？         → 检查方法是否有标准化描述
4. 这个案例推动了什么改变？           → 不是问"查出多少钱"而是"改变了什么制度"
5. 下个项目怎么用这个案例？           → 写一个"复用指引"
```

### Frontmatter 新增字段

```yaml
case_quality:          # 案例质量评分
  systemic: true        # 标准1：是否暴露系统性漏洞
  new_domain: false     # 标准2：是否涉及新领域/新风险
  clever_method: true   # 标准3：审计方法是否巧妙
  institutional_fix: true # 标准4：是否推动了制度性整改
  replicable: true      # 标准5：是否具有普适可推广性
  total_score: 4        # 满足条数
  case_potential: 5     # 案例潜力分 1-5
```

## 速记卡：五条标准一句话版

| # | 标准 | 一句话判断 | 反例 |
|---|------|-----------|------|
| 1 | 系统性漏洞 | 换了谁来都会错？ | 张三忘了签字——换个人就不会 |
| 2 | 新领域/新风险 | 以前审过这种吗？ | 第N次查出预算超支 |
| 3 | 手法巧妙 | 同行看完会"拍大腿"吗？ | 翻凭证翻出来的常规问题 |
| 4 | 制度性整改 | 改了之后还会再犯吗？ | 罚款了事，下次照旧 |
| 5 | 普适可推广 | 换个项目还能用吗？ | 只在这个单位特有的个别问题 |
