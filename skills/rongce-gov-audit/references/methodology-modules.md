## 模块一：前中后台协同模型

### 通用架构

```
前台（采集/核查）         中台（分析/建模）          后台（沉淀/优化）
      │                        │                        │
 审计人员                 数据主审                  AuditKB
 ├─ 数据采集            ├─ 规则匹配              ├─ 规则沉淀
 ├─ 现场核查            ├─ 模型运行              ├─ 案例沉淀
 ├─ 访谈取证            ├─ 疑点输出              ├─ 方法模板化
 └─ 问题确认            └─ 模型优化              └─ 制度优化
```

### 不同审计类型的适配

| 审计类型 | 前台 | 中台 | 后台 |
|---------|------|------|------|
| **经济责任审计** | 核查领导干部履职情况 | 预算执行/三公经费/决策合规性规则 | 经责审计规则库扩充 |
| **预算执行审计** | 核对预算执行偏差 | 偏离度分析+异常支出检测 | 预算审计模板标准化 |
| **专项资金审计** | 核实资金使用去向 | 资金流向追踪+使用合规性检查 | 专项资金案例沉淀 |
| **绩效审计** | 现场评价项目效果 | 投入产出分析+目标完成率比对 | 绩效指标体系完善 |
| **采购审计** | 核查采购流程文件 | 串标检测+围标分析+报价异常 | 采购规则库扩充 |

### 使用方式
- 项目启动时：确定前台（谁做现场）、中台（谁做分析）、后台（谁做归档）的角色分配
- 项目进行中：前台->中台->后台形成反馈闭环
- 项目结束后：后台的沉淀物自动供下一个项目的前中台使用

## 模块二：持续监测制（从项目制→监测制）

### 通用逻辑

```
传统：审计组进驻 → 翻查资料 → 发现疑点 → 核查 → 走人 → 下次再来
                          ↓
持续监测：先跑一遍规则 → 输出疑点清单 → 带疑点进场 → 针对性查 → 更新规则
```

### 不同审计类型的持续监测方式

| 审计类型 | 监测范围 | 监测频次 | 监测方式 |
|---------|---------|---------|---------|
| **经济责任** | 任期内预算/收支/资产变动 | 季度 | 运行规则库→疑点清单→季度预警函 |
| **专项资金** | 资金拨付→使用→验收全流程 | 月度（大额实时） | 资金流向追踪脚本 |
| **采购审计** | 中标公告+新开标项目 | 月度 | 爬虫抓取中标信息+串标规则检测 |
| **预算执行** | 部门预算执行进度 | 季度 | 偏离度分析+异常支出检测 |
| **投资审计** | 在建项目进度款支付 | 月度 | 进度款vs完工比例匹配 |

### 落地工具
- 现有：AuditKB 30条规则库 + Python脚本定时执行
- 扩展方向：设置季度/月度的审计数据"一键体检"（对标宁津104个模型）
- 输出格式：《持续监测快报》— 标注新增疑点、持续异常、已关闭

## 模块三：双维考核（结果+模型贡献度）

### 考核维度

```
项目完成度（60%）               知识贡献度（40%）
 ├─ 发现问题数量/质量          ├─ 新增规则条数
 ├─ 报告按期交付              ├─ 新增分析脚本/模型
 ├─ 客户满意度                ├─ 新增案例(含完整证据链)
 └─ 整改跟踪完成率            └─ 方法模板化/避坑经验
```

### 融策10人团队适配

| 角色 | 结果指标 | 知识指标 | 权重 |
|------|---------|---------|------|
| 资深CPA/项目组长 | 报告质量、客户评价、整改完成率 | 规则贡献、案例沉淀 | 60/40 |
| 数据分析师 | 疑点准确率、模型运行效率 | 脚本模板化、新增分析脚本 | 50/50 |
| 助理审计员 | 底稿规范性、数据采集完整 | 采集模板优化、避坑记录 | 70/30 |

### 落地方式
- 项目结束后：《项目知识贡献评估表》（与full-chain-sop.md的归档环节同步执行）
- 年底统计：各成员的知识贡献积分，作为绩效考核加分项

## 模块四：作业验证模型 + 模型反哺作业（双向优化机制）

### 循环流程

```
模型输出疑点 → 人工核查 → 确认/排除 → 反馈模型准确率 → 模型优化
   ↑                                                       │
   └─────────────────────────────────────────────────────────┘
```

### 指标定义

| 指标 | 计算公式 | 目标值 | 备注 |
|------|---------|-------|------|
| 模型疑点覆盖率 | 模型输出疑点数/总疑点数×100% | >80% | 宁津做到92% |
| 模型问题转化率 | 模型确认问题数/模型疑点数×100% | 15-30% | 太高说明规则太松，太低说明规则需调整 |
| 人工新增疑点率 | 人工补充疑点数/总疑点数×100% | <20% | 若太高说明规则覆盖不足 |

### 落地方式
- 数据分析师在疑点清单中标注：每个疑点是"模型发现"还是"人工补充"
- 项目结束后输出《模型效能评估表》
- 准确率<10%的规则 → 降级/删除/调整阈值
- 准确率>50%的规则 → 固化+推广

## 模块五：审计关口前移（事后→事中）

### 通用思路

```
传统：出问题了才去查 → 被动、损失已发生
                          ↓
事中监督：运行过程中就监控 → 主动、及时纠偏
```

### 不同审计类型的前移方式

| 审计类型 | 传统（事后） | 前移后（事中） |
|---------|------------|--------------|
| **经济责任** | 离任时才审，问题已成事实 | 任中季度体检，半年预警提示 |
| **专项资金** | 资金用完了才去查使用合规性 | 每笔大额资金拨付后7日内核查去向 |
| **采购审计** | 开标后/合同签订后去查 | 招标文件发布时预审参数设置是否指向特定厂商 |
| **预算执行** | 年终结算后看执行偏差 | 季度预算执行分析+超支预警 |

### 落地条件
- 需要：标准化数据采集渠道（数据按期报送或对接）
- 工具：季度规则运行脚本（已具备部分能力）
- 输出：《事中监督预警通知》— 超支/异常/违规行为的及时提醒

## 模块六：模型探索与应用隔离

### 通用架构

```
开发环境（workspace）               生产环境（项目级执行）
    │                                    │
 Python脚本开发                    已固化的脚本/规则
 AI模型调参                       AuditKB规则库中的成熟规则
 探索性数据分析                   标准化的SQL查询模板
 新规则/新方法验证                  已验证的问题定性模板
    │                                    │
    └───────────── 验证通过 → ──────────────┘
```

### 管理原则
- 新规则必须在开发环境下验证至少2个项目，确认转化率>15%后才固化到生产环境
- 生产环境的规则每次修改要记录变更日志（rule log.md）
- 开发环境的脚本不要直接用于项目数据（避免未验证的算法产生误导）

## 模块八：可视化仪表盘

### 当前能力
- 融策现状：Excel/Word报告输出，无实时可视化
- 可替代方案：直接使用Excel条件格式+数据透视表+图表
- 第三方工具：Power BI（免费桌面版）/ Apache Superset（开源）

### 最小可行方案
- 阶段一：用Excel的切片+条件格式做静态仪表盘（1周内可落地）
- 阶段二：用Python pandas+matplotlib生成PDF版数据仪表（已有部分能力）
- 阶段三：在OpenClaw内做定期数据汇总（通过cron定时输出）
