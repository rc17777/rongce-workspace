## 一、检测体系总览：17层+纵深防御

### 核心十二层（标准检测）

| 层级 | 检测维度 | 数据源 | 爆炸力 | 依赖条件 |
|:----|:---------|:-------|:------|:--------|
| L1 | 报价规律性 | 开标一览表/分项报价表 | 🔴铁证 | 需报价数据 |
| L2 | 投标IP/MAC | 电子交易系统后台日志 | 🔴铁证 | 需向代理机构调取 |
| L3 | 文本雷同(TF-IDF) | 技术标/商务标全文 | 🔴铁证 | 需文字层PDF或OCR |
| L4 | 图片/资源哈希 | PDF嵌入图片→感知哈希(DCT)/SHA256 | 🔴铁证 | PyMuPDF+PIL+scipy |
| L4-v2 | 感知哈希升级 | DCT+Hamming → 检测同图不同扫描版本 | 🔴铁证 | 0.80阈值, 128bit特征 |
| L5 | 元数据交叉 | PDF Author/Creator/Producer/CreationDate | 🔴铁证 | PyMuPDF提取 |
| L6 | 文档结构/字体 | PDF页面字体span统计 | 🟡强信号 | PyMuPDF提取 |
| L7 | 生成设备信息 | PDF Producer/扫描仪型号 | 🟡强信号 | PyMuPDF提取 |

| **L8-v2** | **图分析升级** | **对标Neo4j→networkx：1-4层穿透+双高中介/点度节点** | **🔴铁证** | **对标审计署太原办方法** |
| L9 | 保证金/资金链 | 银行汇款凭证+电子保函编号 | 🔴铁证 | 需向交易中心调取 |

| **L11-v2** | **FP-growth升级** | **替换Jaccard：置信度≥0.9+中标集中度≥0.8=职业陪标** | **🔴铁证** | **对标审计署太原办方法** |
| **L12** | **历史投标异常关联** | **历史IP/MAC/关联标记数据库** | **需建立历史异常标记库** |
| **L13** | **节资率分析+支持度/置信度** | **招标台账(控制价+中标价+投标人)** | **需历史招标台账数据** |
| **L14** | **最优围标人数** | **投标单位数=3~4** | **投标人数统计即可** |
| **L15** | **陪标专业户** | **投标次数前5%且中标=0** | **项目投标台账** |
| **L16** | **保证金同时缴纳** | **同项目时间差<10分钟** | **保证金缴纳记录** |
| **L17** | **经办人一致性** | **同项目负责人姓名/身份证相同** | **项目负责人信息** |
| **L18** | **硬盘/MAC/IP一致** | **硬盘特征码/MAC/公网IP** | **交易平台硬件特征码表** |
| **L19** | **评标专家违规** | **未回避/跨项目一致/签到异常** | **专家库+社保缴费表** | **🔴铁证** | **需建立历史异常标记库** |

### 纵深五层（数字取证级）

| 层级 | 检测维度 | 工具/方法 | 适用场景 |
|:----|:---------|:---------|:--------|
| D1 | WPS签名残留 | PDF全文搜索b'WPS'/b'wps' | 元数据被清除时 |
| D2 | JPEG量化表指纹 | DQT表提取+哈希比对 | 扫描件PDF的图像分析 |
| D3 | JPEG文件完整性 | FFD8/FFD9标记验证 | 检测PDF是否为"重新封装" |
| D4 | 像素分布统计 | RGB均值/标准差/偏度/边缘密度 | 检测扫描来源一致性 |
| D5 | 文件系统时间线 | stat(ctime/mtime/atime) + PDF内部时间戳 | 还原文件制作时序 |
| **D6** | **节资率箱线图** | **IQR异常检测+节资率低疑点表** | **竞争不足的围标信号** |
| **D7** | **支持度/置信度矩阵** | **投标人共现网络** | **长期联手围标集团** |
| **D8** | **提升度(Lift)分析** | **区分随机共现vs人为操纵** | **Lift>800为强关联** |
| **D9** | **评标专家社交图谱** | **专家-投标单位雇佣关系** | **利益冲突挖掘** |

## 二、项目类型分类与检测策略

### 类型A：小额服务采购（竞争性磋商/谈判）

**特征**：预算<100万、3-5家投标人、服务类标书
**案例**：艺术团采购（18万/3家）

**策略**：
1. L5元数据 → 最高优先级（小项目投标人常不自知保留原始元数据）
2. D1-D5纵深层 → 专门应对"元数据清除"行为
3. L4图片哈希 → 服务标书嵌入图片少，价值有限
4. L3文本雷同 → 常因扫描件限制无法执行
5. **特别注意**：竞争性磋商的"最后报价"单独提交，不在主响应文件中

### 类型B：货物采购（公开招标）

**特征**：预算100-500万、3-6家投标人、含报价明细表
**案例**：急救实训室（160万/3家）、校服采购

**策略**：
1. L5元数据 → 🔴最关键（.docx→PDF保留完整元数据链）
2. L1报价 → 分项报价表供应商品牌对比（查围标配套）
3. L3文本雷同 → 注意排除标准承诺函模板
4. L4图片 → .docx解压word/media比PDF更有效
5. L2投标IP → 电子交易系统有记录，须调取

### 类型C：大型工程监理（公开招标）

**特征**：预算大、投标人多（10-30家）、标书极长（1000-3000页）
**案例**：宿舍监理（6200万/22家）

**策略**：
1. **L3 TF-IDF → 最高价值**（投标人多+有文字层=统计显著性极高）
2. L5元数据 → 注意平台Aspose.PDF转换覆写风险
3. L1报价 → 大样本统计（极差/标准差/正态性检验/评标基准价偏离度）
4. L8工商关联 → 22家中找关联对更易
5. 无需OCR → 大型投标文件通常有文字层

### L11：供应商伴随投标（跨项目共现分析）

**原理**：围标集团的特征是"固定伙伴、轮流中标"。如果A、B、C三家公司在N个项目中频繁共同出现，且中标人始终是固定的某一家，则构成围标集团的强信号。

**数据要求**：至少3个以上同类项目的投标人名单 + 中标结果

**检测方法**：

```python
# 跨项目共现矩阵构建
for 每个项目 proj_i:
    bidders_i = set(proj_i的投标人)

for 任意两家公司(A, B):
    共现次数 = sum(1 for proj if {A,B} ⊆ proj.投标人)
    共现率 = 共现次数 / (A的投标次数 + B的投标次数 - 共现次数)

# 围标信号判定
if 共现次数 >= 3 and 共现率 >= 0.6:
    if 其中一家始终中标:
        → 🔴 围标集团
    else:
        → 🟡 固定陪标伙伴
```

**输出指标**：

| 指标 | 计算方式 | 阈值 |
|:-----|:---------|:-----|
| Jaccard共现系数 | |A∩B| / |A∪B| | ≥0.6 可疑 |
| 中标集中度 | max(某家中标次数) / 集团总投标次数 | ≥0.8 = 固定中标人 |
| 集团规模 | 核心集团的成员数 | ≥3家 = 完整围标生态 |
| 时空一致性 | 集团成员是否在相同区域/时间段活跃 | 辅助判断 |

**参考来源**：《政府采购法》要求≥3家供应商 → 围标方必须拉"小伙伴"→ 小伙伴关系会在跨项目数据中显现。

### L12：历史投标异常关联（异常标记库）

**原理**：每一次审计发现的异常（IP重复/元数据同源/文本雷同）应存入"异常标记库"。未来项目中，只要有两家被标记过的公司同时出现，系统自动预警。这正是海南省"机器管招投标"系统的思路——历史IP重复=永久关联。

**数据模型**：

```yaml
异常标记记录:
  关联ID: "ASN-2026-001"
  来源项目: "宿舍监理"
  关联公司: ["四川伟业启航", "四川五行建设"]
  异常类型: "TF-IDF文本雷同"
  证据强度: 0.7787
  发现日期: "2026-05-27"
  发现工具: "L3-TFIDF"
  
  关联ID: "ASN-2026-002"
  来源项目: "急救实训室"
  关联公司: ["易可天地", "江西正好"]
  异常类型: "L5元数据同源"
  证据强度: 0.95 (Author字段完全一致)
  发现日期: "2026-05-27"
  发现工具: "L5-元数据"
```

**查询逻辑**：
```
新项目投标人名单 → 查询异常标记库
  → 任意两家公司存在于同一历史异常记录中？
    → 是 → 🔴 自动预警（历史关联复用）
    → 否 → 继续正常检测
```

**与海南省机器管招投标的关系**：海南省2024年《措施》明确要求"开标后自动比对IP/MAC/加密锁序列号，涉嫌串通的自动截留不得进入评标"。L12异常标记库+自动化检测脚本为融策客户提供**主动预警能力**，而非等待交易平台建设。

## 三、L5元数据检测的三种失效模式与应对

经过四个项目的实战，总结出L5元数据检测可能失效的三种模式：

### 模式1：平台统一转换覆写

| 特征 | 应对 |
|:-----|:-----|
| 全部投标人Producer/Creator/Author/CreationDate完全一致 | 核查招标文件是否也同源 → 如是，确认为平台行为 |
| 常见工具：Aspose.PDF for .NET, iTextSharp | L5层在本项目中无检测价值，转向L3 TF-IDF |
| 案例：宿舍监理项目22家全部一致 | 建议函调平台确认转换机制 |

### 模式2：人为清除元数据

| 特征 | 应对 |
|:-----|:-----|
| Producer/Creator/Author全空，但PDF内有WPS/软件签名残留 | **执行D1纵深检测**：WPS签名搜索 |
| PDF版本异常（1.4而非1.7） | JPEG量化表指纹比对(D2) |
| JPEG缺少FFD9尾部标记 | **行为本身即是证据**：清除元数据=反检测操作 |
| 案例：艺术团项目胤皓 | 报告写入"投标人执行反检测操作" |

### 模式3：文件物理扫描/损坏

| 特征 | 应对 |
|:-----|:-----|
| Producer=扫描仪型号(RICOH/KONICA MINOLTA) | 提取JFIF密度/扫描时间信息 |
| 0页或无法打开 | **文件无效本身就是审计问题** |
| 案例：艺术团太格(RICOH)、立美(损坏) | 如有效投标<3家，应终止采购 |

## 四、TF-IDF文本雷同分析的实战经验

### 三级分析策略

```
第一级：char_wb (3-5 gram) — 快速筛查
  ├─ ≥0.95 → 模板文本高度重叠（可能正常，需确认是标准格式）
  ├─ 0.90-0.95 → 需关注
  └─ <0.90 → 正常

第二级：word级 (jieba分词, 1-2 gram) — 核心指标
  ├─ ≥0.80 → 🔴 高度可疑（几乎可以认定文本共享）
  ├─ 0.70-0.79 → 🔴 非常可疑（需段落级比对确认）
  ├─ 0.50-0.69 → 🟡 需关注（可能为行业标准文本或模板）
  └─ <0.50 → 🟢 正常

第三级：段落级精确匹配 — 定性确认
  对第二级≥0.70的投标人对，用difflib.SequenceMatcher做段落级比对
```

### 关键参数

```python
# char_wb（快速，适合大样本）
TfidfVectorizer(analyzer='char_wb', ngram_range=(3,5), max_features=5000)

# word级（精确，适合深度分析）
TfidfVectorizer(analyzer='word', max_features=8000, ngram_range=(1,2))

# 必须使用jieba分词（中文标准）
jieba.cut(text)
```

### 误判排除（⚠️ 阜新审计局案例+实战验证）

以下三种情况**不能直接定性为串标**（来源：《中国审计》2023年19期）：

1. **招标文件引用**：投标人编制技术标时大量引用招标文件原文 → 各投标人部分内容完全一致，甚至招标文件中的文字错误也会一致
2. **公开渠道内容**：技术方案中引用的标准规范、政策文件等可公开检索到的内容 → 即使完全一致也不能认定串通
3. **官网/公示栏文件**：某章节内容一致 → 需核实是否为有关单位在官网、公示栏公开发布过的文件

**应对**：
- 文本提取时过滤manifestly template sections（投标函、法定代表人证明、授权委托书）
- 对≥0.70的投标人对做**段落级精确匹配**，区分"引用公共文本"和"抄袭竞争对手文本"
- 结合L8（工商关联）交叉验证：高相似+无关联=可能引用公共文本；高相似+有关联=串标可能性大

## 六、标准作业程序（SOP）

### Phase 1: 进场（5分钟）

```
1. 确认项目类型（货物/服务/工程）
2. 统计投标人数量
3. 用PyMuPDF抽样检查前3家PDF：
   - 是否有文字层？(doc[0].get_text())
   - 元数据状态？(doc.metadata)
   - 文件大小/页数？
→ 确定分析策略（类型A/B/C）
```

### Phase 2: L5元数据全量扫描（3分钟）

```
对全部投标人提取：
  Producer / Creator / Author / CreationDate / ModDate

→ 全部一致？→ 平台转换（记录，L5失效）
→ 部分一致？→ 🔴串标信号（深挖）
→ 全部不同？→ ✅正常
→ 有空白？→ 执行D1纵深检测
```

### Phase 3: L4图片哈希（2分钟）

```
PyMuPDF提取全部PDF嵌入图片 → SHA256哈希
→ 跨公司重复？→ 🔴铁证
→ 无重复？→ ✅正常
```

### Phase 4: L1报价分析（需报价数据）

```
如有报价数据：
  极差/标准差/限价比/等差数列检测/分项报价品牌交叉
如无报价数据：
  标注缺失，建议从公示/评标报告中提取
```

### Phase 5: L3 TF-IDF（根据项目规模）

```
如有文字层+≥5家投标人：
  提取文本 → jieba分词 → TF-IDF → 相似度矩阵
如全扫描件+≤5家：
  标注无法执行（L3 N/A）
```

### Phase 6: L8/L9/L10（向外部调取）

```
L8: 天眼查/企查查查询（网络可行时程序化，否则手动）
L9: 向交易中心函调保证金缴纳记录
L10: 从评标报告/公示中提取评分数据
```

### Phase 7: 报告输出

```
生成Excel（6-8 Sheet）：
  1. 审计发现问题清单（含风险等级/证据/建议）
  2. 十层检测全量结果
  3. L5-元数据详情
  4. TF-IDF分析（如适用）
  5. 项目基本信息
  6. 后续行动建议（按优先级排序）
  7. 纵深检测结果（如适用）
```

## 七、关键经验教训

### 1. 永远不要以"只有PDF"为由跳过检测

> ❌ 错误判断：PDF不能提取图片/元数据 → 跳过L4/L5/L6
> ✅ 正确做法：PyMuPDF可以从任何正常PDF提取嵌入图片、元数据和字体

**教训来源**：急救实训室项目初次分析时跳过L4/L5/L6，用户纠正后补做，L5发现了易可天地=江西正好的元数据同一性（铁证级）。

### 2. 元数据被清除≠无迹可寻

> ❌ 浅层分析：元数据空白 → 无法分析 → 标记"数据缺失"
> ✅ 深度分析：元数据空白 + WPS签名残留 = 故意清除行为（本身即证据）

**教训来源**：艺术团项目胤皓PDF，标准元数据全空但内部11处WPS签名残留，证明WPS创建后人为清除。

### 3. 平台转换覆写元数据需区分

> ❌ 误判：22家元数据全部一致 → 串标铁证！
> ✅ 正确：核查招标文件是否同源 → 是 → 平台行为，非串标信号

**教训来源**：宿舍监理项目22家全部相同元数据，但招标文件也相同，确认为德阳交易平台Aspose.PDF转换。

### 4. 全扫描件项目 = 多维度受限

> 艺术团项目经验：
> - 3家投标文件：全扫描/物理扫描/损坏 → L3+L5+L6+L7全部无法执行
> - 归档资料同时损坏 → L1+L10也无法获取
> - **三种不同的规避方式恰好互补，客观形成检测盲区**
> - 应对：转向JPEG内部结构分析(D2-D4)，从像素和压缩指纹获取信号

### 5. 大数据量项目 = TF-IDF是王牌

> 宿舍监理项目经验：
> - 22家投标人有文字层 → L3成为最强大的维度
> - 93%正常对 vs 2.2%异常对 → 统计显著性极高
> - 发现6家投标人的集群，其中的"中心节点"投标人值得重点调查

## 八、快速检测决策树

```
收到招投标审计项目
│
├─ 有原始.docx文件？
│   ├─ 是 → 优先提取OLE2元数据（作者/修订历史）→ 价值最高
│   └─ 否 → 进入PDF检测
│
├─ PDF有文字层？
│   ├─ 是 + 投标人多(≥10家) → 🔥 TF-IDF是王牌
│   ├─ 是 + 投标人少(3-5家) → L5元数据 > L4图片 > L3文本
│   └─ 否（全扫描件） → D1-D5数字取证级
│
├─ 元数据状态？
│   ├─ 全部一致 → 核查是否平台转换（看招标文件元数据）
│   ├─ 部分一致 → 🔴 立即深挖该组
│   ├─ 全部空白 → D1 WPS签名搜索
│   └─ 全部不同 → ✅ 正常，转向其他维度
│
├─ 报价数据可获得？
│   ├─ 是 → L1价格规律分析（极差/标准差/正态性/限价比）
│   └─ 否 → 从公示OCR提取，或标记缺失
│
└─ 最终输出 → Excel审计报告（7 Sheet标准模板）
```
