# SkillX 方法论 → 政府审计领域映射

> 基于浙江大学 ZJUNLP SkillX 框架（三级技能分层+自动提炼流水线），为融策会计师事务所政府专项审计构建的技能知识库方法论。
>
> 设计日期：2026-05-19

---

## 零、SkillX 回顾

SkillX 的核心贡献：
1. **三级技能分层**：规划技能 → 功能技能 → 原子技能
2. **自动提炼**：从 Agent 执行轨迹 → 迭代提取/合并/过滤 → 即插即用技能库
3. **跨模型可复用**：弱模型注入强模型技能库，提升约10%

## 一、审计领域的"执行轨迹"是什么？

SkillX 的原始输入是 Agent 的 rollout 轨迹（API调用序列+环境反馈）。在审计领域，对应的是：

| SkillX 概念 | 审计领域对应 |
|------------|------------|
| **Agent 执行轨迹** | 一个完整审计项目的所有工作产出：底稿、数据分析脚本、问题发现、报告段落 |
| **rollout** | 同一审计类型（如绩效评价）的多个历史项目 |
| **环境反馈** | 被审计单位的回应、复核意见、客户反馈、监管指导意见 |
| **工具 API** | 具体审计程序：抽样、函证、盘点、Benford测试、SQL查询、文档比对等 |

## 二、三级审计技能层映射

### 2.1 原子技能（Atomic Skills）— 对齐单个审计程序

**定义**：单个审计程序/工具的使用规范，补充了审计准则约束、常见陷阱、参数配置模式。

**结构**：
```
{
  "name": "string",           // 技能名称
  "tool": "string",           // 对齐的审计程序
  "description": "string",    // 增强描述
  "constraints": ["..."],     // 合规约束（来源：审计准则/政策）
  "param_patterns": {...},    // 典型参数配置模式
  "failure_modes": ["..."],   // 常见失败模式
  "use_conditions": ["..."],  // 适用条件
  "evidence_standard": "..."  // 证据标准
}
```

**审计原子技能示例**：

```
原子技能 #1: "凭证分层抽样"
  tool: voucher-sampling
  约束: [样本量≥30（统计推断下限）, 分层至少3层按金额, 必须包含全部5万以上支出]
  参数模式: {method: "分层抽样", strata_fields: ["支出金额"], strata_rules: {"大额层": "≥50000", "中层": "10000-49999", "小层": "<10000"}}
  失败模式: [样本量不足导致无法推断总体, 仅抽大额忽略小额但多次的舞弊风险, 分层标准与审计目标不匹配]

原子技能 #2: "Benford 首数字检验"
  tool: benford-test
  约束: [数据量≥1000, 排除人工设定值(如1000元整的固定资产标准线), MAD≥0.015为异常]
  参数模式: {column: "支出金额", digits: 1, grouping: "按月"}
  适用条件: 自然产生的数值数据，非人工设定值，无固定上下限
  失败模式: [小样本假阳性, 未排除人工设定值, 将合规的四舍五入视为异常]

原子技能 #3: "采购合规性检查"
  tool: procurement-check
  约束: [必须检查化整为零, 必须比对政府采购网公告, 必须验证中小企业预留政策]
  参数模式: {threshold_map: {"自行采购": 10000, "公开比选": 50000, "代理机构": 100000, "政府采购": 500000}}
  失败模式: [只比金额不比时间(未发现拆分), 忽略单一来源采购的特殊审批要求]
```

### 2.2 功能技能（Functional Skills）— 对齐子任务工具组合

**定义**：完成一个审计子任务的完整操作序列——"用什么程序、按什么顺序、达到什么目的"。

**结构**：
```
{
  "name": "string",           // 技能名称
  "document": {               // 输入输出描述
    "goal": "string",         // 要达成的审计目标
    "inputs": ["..."],        // 需要的输入数据
    "outputs": ["..."],       // 产出的审计证据
    "applicable_audit_types": ["..."]
  },
  "content": {                // 工具调用模式
    "sequence": [...],        // 有序步骤
    "tools": [...],           // 使用的原子技能列表
    "branch_logic": {...}     // 分支条件
  },
  "typical_time_hours": 4-16
}
```

**审计功能技能示例**：

```
功能技能 #1: "固定资产盘点验证"
  目标: 验证固定资产的存在性、完整性、准确性
  输入: [资产台账, 折旧计算表, 盘点记录]
  输出: [盘点差异表, 折旧测算差异分析, 资产处置合规性评估]
  步骤序列:
    1. ledger-extract → 提取账面资产清单
    2. physical-verify → 按抽样规则实地核查
    3. depreciation-recalc → 重新计算折旧
    4. disposal-check → 检查处置程序是否合规(三重一大/评估/上级审批)
    5. discrepancy-analysis → 差异分析+原因归类
  组合: [抽样 → 实地核查 → 重计算 → 合规检查 → 差异分析]

功能技能 #2: "专项资金追踪"
  目标: 确认专项资金是否专款专用、是否按进度使用
  输入: [专项资金台账, 银行流水, 项目进度报告]
  输出: [资金流向图, 挪用/滞留问题清单, 进度-资金匹配分析]
  步骤序列:
    1. special-fund-extract → 提取专项资金台账
    2. bank-reconciliation → 银行流水比对
    3. flow-trace → 逐笔追踪资金去向
    4. progress-match → 比对资金使用进度与项目实际进度
    5. compliance-check → 对照专项资金管理办法逐条验证
  组合: [数据提取 → 银行对账 → 资金追踪 → 进度匹配 → 合规验证]

功能技能 #3: "三重一大决策程序检查"
  目标: 验证重大事项决策程序合规性
  输入: [会议纪要, 审批单, 合同台账, 大额支出清单]
  输出: [决策程序合规性矩阵, 违规事项清单]
  步骤序列:
    1. threshold-filter → 筛选5万元以上支出/50万以上采购/100万以上工程
    2. decision-trace → 追溯每笔大额支出的决策记录(会议纪要/审批单)
    3. quorum-check → 验证出席会议人数(≥2/3)
    4. agenda-check → 验证是否有会前议题准备(排除临时动议)
    5. voting-check → 验证表决记录是否完整
  组合: [金额过滤 → 决策追溯 → 法定人数 → 议程检查 → 表决验证]
```

### 2.3 规划技能（Planning Skills）— 对齐审计项目全流程

**定义**：同一审计类型的完整工作流模板——"先做什么、后做什么、关键风险点在哪里"。

**结构**：
```
{
  "name": "string",
  "audit_type": "string",     // 绩效评价 | 资产清查 | 专项债审计 | 监督检查 | 内控审计
  "phases": [...],            // 有序阶段
  "dependencies": {...},      // 阶段间依赖
  "branch_logic": {...},      // 条件分支
  "estimated_duration": {...},// 各阶段参考时长
  "critical_risks": [...]     // 关键风险点
}
```

**审计规划技能示例**：

```
规划技能 #1: "政府绩效评价审计"
  阶段:
    Phase 1 政策学习 (10%) → policy-digest + 指标体系提取
    Phase 2 实施方案 (15%) → 评价指标设计 + 评分标准 + 数据收集计划
    Phase 3 数据采集 (30%) → 多源数据收集(财务+统计+问卷+访谈)
    Phase 4 指标评分 (25%) → 逐指标打分 + 证据支撑
    Phase 5 问题发现 (15%) → 绩效偏差分析 + 原因追溯
    Phase 6 报告建议 (5%) → 绩效评价报告 + 改进建议
  分支: 
    if 预算执行率 < 80% → 深度分析资金滞留原因
    if 满意度 < 基准值 → 启动服务效能专项分析
  关键风险: [指标体系偏离政策目标, 数据采集覆盖面不足, 评分主观性]

规划技能 #2: "资产清查审计"
  阶段:
    Phase 1 制度学习 → 资产管理制度+配置标准+处置办法
    Phase 2 账面整理 → 资产台账核对+分类(固定/无形/低值)
    Phase 3 实地盘点 → 分层抽样+现场盘点+差异记录
    Phase 4 价值重估 → 折旧测试+减值评估
    Phase 5 处置审核 → 处置程序合规性+评估报告+审批文件
    Phase 6 报告 → 资产清查报告+盘盈盘亏明细
  分支:
    if 盘亏金额 > 资产总额5% → 启动专项调查
    if 发现未入账资产 → 追溯来源+补充登记
  关键风险: [账外资产遗漏, 处置程序不合规, 无形资产漏评]

规划技能 #3: "内控审计"
  阶段:
    Phase 1 内控制度收集 → 完整制度文件+流程图
    Phase 2 关键控制点识别 → 穿行测试+控制矩阵
    Phase 3 设计有效性测试 → 制度与准则对照
    Phase 4 执行有效性测试 → 抽样测试+实地观察+访谈
    Phase 5 缺陷认定 → 缺陷分类(重大/重要/一般)
    Phase 6 报告 → 内控审计报告+整改建议
  分支:
    if 发现重大缺陷 → 立即报告治理层
    if 关键岗位未轮岗 → 扩大实质性测试范围
  关键风险: [管理层凌驾内控, 制度与执行两张皮, 样本量不足]
```

### 3.3 审计特有的提炼增强

SkillX 的原始设计面向通用 Agent 任务，审计领域有独特的增强机会：

**增强1：审计准则约束注入**
在提取阶段，自动对照《中国注册会计师审计准则》验证技能有效性：
- 原子技能是否满足审计证据的充分性和适当性要求？
- 功能技能是否覆盖了应有的审计程序？
- 规划技能是否在审计准则允许的范围内？

**增强2：政策依据追溯**
每个技能项自动附加政策依据链接（法规条款号），使技能不仅"知道怎么做"，还"知道为什么这么做"。

**增强3：审计风险评估权重**
利用审计风险模型（AR = IR × CR × DR），给每个技能赋予风险敏感度参数：
- 高风险领域 → 更保守的参数配置
- 低风险领域 → 可以接受更大样本量灵活性

### 3.4 迭代优化中的审计特殊性

| SkillX 原始 | 审计领域特化 |
|------------|------------|
| 合并相似技能 | 合并且考虑审计类型差异（绩效评价的"抽样" vs 资产清查的"抽样"合并条件更严格） |
| 通用过滤 | 额外过滤：是否符合独立性要求、是否满足保密义务 |
| 工具验证 | 对照工具清单：不仅验证工具存在，还验证是否符合最新审计准则 |
| 回溯测试 | 用历史底稿验证：模拟运行技能，检查产出的审计证据是否达到原项目质量 |

## 四、检索与注入机制

### SkillX 原始流程
```
新任务 → 检索规划技能 → 伪规划改写 → 逐步检索功能/原子技能 → LLM自筛选 → 注入系统提示词
```

### 审计领域适配

```
新审计项目
  ↓
① 匹配审计类型（绩效评价/资产清查/...）
  → 检索 Top-3 规划技能
  → LLM 生成项目特定的伪规划
  ↓
② 按伪规划的阶段，逐阶段检索功能技能
  → 每个阶段去重 + LLM 自筛选保留适用技能
  ↓
③ 按筛选后的功能技能，检索关联的原子技能
  → 注入系统提示词 + 政策知识库(CLAUDE.md)
  ↓
④ Agent 基于注入的技能执行审计任务
  → 产出: 政策解读 / 分析底稿 / 问题发现 / 报告
  ↓
⑤ 项目完成后，新轨迹回流入库
  → 触发增量技能提炼
```

### 检索注入的技术细节

```python
# 伪代码
def prepare_audit_agent(audit_project: dict):
    # Step 1: 检索规划技能
    planning_skills = skills_db.retrieve(
        query=audit_project["audit_type"],
        tier="planning",
        top_k=3
    )
    
    # Step 2: 伪规划改写
    pseudo_plan = llm.generate(
        prompt=f"基于以下审计项目特征和参考规划技能，生成具体执行计划:\n"
               f"项目: {audit_project}\n"
               f"参考: {planning_skills}"
    )
    
    # Step 3: 按阶段检索功能技能
    all_func_skills = []
    for phase in pseudo_plan.phases:
        func_skills = skills_db.retrieve(
            query=phase.goal,
            tier="functional",
            top_k=5
        )
        all_func_skills.extend(func_skills)
    
    # Step 4: LLM 自筛选
    filtered_func = llm.filter(
        skills=all_func_skills,
        context=audit_project,
        criteria="仅保留适用于本项目的技能"
    )
    
    # Step 5: 关联原子技能
    atomic_skills = skills_db.retrieve_by_relations(
        func_skills=filtered_func,
        tier="atomic"
    )
    
    # Step 6: 注入 agent 系统提示词
    agent_prompt = compose_prompt(
        policy_knowledge=CLAUDE_md,
        planning_skills=pseudo_plan,
        functional_skills=filtered_func,
        atomic_skills=atomic_skills
    )
    
    return agent_prompt
```

## 六、关键决策与设计选择

### 为什么选择 JSON 而非 YAML？
审计技能包含大量嵌套约束和条件逻辑，JSON 更易于程序化检索和验证。LLM 对 JSON 的结构化理解也更稳定。

### 为什么不直接复制 SkillX 代码？
SkillX 面向通用 Agent 任务（BFCL/AppWorld/τ²-Bench），审计领域需要：
1. 审计准则约束注入层
2. 政策依据追溯机制
3. 审计风险模型集成
4. 审计证据标准验证

这些是领域特有的，需要在方法论层面做适配，而非简单代码复用。

### 渐进策略
不追求一步到位全自动化。先手工构建初始技能库（用已知的审计知识）→ 积累足够的项目轨迹 → 再启动自动提炼流水线。这样可以避免"冷启动"问题（SkillX 需要种子训练数据）。
