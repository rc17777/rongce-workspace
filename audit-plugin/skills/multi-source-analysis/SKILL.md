# 多源数据综合分析 (Multi-Source Analysis)

## 元数据

- **类型**：interactive（交互式）
- **命令**：`/audit:multi-source-analysis`
- **前置条件**：需 CLAUDE.md（政策知识库+数据源+审计方法）
- **输入**：财务数据 + 业务数据 + 非结构化文本 + 访谈记录 + 实地考察记录
- **输出**：多源交叉分析底稿（DRAFT）

---

## 目标

不是做单一数据分析。是 **把财务数据、业务数据、文本证据、访谈记录、实地观察放在一起交叉验证**。

核心逻辑：政策怎么要求的 → 实际怎么做的 → 钱怎么花的 → 效果怎么样 → 四个维度交叉找矛盾。

**数据分析遵循五步法**（详见 `data-analysis-methods` 技能）：
①提出问题 → ②获取数据 → ③清洗处理 → ④分析建模 → ⑤得出结论

---

## 可用审计方法

| 方法 | 适用数据类型 | 首选工具 |
|------|------------|---------|
| 查阅法 | 政策文件、合同、凭证、会议纪要 | 文档审阅 |
| 数据分析 | 财务数据、业务台账 | → `data-analysis-methods` 选方法 |

| 实地考察 | 项目现场、实物资产 | 现场观察记录 |
| 函证 | 银行、往来单位 | 函证回函 |
| 穿行测试 | 业务流程全链条 | 逐环节验证 |
| 财务核查 | 记账凭证、原始凭证 | 凭证抽查 |
| 对比分析 | 多期数据、同类项目 | 同期/同类比较 |
| 复核计算 | 工程量、拨款金额 | 重新计算 |

## 工作流程

### 第一步：数据接入

```
/audit:multi-source-analysis --data D:\项目\数据\
```

自动识别数据类型并分派分析方法：

| 数据类型 | 识别特征 | 分派方法 |
|---------|---------|---------|
| 财务报表/科目余额表 | 借贷结构、科目编码 | 财务核查+对比分析 |
| 资金拨付台账 | 拨付日期/金额/单位 | 数据分析（进度追踪） |
| 项目进度表 | 任务/完成率/时间 | 对比分析（计划vs实际） |
| 合同台账 | 合同编号/金额/签署方 | 查阅法（条款审核） |
| 访谈记录 | 问答文本 | 结构化提取 |
| 实地考察照片/记录 | 图片+文字说明 | 交叉验证 |

### 第二步：逐维度分析

#### A. 资金维度

```
数据源：财务数据 + 资金拨付台账 + 政策要求

分析逻辑：
1. 资金来源 → 配套资金是否到位？
2. 资金拨付 → 拨付时间和金额是否合规？
3. 资金使用 → 支出是否在允许范围内？
4. 资金结余 → 结余是否按规定处理？
5. 资金效益 → 投入产出是否合理？
```

#### B. 程序维度

```
数据源：项目档案 + 合同 + 会议纪要 + 穿行测试记录

分析逻辑：
1. 立项 → 审批程序是否完整？
2. 采购 → 招投标/比选是否合规？
3. 实施 → 变更是否按程序报批？
4. 验收 → 验收标准和程序是否遵循？
```

#### C. 绩效维度

```
数据源：绩效自评报告 + 业务数据 + 实地考察 + 访谈

分析逻辑：
1. 产出 → 申报的产出数据是否可验证？
2. 效益 → 是否达到预期的社会/经济效益？
3. 满意度 → 受益对象反馈如何？
```

### 第三步：交叉验证

这是最关键的一步。**找矛盾**。

> 💡 核心原则：**单一来源的信息不能支撑结论。** 至少两个独立来源指向同一方向，才算站得住脚。

#### 五维交叉验证框架

AI处理的是一个数据库里的数据。但现实世界里，真相往往藏在不同来源、不同形态的信息之间的缝隙里。交叉验证，是人类审计员最被低估的核心技能。

| 维度 | 验证内容 | 核心问题 | 典型矛盾信号 |
|------|---------|---------|------------|
| **1. 财务数据维** | 账面记录 / 银行流水 / 票据凭证 | 三者任意两个对不上，就要问为什么 | 凭证金额≠银行流水金额 / 入账日期≠实际收付日期 |
| **2. 实物现场维** | 台账资产 vs 现场实物 / 竣工量 vs 现场实测 | 台账上的资产能不能在现场找到？ | 资产台账有但现场找不到 / 竣工报告100%但实测不足 |
| **3. 人员访谈维** | 同一件事问三个不同岗位的人 | 答案是否一致？不一致的地方是重点 | 财务说已验收、使用部门说没用过 / 领导说没问题、经办人说有压力 |
| **4. 外部信息维** | 工商登记 / 司法查询 / 招投标网站 / 行业价格指数 | 账面之外的参照系 | 供应商成立日 < 合同启动日 / 采购价远超行业均价 |
| **5. 时间逻辑维** | 事件发生的先后顺序 | 时间线在逻辑上说得通吗？ | 合同签了但招标还没开始 / 验收报告日期早于完工日期 |

#### 交叉验证矩阵（示例）

```markdown
| 验证项 | 数据源A | 数据源B | 是否一致 | 验证维度 | 问题标记 |
|--------|---------|---------|---------|---------|---------|
| 某项目完工 | 进度表显示100% | 实地考察发现未完工 | ❌ | 实物现场维 | 虚假进度 |
| 某笔资金使用 | 财务凭证显示为材料费 | 合同显示为设备采购 | ❌ | 财务数据维 | 科目误列 |
| 某采购项目 | 合同签署日期1月 | 会议纪要显示2月讨论 | ❌ | 时间逻辑维 | 先签后议 |
| 受益人数 | 自评报告称500人 | 访谈显示实际约200人 | ❌ | 人员访谈维 | 绩效虚报 |
| 供应商资质 | 工商登记显示成立3个月 | 中标200万项目 | ❌ | 外部信息维 | 供应商存疑 |
```

#### 交叉验证操作指南

1. **每个关键结论至少用两个独立来源交叉验证**——单一来源不得作为结论依据
2. **优先关注跨维度的矛盾**——资金维+时间维的矛盾 > 单一维度的矛盾
3. **访谈维是第一优先级补充手段**——很多时候数据天衣无缝，一个电话就问出破绽
4. **外部信息维常用于打破信息茧房**——当内部数据过于一致时，用外部参照系来校准

#### 案例：五维验证发现虚假验收

> 某IT项目，财务数据显示已付款完毕，验收报告有甲乙双方签字，合同归档完整，AI全部通过。
> 审计员做了一件事：打电话给项目实际使用部门的一个普通员工，问："这套系统你们现在用得怎么样？"
> 对方沉默片刻："什么系统？我们部门没用过这个。"
>
> 验收报告是假的。资金已经划走。数据层面，零异常。
>
> 📌 单一维度绿灯 ≠ 没问题。关键时刻，**人员访谈维**可以一击击穿多层伪装。

## 参数

```
/audit:multi-source-analysis                        → 全维度分析
/audit:multi-source-analysis --focus 资金            → 只做资金维度
/audit:multi-source-analysis --focus 程序            → 只做程序维度
/audit:multi-source-analysis --focus 绩效            → 只做绩效维度
/audit:multi-source-analysis --method 财务核查       → 指定方法
/audit:multi-source-analysis --cross-verify          → 专门做交叉验证
```

### 数据分析工作流（嵌入五步法）

```
审计问题 → 五步法 → 结果
    ↓
问题: "供应商付款中是否有围标串标？"
    ↓ ①提出问题
假设: "如果围标，会出现: 多家投标→同一地址/联系方式/控制人"
    ↓ ②获取数据
数据: 投标记录表 + 供应商工商信息 + 联系方式比对
    ↓ ③清洗处理
清洗: 验证供应商名称标准化、去空值、检查数据完整性
    ↓ ④分析建模
方法: 关联规则+网络分析 → Python networkx
    ↓ ⑤得出结论
判读: 数据异常的供应商群组 → 现场核查确认 → CPA判断
```
