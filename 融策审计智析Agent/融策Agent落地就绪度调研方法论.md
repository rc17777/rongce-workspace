# 融策审计智析Agent — 落地就绪度调研方法论

> 设计原则：不到融策办公室坐着看审计员干活，就别谈"落地"。
> 本方法论的目标：从"22个工具在代码仓库里" → "X个工具在审计项目里跑通了"

---

## 一、调研设计：五个维度 × 三层深度

### 五个调研维度

| 维度 | 核心问题 | 不做会怎样 |
|------|---------|-----------|
| **D1. 流程维度** | 审计项目从接单到归档，实际怎么走的？ | Agent嵌入点找不到，工具再强也用不上 |
| **D2. 数据维度** | 审计员每天面对的数据长什么样？ | 工具在构造数据上跑得再好，拿到真实数据就崩 |
| **D3. 人力维度** | 谁在用？什么水平？怕什么？ | 工具复杂度超过承受能力→没人用 |
| **D4. 输出维度** | 审计报告长什么样？谁看？怎么被评价？ | Agent输出格式不对→审计员手动重写→Agent白做 |
| **D5. 约束维度** | 数据安全红线在哪？审批流程是什么？ | 碰了红线→项目直接被毙 |

### 三层深度

**L1 桌面调研**（自己先做功课）→ **L2 随岗观察**（坐在审计员旁边看）→ **L3 深度访谈**（带着发现去问为什么）

---

## 二、L1：桌面调研（产出：审计流程假设图）

### 输入材料清单

在去找融策之前，先收集：
1. 融策官网/公开资料中的业务介绍
2. 政府采购网/招标网上的融策中标公告（看他们接了哪些项目）
3. 审计行业通用的标准流程（政府审计+工程审计）
4. 一份典型的政府审计报告模板（网上公开的即可）

### 具体动作

基于以上材料，绘制 **"假设版"审计流程泳道图**，覆盖以下阶段：

```
Phase 1: 项目承接
  ├─ 招标/委托 → 签订合同 → 组建审计组
  └─ 你的假设：[Agent嵌入点] 项目类型自动匹配Agent配置

Phase 2: 审前准备
  ├─ 收集被审计单位资料 → 制定审计方案 → 发送审计通知书
  └─ 你的假设：[Agent嵌入点] 数据就绪度评估 + 风险场景自动识别

Phase 3: 现场实施
  ├─ 数据分析 → 凭证抽查 → 访谈 → 底稿编制
  └─ 你的假设：[Agent嵌入点] 文本分析+统计检测→自动标记疑点→底稿自动填充

Phase 4: 报告阶段
  ├─ 底稿复核(L1→L2→L3) → 征求意见 → 正式报告
  └─ 你的假设：[Agent嵌入点] L1自动评分→定性模板→报告段落生成

Phase 5: 整改跟踪
  ├─ 整改通知 → 整改验收 → 归档
  └─ 你的假设：[Agent嵌入点] 整改状态追踪 + 时效监控
```

**这一步的输出**：一页A3流程图，标注了所有假设的Agent嵌入点。**用红笔圈出你最不确定的3个假设**——这就是L2-L3要重点验证的。

### 检验标准

✅ 流程图能被一个没做过审计的人看懂
✅ 每个Phase至少标注了1个Agent嵌入点假设
✅ 有至少3个"红圈"（不确定的假设）

## 三、L2：随岗观察（产出：真实流程偏差清单）

### 操作方式

申请在融策审计组**坐班1天**。不是开会，不是演示——就是坐在审计员旁边，看他们干活。征得同意后，记录但不打扰。

### 观察清单（带计时）

| 时间段 | 观察什么 | 记录什么 |
|--------|---------|---------|
| 09:00-09:30 | 打开电脑先干什么？ | 第一个打开的软件/文件 |
| 09:30-11:00 | 核心工作时间做什么？ | 操作类型+工具+耗时 |
| 11:00-11:30 | 遇到什么问题中断了？ | 中断原因+解决方式 |
| 14:00-16:00 | 下午主要产出什么？ | 产出物类型+格式 |
| 16:00-17:00 | 怎么和同事协作？ | 沟通方式+频率+内容 |

### 重点捕捉的"关键时刻"

1. **"等等我找个模板"** → 他们在找什么模板？从哪找？
2. **"这个数对不上"** → 什么数据和什么数据对不上？怎么排查的？
3. **"上次我们查那个项目就…"** → 经验怎么传递？有记录吗？
4. **"这个没法查，数据拿不到"** → 什么数据？为什么拿不到？
5. **"组长说要再核实一下"** → 复核流程实际怎么触发？
6. **叹气/抱怨/骂人** → 什么环节最痛苦？记录下来，这就是Agent最能发挥作用的地方

### 输出：偏差清单

| L1假设 | L2实际观察 | 偏差 | 对Agent设计的影响 |
|--------|-----------|------|------------------|
| 假设：审计员会用Python脚本处理数据 | 实际：全程Excel，VLOOKUP+透视表 | 🔴 严重 | DSG需要输出Excel公式而非Python？ |
| 假设：底稿是逐份编制 | 实际：先做汇总表，再拆成底稿 | 🟡 中等 | 评分引擎需要先评汇总表 |
| 假设：... | 实际：... | ... | ... |

### 检验标准

✅ 至少记录10个"关键时刻"
✅ 偏差清单至少5项
✅ 能说出"审计员最痛苦的3个环节"——不是你以为的，是他们实际表现出来的

## 四、L3：深度访谈（产出：需求优先级矩阵）

### 访谈对象（按顺序）

1. **一线审计员**（1-2名）—— 日常操作者，最清楚痛点
2. **项目组长**（1名）—— 负责复核和质量控制，最清楚"什么会出问题"
3. **部门负责人**（1名）—— 负责资源分配和客户关系，最清楚"什么最重要"

### 访谈提纲（结构化，不是闲聊）

#### 给一线审计员（30分钟）

```
1. 你最近做完的一个项目，从头到尾花了多长时间？
   追问：哪个环节花的时间最长？如果这个环节能提速50%，你会拿省下的时间做什么？

2. （拿出偏差清单）我们在你旁边观察发现你做X的时候会[具体行为]，
   这是每次都这样，还是这个项目特殊？

3. 如果你有一个助手，可以帮你做一件事（只说一件），你希望是什么？
   追问：这件事你现在怎么做？花多少时间？有多频繁？

4. 你们现在的审计软件/工具，最不想用的是什么？为什么？
   追问：如果必须保留一个功能，你留哪个？

5. （拿出v9证据链图谱的HTML截图）如果审计报告里能附带这样一张图，
   你觉得组长会怎么看？客户会怎么看？
```

#### 给项目组长（45分钟）

```
1. 你复核一份底稿平均花多长时间？复核中最常发现的问题是什么？
   追问：如果系统能在你复核之前先标出"这3份底稿最可能有质量问题"，
   你会怎么用？

2. 你们最近有没有审计结论被客户质疑过？什么原因？
   追问：如果当时能拿出[展示v10法释条文+x证据链]，
   你觉得能挡住质疑吗？

3. 一个项目从进场到出报告，你希望控制在多长时间内？
   追问：实际平均多长时间？差距最大的环节是哪个？

4. 如果要让AI工具进入你的项目组，你最担心什么？
   追问（逐个确认）：数据安全？结果不准？审计员不会用？领导不接受？

5. （列出22个Agent工具清单）你觉得哪些工具在你的项目里最可能用到？
   哪些完全用不到？为什么？
```

#### 给部门负责人（30分钟）

```
1. 你们现在接项目，最有利润的是哪类？最不赚钱的是哪类？
   追问：如果AI能让最不赚钱的项目的人工投入减半，会改变你们的接单策略吗？

2. 客户对你们的审计报告最常提的意见是什么？
   追问：是报告太慢了？还是发现的问题太少？还是表达不够有力？

3. 如果要推行AI审计工具，你们内部最大的阻力可能来自哪里？
   追问：预算？技术能力？审计员的抵触？数据安全的顾虑？

4. 你理想中的"融策+AI"，1年后是什么状态？
```

### 输出：需求优先级矩阵

将所有发现的需求填入四象限：

```
          高频                    低频
    ┌──────────────┬──────────────┐
    │ P0 立刻做     │ P2 按需做     │
高痛│ ──────────── │ ──────────── │
    │ 例：底稿复核  │ 例：Benford   │
    │     自动化    │     专项检测  │
    ├──────────────┼──────────────┤
    │ P1 尽快做     │ P3 暂不做     │
低痛│ ──────────── │ ──────────── │
    │ 例：合同提取  │ 例：热词分析  │
    └──────────────┴──────────────┘
```

判据：
- 高频 = 每个项目都遇到 / 每天都要做
- 高痛 = 不做会显著影响质量/效率 / 被骂 / 被质疑
- P0 = 高频+高痛 → 这就是Agent的MVP范围

### 检验标准

✅ 需求矩阵至少填充8项
✅ P0象限至少3项（高频+高痛）
✅ 能和偏差清单互证——L2观察到的"最痛苦的3个环节"应该在P0或P1象限中

## 五、从调研到路线图：四步转化

有了上面的输出，转化成落地路线图只需要四步。

### Step 1：确定MVP范围（砍掉80%）

基于需求优先级矩阵的P0象限 + 数据可得性 + 工具成熟度，选出**3个以内**的首批落地场景。

选择标准：
- ✅ 数据能拿到（这是硬门槛——拿不到数据的工具，再好也不用）
- ✅ 工具已实现（v3-v11已开发的工具中选，不开发新的）
- ✅ 效果可量化（能说出"以前花X小时，现在花Y分钟"）
- ✅ 审计员能接受（不是"替代你"而是"帮你省掉最烦的那部分"）

**建议候选**：
- 合同字段提取+支付交叉比对（v4 contract_field_extract）→ 数据可拿到（合同+付款记录都在）
- 底稿质量自动评分（v3 workpaper_scorer）→ 组长复核刚需
- 翻凭证模板（v8 AP/AR/EXP/FA）→ 审计员每天都要做

### Step 2：设计嵌入点（不是"替换"是"插入"）

在L2的真实流程图上，标注Agent的嵌入位置——不是替换哪个环节，而是**插入到两个已有环节之间**。

```
现有流程：  数据导出 → 人工清洗 → VLOOKUP比对 → 标记异常 → 编制底稿
Agent嵌入： 数据导出 → [Agent:数据就绪评估] → 人工清洗 → [Agent:多工具并行分析] → [Agent:自动标记] → 人工确认 → 编制底稿 → [Agent:自动评分] → 组长复核
```

关键原则：**Agent只做"标记"不做"结论"**——每个Agent输出都要经过人工确认。

### Step 3：选一个真实项目做Pilot

不是"找个数据集跑一下"，而是选一个**融策正在做或刚做完的真实审计项目**。

操作：
1. 从已结项的项目中选1个（数据完整、结论已知、不涉密或已脱敏）
2. 把项目的原始数据（合同、凭证、流水、报表）导出
3. 用Agent重新跑一遍分析
4. 对比：Agent检出异常 vs 原始审计报告中的发现
5. 计算：检出率、误报率、漏报率
6. 让原项目组长评价："AI发现的东西，有没有价值？有没有我们漏掉的？有没有误报？"

### Step 4：量化效果，写成一页纸

Pilot跑完之后，输出一张对比表：

| 指标 | 纯人工 | 人工+Agent | 差异 |
|------|--------|-----------|------|
| 总耗时 | X小时 | Y小时 | -Z% |
| 检出异常数 | A个 | B个 | +C个（其中D个为人工遗漏） |
| 误报数 | E个 | F个 | 需评估可接受性 |
| 底稿评分 | G分 | H分 | +I分 |
| 组长复核时间 | J小时 | K小时 | -L% |

**这张表就是融策Agent落地的第一份证据**——用真实数据、真实项目、真实对比来说服所有人。

调研结束后，交付以下5份文档：

| # | 文档 | 内容 | 长度 |
|---|------|------|------|
| 1 | 审计流程真实泳道图 | L1假设→L2修正→Agent嵌入点标注 | 1页A3 |
| 2 | 需求优先级矩阵 | 四象限图 + 每项需求的详细说明 | 2-3页 |
| 3 | 数据可得性评估表 | 22个工具 × 融策实际数据源 → 可用/不可用/需改造 | 1页 |
| 4 | MVP落地场景建议 | 3个以内场景 + 嵌入流程 + 预期效果 + 风险 | 3-5页 |
| 5 | Pilot项目选择建议 | 推荐项目 + 选择理由 + 数据清单 + 对比方案 | 1-2页 |

## 七、检验闭环

整个调研方法论是否有效，用以下5个问题检验：

### 如果调研后能回答这5个问题→方法论有效

1. **融策审计员每天花最多时间的3件事是什么？**（不能猜，必须从L2观察+计时中得出）
2. **哪个环节的"人工投入/产出价值比"最低？**（即最值得Agent替换的环节）
3. **融策的真实数据中，字段缺失率最高的是哪类数据？**（决定工具的输入容错策略）
4. **如果要在一个月内让一个Agent工具在融策真实项目上跑通，选哪个工具？**（为什么是这个不是别的）
5. **如果Agent工具跑出的结果和审计组长判断不一致，怎么处理？**（不是技术问题，是组织流程问题——但必须答）

### 如果有一个问题答不上来→调研不够深，回到L2重复
